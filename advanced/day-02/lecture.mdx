## 1. Как текст становится программой {#text}

Вчера мы читали алгоритмы — вторую половину спецификации. Но прежде чем выполняться,
программа должна быть *прочитана*: из строки символов получается структура, которую можно
вычислять. Как именно — описывают грамматики, и вся страница MDN
[Lexical grammar](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Lexical_grammar)
посвящена первому шагу этого пути.

Отсюда главное различие ошибок: `SyntaxError` не даёт скрипту начаться (поэтому на
дне 26 курса 2 ошибку разбора не поймал `try` того же скрипта), а `TypeError`
или `ReferenceError` случаются на ходу. Первое — дело грамматик и ранних ошибок, второе —
алгоритмов.

## 2. Три грамматики и число двоеточий {#grammars}

Раздел [5.1.1](https://tc39.es/ecma262/2026/#sec-context-free-grammars) определяет
**бесконтекстную грамматику**: набор правил-продукций. У каждого правила слева —
**нетерминал**, абстрактное имя, справа — последовательность нетерминалов и
**терминалов**, «букв» этой грамматики. Начинают с одного нетерминала — **цели** —
и раз за разом заменяют нетерминалы правыми частями правил; все цепочки терминалов, которые так
получаются, и есть язык грамматики.

Грамматик в спецификации несколько, и различают их по числу двоеточий в правилах:

| Грамматика | Буквы (терминалы) | Цель | Знак |
| --- | --- | --- | --- |
| лексическая, глава 12 (5.1.2) | кодовые точки | пять видов `InputElement…` | `::` |
| регулярных выражений, 22.2.1 (5.1.2) | кодовые точки | `Pattern` | `::` |
| числовых строк, 7.1.4.1 (5.1.3) | кодовые точки | `StringNumericLiteral` | `:::` |
| синтаксическая, главы 13–16 (5.1.4) | токены лексической | `Script` или `Module` | `:` |

Грамматику регулярных выражений мы читали на дне 17 курса 2. Грамматика числовых строк
работает, когда строка превращается в число, — и она не та же, что у чисел в коде:

```js
console.log(Number(" 12 "), Number("0x1F"), Number(""));   // пробелы по краям разрешены
console.log(Number("\n12\t"), Number("-Infinity"));        // и переводы строк, и слово Infinity
console.log(Number("1_000"), Number("12px"));               // разделителя _ в ней нет
```

<ResultBox>
12 31 0\
12 -Infinity\
NaN NaN
</ResultBox>

В коде можно написать `1_000` — это литерал лексической грамматики (о нём завтра),
а строка `"1_000"` числом не становится. Две грамматики, два разных набора правил.

Синтаксическая грамматика (раздел [5.1.4](https://tc39.es/ecma262/2026/#sec-syntactic-grammar))
строит из токенов **дерево разбора**: корень — `Script` или `Module`,
каждый узел — экземпляр символа грамматики. Если токены не складываются в одно дерево без
остатка, — `SyntaxError`. Узлы дерева — понятие спецификации: движок не обязан
строить именно такую структуру.

Иногда грамматика читает «на вырост». Текст `(a, b)` в начале может оказаться и
выражением в скобках, и параметрами стрелочной функции — это ясно только у `=>`.
Поэтому сначала разбирается общее правило, а потом проверяется, что оно «покрывает» нужное:
раздел 5.1.4 называет это «P must cover an N». Выражением `(a + 1, b)` быть может,
а параметрами — нет:

```js
const parse = (code) => {
  try {
    new Function(code);
    return "разобрано";
  } catch (e) {
    return `${e.name}: ${e.message}`;
  }
};
console.log(parse("(a, b) => a + b"));
console.log(parse("(a + 1, b) => a"));
```

<ResultBox>
разобрано\
SyntaxError: Invalid destructuring assignment target
</ResultBox>

Функцию `parse` будем звать весь день: `new Function` (день 4 курса 2)
разбирает строку как тело функции, и по ошибке видно, принимает ли текст грамматика.

## 3. Как читать правило грамматики {#notation}

Раздел [5.1.5](https://tc39.es/ecma262/2026/#sec-grammar-notation) — словарь записи.
Вот правило цикла `while` в синтаксической грамматике:

```grammar
*WhileStatement* :
    while ( *Expression* ) *Statement*
```

Моноширинным шрифтом — терминалы: их пишут в тексте буквально, и только символами латиницы
(похожая буква другого алфавита не подойдёт). Курсивом — нетерминалы. Одно двоеточие — синтаксическая
грамматика. Если вариантов несколько, каждый пишется на своей строке. Правило может ссылаться
на себя — так список аргументов растёт до любой длины:

```grammar
*ArgumentList* :
    *AssignmentExpression*
    *ArgumentList* , *AssignmentExpression*
```

Остальные обозначения раздела:

| Запись | Что значит | Пример |
| --- | --- | --- |
| *X*<sub>opt</sub> | символ можно пропустить: два варианта в одном | `let x` и `let x = 1` |
| *X*\[Yield, Await\] | параметры: одно правило — несколько версий для разных мест | `await` в async-функции и вне её |
| one of | любой из перечисленных терминалов | знаки пунктуации |
| \[empty\] | пустая правая часть | пустой список параметров |
| \[lookahead ∉ …\] | проверка впереди: следующий токен не из набора | `?.` перед цифрой (раздел 10) |
| \[no *LineTerminator* here\] | перевод строки здесь запрещён | после `return` (завтра) |
| but not | всё, кроме | имя, но не зарезервированное слово |

Пример с `opt` из раздела показывает, как быстро растёт число вариантов: правило цикла
`for` с двумя необязательными выражениями — это на самом деле четыре правила: с обоими
выражениями, с одним из двух и совсем без них.

### Параметры: зачем выражению \[In\]

Выражения записаны как *Expression*\[In\] и в версии без `In`: там оператор
`in` запрещён. Нужно это в заголовке `for`: встретив `in`, грамматика
должна решить, оператор это или начало `for...in`. В начале заголовка она берёт версию без
`In`, и вставить туда оператор можно только в скобках:

```js
const parse = (code) => {
  try {
    new Function(code);
    return "разобрано";
  } catch (e) {
    return `${e.name}: ${e.message}`;
  }
};
console.log(parse('for (var i = "a" in {}; false;) {}'));     // in — начало for...in
console.log(parse('for (var i = ("a" in {}); false;) {}'));   // в скобках — оператор
```

<ResultBox>
SyntaxError: Unexpected token ';'\
разобрано
</ResultBox>

Первый заголовок прочитан как `for...in` с начальным значением (его в нестрогом коде
разрешает приложение B, день 31), и точка с запятой там уже лишняя.

### Проверка впереди: чем не может начинаться инструкция

Инструкция-выражение (раздел 14.5) записана с проверкой
`[lookahead ∉ { {, function, async [no LineTerminator here] function, class, let [ }]`: она не начинается
с фигурной скобки, `function`, `class`. Иначе её нельзя было бы отличить от
блока и объявлений. Отсюда два знакомых правила:

```js
const parse = (code) => {
  try {
    new Function(code);
    return "разобрано";
  } catch (e) {
    return `${e.name}: ${e.message}`;
  }
};
console.log(parse("function () {}();"));       // в начале инструкции — объявление
console.log((function () { return 5; })());     // в скобках — выражение
console.log(parse("{ mark: 5 }"));              // { в начале — блок с меткой mark
```

<ResultBox>
SyntaxError: Function statements require a function name\
5\
разобрано
</ResultBox>

Поэтому функцию, вызываемую сразу (день 28 курса 2), берут в скобки: в начале инструкции
`function` — всегда объявление, и ему нужно имя. А `{ mark: 5 }` в начале
строки — не объект, а блок, внутри которого метка `mark` и число 5.

## 4. Исходный текст — кодовые точки {#source}

Раздел [11.1](https://tc39.es/ecma262/2026/#sec-source-text) начинается с правила
`SourceCharacter :: any Unicode code point`. Исходный текст — последовательность кодовых
точек Unicode; в каком кодировании лежит файл, стандарту неважно. Знакомое по дню 20 курса 2:
«буква с ударением», набранная двумя кодовыми точками, для языка — две точки, а не одна.

Отсюда неожиданное следствие для имён. Раздел 12.7.1 прямо говорит: два имени, которые Unicode
считает равными, но которые записаны разными кодовыми точками, — *разные* имена. Спросим
у Chrome через `new Function` (день 4 курса 2): он разбирает строку как тело функции.

```js
const composed = "caf" + String.fromCharCode(0xE9);           // é одной точкой
const decomposed = "cafe" + String.fromCharCode(0x301);       // e и знак ударения
console.log(composed === decomposed, composed.normalize() === decomposed.normalize());
const body = `const ${composed} = 1; const ${decomposed} = 2; return [${composed}, ${decomposed}];`;
console.log(new Function(body)());
```

<ResultBox>
false true\
(2) \[1, 2\]
</ResultBox>

На экране оба имени — «café», а переменных две. Нормализация из дня 20 курса 2 делает строки
равными, но к именам в коде её никто не применяет.

Второе следствие — escape-последовательности. В строках, регулярках, шаблонах и именах кодовую
точку можно записать числом: `\u0061` — это «a». Но **внутри комментария**
такая запись — просто текст. Раздел 11.1 сравнивает с Java, где `\u000A` в
комментарии превращается в перевод строки и обрывает комментарий. В ECMAScript — нет:

```js
let mark = 4;
// \u000A mark = 5;
console.log(mark);
```

<ResultBox>
4
</ResultBox>

Подразделы 11.1.1–11.1.6 — служебные операции над текстом: собрать кодовую точку из двух
16-битных половинок, разложить строку на точки (`CodePointAt` мы пересказывали
на дне 20 курса 2) и `ParseText` — разобрать текст с заданной целью. `ParseText`
возвращает либо дерево, либо список ошибок: и синтаксических, и ранних. Наша `parse`
делает то же руками: `new Function` зовёт разбор с целью «тело функции» и превращает
первую ошибку списка в исключение.

## 5. Четыре вида кода и директива {#kinds}

Раздел [11.2](https://tc39.es/ecma262/2026/#sec-types-of-source-code) различает
четыре вида кода: **глобальный** (обычный скрипт), **eval** (строка,
переданная в `eval`, — день 13), **код функции** (тело и параметры) и
**код модуля**. Код вложенной функции не входит в код внешней: у каждой функции
свой.

Раздел 11.2.1 уточняет директиву `"use strict"`, знакомую по дню 3 курса 2. Она
действует, только если стоит в начале кода, в «прологе директив», и записана
**точно**: эти буквы, в двойных или одинарных кавычках, без escape-последовательностей.

```js
function loose() { "Use strict"; return typeof this; }   // большая U — просто строка
function strict() { 'use strict'; return typeof this; }  // одинарные кавычки — директива
console.log(loose(), strict());
```

<ResultBox>
object undefined
</ResultBox>

В `loose` строка с большой буквой — обычное выражение, режим остался нестрогим, и
`this` без объекта — окно браузера. Раздел 11.2.2 перечисляет, что строго всегда: код
модуля и тело класса. Раздел 11.2.3 разрешает функции, написанные не на ECMAScript: встроенные
функции движок может написать на чём угодно, и снаружи это почти незаметно — разве что исходника
у них нет:

```js
console.log(Math.max.toString());
```

<ResultBox>
function max() \{ \[native code\] \}
</ResultBox>

## 6. Лексер: самый длинный токен и пять целей {#longest}

Глава [12](https://tc39.es/ecma262/2026/#sec-ecmascript-language-lexical-grammar)
начинается с правила, которое объясняет многие загадки: текст читается **слева направо**,
и каждый раз берётся **самый длинный** кусок, который может быть элементом ввода.

```js
let a = 1, b = 2;
console.log(a+++b, a, b);
```

<ResultBox>
3 2 2
</ResultBox>

Лексер видит `+++` и берёт самое длинное — `++`, потом `+`.
Получается `a++ + b`: сложение 1 и 2, а `a` после этого стала 2. Пробелы
решают дело иначе: `a + ++b` — уже другая программа. А `a+++++b` разбивается
на `a ++ ++ + b`, и синтаксическая грамматика такое не принимает.

Второе правило главы — **пять целей**. Символ `/` может начинать и
деление, и регулярное выражение, и лексер решает по месту: там, где грамматика ждёт оператора, —
деление; где ждёт значения — регулярка. Примечание к главе приводит пример: после переноса строки
`/hi/g` читается как деление, потому что выражение `b` ещё может продолжаться.

```js
const b = 10, hi = 2, g = { exec: () => [1] }, c = 0;
let a;
a = b
/hi/g.exec(c).map(Number);
console.log(a);
```

<ResultBox>
5
</ResultBox>

Это `a = b / hi / g.exec(c).map(Number)`: 10 / 2 / 1. Точки с запятой после
`b` язык не вставил — почему, разберём завтра.

Так же лексер решает судьбу `}`. В шаблоне `` `итог ${total / n} из ${n}` ``
фигурная скобка после `n` закрывает подстановку, и дальше идёт не код, а продолжение
шаблона — « из ». Поэтому закрывающая скобка вынесена из общих токенов в отдельные правила,
и цель `InputElementTemplateTail` говорит лексеру: сейчас `}` — хвост шаблона.
Целей пять, потому что эти решения нужно принимать в разных местах грамматики.

## 7. Пробелы {#space}

Раздел [12.2](https://tc39.es/ecma262/2026/#sec-white-space): пробелы разделяют токены
и в остальном ничего не значат. Таблица 30 перечисляет, что язык считает пробелом: табуляцию
(U+0009), вертикальную табуляцию (U+000B), перевод страницы (U+000C), U+FEFF и любой символ
категории Unicode «Space_Separator» — туда входят обычный пробел и неразрывный U+00A0. Других
«пробельных» символов Unicode язык нарочно не берёт. Проверим тремя символами:

```js
const NBSP = String.fromCharCode(0xA0), BOM = String.fromCharCode(0xFEFF), NEL = String.fromCharCode(0x85);
console.log(new Function("let" + NBSP + "x = 1; return x;")());   // неразрывный пробел
console.log(new Function("let" + BOM + "y = 2; return y;")());    // U+FEFF — тоже пробел
try {
  new Function("let" + NEL + "z = 3; return z;");                 // U+0085 — нет
} catch (e) {
  console.log(`${e.name}: ${e.message}`);
}
```

<ResultBox>
1\
2\
SyntaxError: Invalid or unexpected token
</ResultBox>

U+0085 («следующая строка») у Unicode — пробельный символ, но в таблицу 30 он не попал, и
в коде это ошибка. Неразрывный пробел, наоборот, в коде работает. Он легко попадает в программу,
когда код копируют из текстового редактора или со страницы, — и ошибкой не станет. Раздел
[12.1](https://tc39.es/ecma262/2026/#sec-unicode-format-control-characters) добавляет:
U+FEFF в начале файла — метка порядка байтов, а дальше в тексте — обычный пробел.

Тот же раздел говорит об управляющих символах формата — невидимых знаках вроде ZWNJ (U+200C) и
ZWJ (U+200D). MDN объясняет, зачем они: в некоторых письменностях, например в персидской, они
запрещают или требуют соединить соседние буквы. Поэтому стандарт пускает их в комментарии, строки,
шаблоны и регулярки, а ZWNJ и ZWJ — даже внутрь имён (раздел 11).

<Mistake>
Пробел для языка и пробел для `trim` — не одно и то же. `trim` снимает
и переводы строк, а MDN напоминает: редакция ES2016 перешла на Unicode 8.0, где символ U+180E
из пробелов стал управляющим, и `"\u180E".trim().length` с тех пор равен 1.
Определения зависят от версии Unicode, на которую ссылается стандарт.
</Mistake>

## 8. Переводы строк {#lines}

Раздел [12.3](https://tc39.es/ecma262/2026/#sec-line-terminators): переводов строки
четыре — LF (U+000A), CR (U+000D), разделитель строк LS (U+2028) и разделитель абзацев PS (U+2029).
Пара CR LF считается одним. В отличие от пробелов, перевод строки влияет на грамматику: есть места,
где он запрещён (`[no LineTerminator here]`), и он управляет автоматической вставкой
точки с запятой — завтра.

LS и PS на экране не видны, но для языка это полноценный перевод строки. Например, на нём
кончается однострочный комментарий:

```js
const LS = String.fromCharCode(0x2028);
const body = "let mark = 4;\n// комментарий" + LS + "mark = 5;\nreturn mark;";
console.log(new Function(body)());
```

<ResultBox>
5
</ResultBox>

В редакторе строка «комментарий mark = 5;» выглядит одной строкой комментария, а язык выполнил
присваивание. Ещё одно правило 12.3 касается номеров строк: пару CR LF, которой заканчиваются
строки в файлах Windows, нужно считать *одним* переводом строки. Иначе номера строк в стеке
ошибки (день 26 курса 2) у файла из Windows удвоились бы. Класс `\s` регулярных выражений, по словам раздела, включает и
переводы строк — поэтому на дне 17 курса 2 он совпал с набором, который снимает `trim`.

## 9. Комментарии и hashbang {#comments}

Раздел [12.4](https://tc39.es/ecma262/2026/#sec-comments): однострочный комментарий
`//` — до конца строки, а сам перевод строки в него не входит и остаётся в потоке.
Многострочный `/* … */` можно поставить и посреди строки, и вокруг кода, который
нужно временно отключить, — пример MDN:

```js
const x = "dünýä";
console.log("Salam, " + x /* вставили x */ + "!");
/* console.log("этой строки не будет"); */
```

<ResultBox>
Salam, dünýä!
</ResultBox>

Но многострочные комментарии **не вкладываются**: отключить так кусок, в котором
уже есть `/* … */`, не выйдет. Почему ошибка выглядит так странно, объясняет правило
пяти целей:

```js
const parse = (code) => {
  try {
    new Function(code);
    return "разобрано";
  } catch (e) {
    return `${e.name}: ${e.message}`;
  }
};
console.log(parse("/* a /* b */ c */"));
console.log(parse("/* a */ /* b */"));
```

<ResultBox>
SyntaxError: Invalid regular expression: missing /\
разобрано
</ResultBox>

Комментарий закончился на первом `*/`. Остаток `c */` — имя `c`,
знак умножения и `/`. После умножения грамматика ждёт значение, значит, `/`
начинает регулярное выражение — без закрывающей черты. Отсюда и текст про регулярку.

Ещё одно правило 12.4: многострочный комментарий, внутри которого есть перевод строки, для
грамматики *сам* считается переводом строки:

```js
function total() {
  return /*
  */ 5;
}
console.log(total());
```

<ResultBox>
undefined
</ResultBox>

Для грамматики это `return` и перевод строки, а после `return` перевод
строки запрещён — вставляется точка с запятой. Механизм — завтра.

Раздел [12.5](https://tc39.es/ecma262/2026/#sec-hashbang) — комментарий
`#!`. Он допустим только в самом начале скрипта или модуля, без единого символа перед
ним, и нужен для запуска файла из командной строки. В браузере он тоже работает:

```js
#!/usr/bin/env node
console.log("hashbang разобран");
```

<ResultBox>
hashbang разобран
</ResultBox>

Поставьте перед `#!` пробел или перенесите его на вторую строку —
`SyntaxError: Invalid or unexpected token`. Начало скрипта — единственное место, где
работает цель `InputElementHashbangOrRegExp`. MDN предупреждает: файл с `#!`
сохраняйте в UTF-8 без метки U+FEFF. Браузер метку снимает ещё при чтении файла, а командная строка
Unix с ней не узнает `#!`.

## 10. Токены и знаки пунктуации {#tokens}

Раздел [12.6](https://tc39.es/ecma262/2026/#sec-tokens): обычные токены — имена,
приватные имена с `#`, знаки пунктуации, числа, строки и шаблоны. Деление,
регулярки, закрывающая фигурная скобка и хвосты шаблонов вынесены отдельно — именно их лексер
различает по цели. Раздел [12.8](https://tc39.es/ecma262/2026/#sec-punctuators)
перечисляет знаки пунктуации через «one of»: от `{` до `=>`, всего их
больше пятидесяти.

Один знак записан с проверкой впереди — необязательная цепочка:
`OptionalChainingPunctuator :: ?. [lookahead ∉ DecimalDigit]`. Знак `?.`,
за которым идёт цифра, — не цепочка. Без этого правила сломалась бы старая запись:

```js
const ready = true;
console.log(ready?.5:0);                 // ? и .5 — тернарный оператор
const card = { step: 2 };
console.log(card?.step);                 // ?. — необязательная цепочка
```

<ResultBox>
0.5\
2
</ResultBox>

В первой строке `?.` не выделился в токен: следом цифра, поэтому лексер взял
`?`, а `.5` прочитал как число.

## 11. Имена {#names}

Раздел [12.7](https://tc39.es/ecma262/2026/#sec-names-and-keywords): имя начинается
с символа, у которого в Unicode есть свойство ID_Start, или с `$` и `_`,
а дальше идут символы ID_Continue и `$`. В ID_Continue входят и два невидимых
соединителя — ZWNJ и ZWJ. Буквы любых алфавитов годятся, цифра в начале — нет:

```js
const ýyl = 2026, çörek = "bread", $_$ = 3;
console.log(ýyl, çörek, $_$);
const apple = 5;
console.log(\u0061pple);                // \u0061 — это «a»: то же имя
```

<ResultBox>
2026 bread 3\
5
</ResultBox>

MDN советует, если когда-нибудь придётся разбирать код самим, не считать имена латиницей: точнее
их описывает регулярное выражение на классах Unicode из дня 20 курса 2.

```js
const isName = (s) => /^[$_\p{ID_Start}][$\p{ID_Continue}]*$/u.test(s);
console.log(["ýyl", "2mark", "çörek", "my-name", "_x", "$"].map(isName).join(" "));
```

<ResultBox>
true false true false true true
</ResultBox>

Туркменские ý и ç — буквы с ID_Start, имя законное; дефис в имя не входит. Запись `\u0061pple` раздел
12.7.1 разрешает: escape-последовательность даёт ту же кодовую точку, и имя то же. Но так нельзя
протащить в имя то, что в нём запрещено. Невидимый ZWJ внутри имени тоже часть имени: `ab`
и то же имя с ZWJ между буквами — разные переменные, на экране неотличимые.

## 12. Ключевые и зарезервированные слова {#reserved}

Раздел [12.7.2](https://tc39.es/ecma262/2026/#sec-keywords-and-reserved-words)
разводит два понятия. **Ключевое слово** — имя, которое встречается в грамматике
буквально: `if`, `async`, `of`. **Зарезервированное** —
имя, которое нельзя сделать идентификатором. Раздел делит все имена на пять групп:

| Группа | Примеры | Как имя переменной |
| --- | --- | --- |
| обычные имена | `Math`, `window`, `_` | всегда можно |
| зарезервированные всегда | `if`, `class`, `enum`, `import` | никогда |
| зависят от места | `await`, `yield` | `await` — вне async-функций и модулей, `yield` — вне генераторов и строгого кода |
| запрещены в строгом коде | `let`, `static`, `private`… | только в нестрогом |
| ключевые, но не зарезервированные | `as`, `async`, `from`, `get`, `of`, `set` | всегда можно |

```js
const async = 5, of = 6, get = 7;
let await = 8;                                  // обычный скрипт — можно
console.log(async + of + get + await);
const lesson = { import: 1, if: 2 };            // в именах свойств — можно
console.log(lesson.import + lesson.if);
```

<ResultBox>
26\
3
</ResultBox>

```js
const parse = (code) => {
  try {
    new Function(code);
    return "разобрано";
  } catch (e) {
    return `${e.name}: ${e.message}`;
  }
};
console.log(parse("const enum = 1;"));
console.log(parse("function import() {}"));
console.log(parse("let let = 1;"));
console.log(parse("var let = 1;"));
console.log(parse("const els\\u{65} = 1;"));
```

<ResultBox>
SyntaxError: Unexpected reserved word\
SyntaxError: Unexpected token 'import'\
SyntaxError: let is disallowed as a lexically bound name\
разобрано\
SyntaxError: Keyword must not contain escaped characters
</ResultBox>

Список меняется со временем. MDN перечисляет слова, которые редакции 1–3 держали «про запас»,
а теперь это обычные имена:

```js
const int = 1, goto = 2, abstract = 3, boolean = 4;
console.log(int + goto + abstract + boolean);
```

<ResultBox>
10
</ResultBox>

`enum` зарезервировано «на будущее» до сих пор и ничего не делает, но имени не даст.
`let` нельзя объявить через `let`, а через `var` в нестрогом
коде можно — пережиток времён, когда `let` ещё не было. Последняя строка — обход
через escape: `els\u{65}` — это `else`, и раздел 12.7.2 прямо запрещает
так объявлять зарезервированные слова; V8 говорит, что в ключевом слове не может быть
escape-последовательностей. Обратный слэш в строке для `parse` удвоен: одиночный
раскрыла бы сама строка, разбор получил бы готовое `else` и ответил бы
`Unexpected token 'else'`.

Примечание 3 к разделу добавляет ещё два имени с ограничениями: `eval` и
`arguments` — не ключевые слова, но в строгом коде объявить их нельзя (таблица дня 3
курса 2):

```js
const parse = (code) => {
  try {
    new Function(code);
    return "разобрано";
  } catch (e) {
    return `${e.name}: ${e.message}`;
  }
};
console.log(parse('"use strict"; let eval = 1;'));
console.log(parse("let eval = 1;"));
```

<ResultBox>
SyntaxError: Unexpected eval or arguments in strict mode\
разобрано
</ResultBox>

## 13. «Карточки 2.0»: строка по токенам {#cards}

Разберём руками строку из метода `know` «Карточек 2.0» (день 35 курса 2):

```js
// deck.js, день 35 курса 2 — одна строка метода know
const step = this.progress.get(id)?.step ?? 1;
```

<Scheme src="scheme-cards.svg">Строка «Карточек 2.0» глазами лексера: четыре вида токенов</Scheme>

Лексер прошёл строку слева направо и каждый раз брал самый длинный кусок. На `?.step`
он сначала проверил, не цифра ли после `?.`, — и взял знак необязательной цепочки целиком.
На `??` — два вопросительных знака одним токеном, а не два тернарных. Пробелы ушли из
потока, и синтаксическая грамматика получила 16 токенов. Если бы `id` назывался
`id` с невидимым ZWJ внутри, токенов было бы столько же — но имя другое, и
`progress.get` искал бы другую переменную.

<Selfcheck>
1. Чем отличаются правила с `::`, `:::` и `:`?
   <Answer>Это разные грамматики: `::` — лексическая и регулярных выражений (буквы —
   кодовые точки), `:::` — числовых строк, `:` — синтаксическая
   (буквы — токены лексической).</Answer>
2. Почему `a+++b` — это `a++ + b`, а не `a + ++b`?
   <Answer>Лексер читает слева направо и каждый раз берёт самый длинный возможный кусок:
   сначала `++`, потом `+`.</Answer>
3. Почему `/* a /* b */ c */` даёт ошибку про регулярное выражение?
   <Answer>Комментарии не вкладываются: он кончился на первом `*/`. Дальше
   `c * /`, а после умножения грамматика ждёт значение — `/`
   начинает регулярку, которая не закрыта.</Answer>
4. Неразрывный пробел U+00A0 и символ U+0085 оба пробельные для Unicode. Что будет с каждым
   в коде?
   <Answer>U+00A0 входит в категорию Space_Separator и для языка — пробел. U+0085 в таблицу 30 не
   входит: в коде это `SyntaxError: Invalid or unexpected token`.</Answer>
5. Можно ли назвать переменную `async`? А `enum`? А `let`?
   <Answer>`async` — всегда: ключевое, но не зарезервированное. `enum` —
   никогда: зарезервировано на будущее. `let` — только через `var`
   и только в нестрогом коде.</Answer>
