## 1. Why a value needs a name {#why}

Yesterday we saw a map of the whole language. Today we take the first brick and study it to the end.

A program works with values: numbers, strings, lists. But a value without a name lives for one
moment — it is calculated and gone. To come back to it ten lines later, it is given a name. That is what a
variable is: **a name that a value is attached to**.

```js
console.log(12 * 40 * 7.5);   // calculated and forgotten

const price = 12;             // but here every number can be named
const count = 40;
const days = 7.5;
console.log(price * count * days);
```

The second version is longer, but a month later you will understand what it calculates, while the first one will have to be
puzzled out. Names are not a convenience for the computer — the engine does not care. Names are for the person who will read
your code, and most often that person is you, half a year later.

<Analogy>
A variable is a labeled box. The name is written on the lid and does not change, but the contents can be
replaced: you put one thing in, take it out, put another in. In school algebra `x` means
an unknown to be found. In programming `x` is a label on a box,
and you yourself put in whatever you want.
</Analogy>

Every variable has three properties, and the whole of today’s lesson is about them:

| Property | Question | Where we cover it |
| --- | --- | --- |
| **name** | what it is called and by which rules | section 3 |
| **mutability** | can another value be put into it | sections 4–5 |
| **lifetime** | from which line to which line it exists | sections 6–9 |

The first property is obvious, the second is clear after one example. But the third — lifetime — is
the place where beginners lose the most time: the variable “exists” but for some reason is not visible, or
is visible but empty. By the end of the lesson both situations will become predictable.

The examples of one section continue each other, and before each new section reload
the page (<Kbd>F5</Kbd>): the names from earlier sections will disappear and will not get in the way of new ones.

## 2. Declaration and initialization {#declare}

The line `let score = 42;` contains two different things, and each has its own name:

- **the declaration** — `let score`. It creates the name, and from this moment
  using it does not cause an error;
- **the initializer** — `= 42`. It puts the first value into the box.

The initializer can be left out. Then the variable will hold `undefined` — “nothing was put in”:

```js
let score;
console.log(score);   // undefined

score = 42;           // put in later
console.log(score);   // 42
```

So `let score = 42;` is exactly the same as `let score; score = 42;`,
just on one line.

<Mistake>
For `const` the initializer is **required**. The logic is simple: the value of a constant
cannot be replaced later, so an empty constant would be empty forever — almost certainly that is
a slip of the programmer, and the language does not let it through.

```js
const total;   // SyntaxError: Missing initializer in const declaration
```
</Mistake>

### Several variables on one line

After `let` or `const` you can list several names separated by commas.
And the next initializer already sees the previous name:

```js
let width = 3, height = 4;
let base = 10, doubled = base * 2;   // doubled = 20
```

The comma here is just a list separator, not an operator. People rarely write this way: a separate line for
each variable reads better and is easier to edit. But you need to know this form, because it appears all the time
in old code.

And here is a similar line that does something quite different from what people expect:

```js
let a = b = 5;

console.log(a);              // 5 — as expected
console.log(globalThis.b);   // 5 — and this is a surprise
```

The engine reads this as `let a = (b = 5)`. First the assignment
`b = 5` runs — and `b` is not declared anywhere, so it silently becomes a global
variable. Then its value goes into `a`. One variable is declared properly,
the other is an accidental global. More about this mechanism in section 10.

## 3. Variable names {#names}

In the language of the documentation a variable name is called an *identifier*. The rules are:

| Rule | Allowed | Not allowed |
| --- | --- | --- |
| the first character is a letter, `_` or `$` | `name`, `_tmp`, `$el` | `2fast` |
| after that digits are allowed too | `temp99`, `user2` | `user-2` |
| no spaces or hyphens | `firstName` | `first name` |
| not a reserved word | `result` | `class`, `return` |

The letters can be any letters from Unicode, so technically this works:

```js
const Früh = "early";    // a German letter in a name — allowed
const ýyl = 2026;        // Turkmen letters are allowed too
```

But people do not do this. All the code around you — libraries, examples, documentation — is in English, and a mix
of two alphabets in one file reads badly. Let us agree for the whole course: **we write names with the English letters a–z**.

<Important>
**Case matters.** `score`, `Score` and `SCORE` are
three different variables. This is the reason for half of the “is not defined” messages in the first week:
`userName` was declared, and `username` was used.
</Important>

If you forget the name completely, the engine complains at once. In Chrome the message is:

```js
var = 5;   // SyntaxError: Unexpected token '='
```

In Firefox the same error has a clearer name — `SyntaxError: missing variable name`.
That is normal: **the same error has different text in different browsers**. The meaning is the same, but the words
are chosen by whoever wrote the engine. On MDN such pages are titled with the Firefox wording, so
do not be surprised that they differ from what you see in Chrome.

### Comments and one trap

Since we are talking about how the language reads our text: there are two kinds of comments, and the engine
simply throws both away, like spaces.

```js
// a one-line comment — up to the end of the line

/* a multi-line
   comment */
```

The trap is that **multi-line comments do not nest**. The very first
`*/` closes the comment, and the engine reads everything after it as code again:

```js
/* outer /* inner */ tail */
console.log("we will not get here");
```

The comment ended at the first `*/`; then the engine saw the word `tail`,
then `*`, then `/` — and decided that a regular expression had started. The message
turns out completely puzzling:

```js
// SyntaxError: Invalid regular expression: missing /
```

Remember this combination: **a puzzling error about a regular expression — look for an extra
`*/`**. It usually happens when you comment out a piece of code that already had
a comment in it.

## 4. Three words: the big picture {#three}

A variable can be declared with three words. Here is the whole difference between them — we will come back
to this table throughout the lesson:

|  | `const` | `let` | `var` |
| --- | --- | --- | --- |
| the value can be replaced | no | yes | yes |
| an initializer is required | yes | no | no |
| visible only inside the block | yes | yes | **no** |
| can be declared again | no | no | **yes, silently** |
| access before declaration | error | error | **`undefined`** |
| when we write it | by default | if the value changes | never |

The three rows in bold are exactly the reasons why `var` left new code.
Let us go through them one by one.

## 5. const: what it forbids and what it does not {#const}

`const` forbids **reassignment** — an attempt to tie the name to another
value:

```js
const city = "Mary";
city = "Ashgabat";   // TypeError: Assignment to constant variable.
```

And here is what it does not forbid — this surprises every second person:

```js
const basket = ["bread", "tea"];
basket.push("rice");       // it works! no error
console.log(basket);       // ["bread", "tea", "rice"]

const user = { name: "Aman" };
user.name = "Meret";       // this works too
user.age = 17;             // and a property can be added
```

<Scheme src="scheme-const.svg">A constant locks the link “name — value”. The object itself stays changeable</Scheme>

Why is that? Remember day 3: objects and arrays are passed **by reference**. The variable
holds not the list itself but the address of the list. `const` forbids changing the address — but does not forbid
coming to that address and rearranging the things inside.

<ProTip>
If you need to forbid changing the contents too, there is `Object.freeze(object)`. However, in normal
mode an attempt to change a frozen object *silently does nothing*, and you will see the error
`TypeError: Cannot assign to read only property 'x' of object '#<Object>'` only in strict mode.
Strict mode is a topic of course 2, but `freeze` will be useful already in the projects.
</ProTip>

## 6. A block is curly braces {#block}

A block is a pair of curly braces with statements inside. It is needed where the language expects one statement
and we need several:

```js
if (score > 4) {
  console.log("well done");   // a block of two statements
  count = count + 1;
}
```

Blocks stand after `if`, after loops, in functions. But a block can also stand on its own, without any condition —
just braces:

```js
{
  const tmp = "a temporary value";
  console.log(tmp);
}
// here tmp no longer exists
```

This is sometimes done on purpose, so that a temporary variable does not get in the way further down the file. And exactly this
property of a block is the main point today.

<Mistake>
Where the language expects one statement, you cannot put a declaration — only through a block:

```js
if (true) let a = 1;
// SyntaxError: Lexical declaration cannot appear in a single-statement context

if (true) { let a = 1; }   // this is correct
```

The ban is reasonable: a variable declared without braces would not be visible to anyone anyway.
</Mistake>

One more subtlety about braces. If a line *starts* with `{`, the engine considers it
a block, not an object:

```js
{ "x": 1 }        // SyntaxError: Unexpected token ':'

const obj = { "x": 1 };   // and this is an object — the braces are not at the start of the line
```

In practice this rarely gets in the way, because objects are almost always put into a variable or passed
to a function. But it is worth knowing: the same braces mean different things depending on where they stand.

## 7. Where a variable is visible {#scope}

The area in which a variable exists is called its **scope**.
There are three, and they are nested inside each other:

<Scheme src="scheme-scope.svg">Three scopes. `let` and `const` stop at the braces, `var` does not</Scheme>

Let us check this with code. First `let`:

```js
if (true) {
  let y = 5;
}
console.log(y);   // ReferenceError: y is not defined
```

And now exactly the same with `var`:

```js
if (true) {
  var x = 5;
}
console.log(x);   // 5 — the variable outlived the block
```

For `var` the curly braces of `if`, a loop or `try` are not a border
at all. Only a function is a border for it. It gets ridiculous:

```js
for (var a of [1, 2, 3]);
console.log(a);   // 3 — the loop counter stayed alive after the loop
```

The other side of block scope is **shadowing**: inside a block you can create a variable
with the same name, and it will not touch the outer one.

```js
let s = 1;
{
  let s = 2;        // this is a different variable
  console.log(s);   // 2
}
console.log(s);     // 1 — the outer one is intact
```

It works the other way too: from inside a block or a function you can see perfectly well everything declared
outside. Visibility goes only inward:

```js
const tax = 0.05;

function withTax(price) {
  return price + price * tax;   // tax is declared outside, and it is visible
}

console.log(withTax(100));      // 105
```

We will study this property seriously in course 2 — it is called a closure and lies at the heart of many
techniques of the language. Today it is enough to remember the direction: **inward is visible, outward is not**.

### const in a loop

A separate question that everyone has in the second week. In a `for...of` loop the counter
is declared with `const` — and it works:

```js
for (const n of [1, 2, 3]) {
  console.log(n);   // 1, 2, 3
}
```

But in an ordinary `for` the same `const` breaks:

```js
for (const i = 0; i < 3; i++) { }
// TypeError: Assignment to constant variable.
```

The reason is in how these two loops work. In an ordinary `for` there is **one variable
for the whole loop**, and `i++` changes its value every time — a constant cannot be changed that way.
In `for...of`, a **new** variable is created on every pass, and the next element is put
into it; nobody changes it, so `const` fits.

Hence a habit worth following from day one: `for...of` — write
`const`, an ordinary `for` — write `let`. We will study the loops themselves on days
10 and 11.

## 8. Why var is no longer written {#var}

The word `var` was the only way to declare a variable in JavaScript before 2015. It
was not removed and will not be: there are millions of pages with old code on the internet, and they must work. But
it is not written in new code, and here are three reasons.

**The first — it does not respect the block.** We have just seen it: the variable gets out of `if`
and out of a loop and lives on. Because of this, two distant lines suddenly turn out to be connected.

**The second — it can be declared again silently.** Declare a variable twice — the language will not object,
and the old value is lost:

```js
var total = 100;
var total = 5;      // no error, no warning
console.log(total); // 5
```

With `let` this will not work — a file with such lines will not run at all:

```js
let sum = 100;
let sum = 5;        // SyntaxError: Identifier 'sum' has already been declared
```

In a file of two hundred lines this happens easily, and `let` works as a safety net here.

**The third — it litters the global object.** A `var` variable declared in a file
becomes a property of the global object (in the browser it is `window`), while `let`
and `const` do not:

```js
var a = 1;
let b = 2;
console.log(globalThis.a);   // 1        — var got into the global object
console.log(globalThis.b);   // undefined — let did not
```

Why this is bad: you connect someone else’s library, and it has its own `var config` inside — and your
variable with the same name is quietly overwritten.

<RealWorld>
You will still see `var` — in old projects, in answers on forums, in examples
ten years old. You need to **be able to read it**, which is why we study it.
You do not need to write it.
</RealWorld>

### How to rewrite old code

Found an example with `var` and want to bring it up to today’s rules? The order is:

1. replace every `var` with `const`;
2. run it: where the engine says `TypeError: Assignment to constant variable.`,
   change it to `let`;
3. if a `ReferenceError` appears, the code relied on the variable getting out
   of the block. Such a place has to be sorted out by hand: usually the declaration needs to be moved
   above the block.

```js
// before
for (var i = 0; i < items.length; i++) {
  var item = items[i];
  console.log(item);
}

// after
for (let i = 0; i < items.length; i++) {
  const item = items[i];      // a new variable on every pass
  console.log(item);
}
```

The first two steps are mechanical, and the engine itself shows where exactly `let` is needed.
The third step needs thinking — but that is usually exactly where the real bug of the old code hides.

## 9. Access before declaration {#tdz}

What happens if you use a variable before the line where it is declared? The answer depends on the word
it was declared with, and this is the fourth difference of `var`. Run the examples of this section
from `app.js`, one at a time: the Chrome console runs code differently and instead of
the answers below will often just show `is not defined`.

```js
console.log(bar);   // undefined — var behaves quietly
var bar = 1;

console.log(foo);   // ReferenceError: Cannot access 'foo' before initialization
let foo = 2;
```

The engine processes `var` declarations in advance, before running the code, — as if it lifted
them to the top of the function. This is called *hoisting*. But only the declaration is lifted; the assignment
stays in place. That is why the variable already exists but is still empty:

<Compare>
<Wrong label="What is written">
```js
console.log(x);
var x = 3;
```
</Wrong>

<Right label="How the engine understood it">
```js
var x;
console.log(x);   // undefined
x = 3;
```
</Right>
</Compare>

With `let` and `const` this will not work. From the start of the block to the line of the declaration
the variable is in the **temporal dead zone**: the name is already taken, but you must not touch it.

<Scheme src="scheme-tdz.svg">The red zone lasts from the opening brace to the line with the declaration</Scheme>

Notice the third line of the diagram. The `typeof` operator, which is usually safe
and answers `"undefined"` for names that do not exist, also fails in the dead zone:

```js
console.log(typeof nothingAtAll);   // "undefined" — the name does not exist at all, and that is not an error

{
  console.log(typeof i);            // ReferenceError: Cannot access 'i' before initialization
  let i = 10;
}
```

It sounds picky, but in fact it is a gift: the language catches a typo at the moment you make it,
not a hundred lines later, when `undefined` has already got into the calculation.

### And functions?

Functions have a third story, and it is worth learning now, because you have surely already seen such
code and been surprised. A function declared with the word `function` is hoisted **whole** —
together with its body. That is why it can be called above the place where it is written:

```js
console.log(greet("Aman"));   // "Salam, Aman!" — it works

function greet(name) {
  return `Salam, ${name}!`;
}
```

But a function put into a variable follows the rules of the variable — and so it cannot do this:

```js
hi();                         // ReferenceError: Cannot access 'hi' before initialization
const hi = () => "salam";
```

```js
hi2();                        // TypeError: hi2 is not a function
var hi2 = function () { };    // var hoisted the name, but the value is not assigned yet
```

Notice the different errors in the last two examples. With `const` the engine says
“you must not touch it”, with `var` — “this is not a function”: the name already exists, it holds
`undefined`, and `undefined` cannot be called. We study functions themselves on days 12–15;
here one thing matters: **only the form with `function` is hoisted**.

<Why>
Why invent a dead zone at all, if it could have worked like `var`? Look
at `const`. Its promise is “the value does not change”. But if access before declaration
returned `undefined`, this would happen:

```js
console.log(PI);   // undefined ?
const PI = 3.14;
console.log(PI);   // 3.14 ?
```

The same constant would give two different values — exactly what `const` must
rule out. The dead zone closes this hole: before the line of the declaration the constant simply does not exist, and there is
nothing to argue about. And since the rule is needed for `const`, it was made the same for `let`.
</Why>

## 10. An undeclared variable {#undeclared}

A separate case is assigning a value to a name that was never declared:

```js
totl = 42;   // neither let, nor const, nor var
```

There will be no error. The language creates a global variable by itself — this behavior is left over from the nineties.
And here is why it is dangerous. Imagine a typo:

```js
let total = 0;
totl = total + 5;        // a typo in the name
console.log(total);      // 0 — but we expected 5
```

Nobody complained, the program works, the number is wrong. Such a bug takes a long time to find, because
there is nothing to look for: the console is empty.

<Important>
Hence a rule without exceptions: **every variable is declared** with
`const` or `let`. Not for beauty — so that a typo immediately becomes
a visible `ReferenceError` and not a quietly wrong result.
</Important>

In strict mode the language already forbids this and throws
`ReferenceError: totl is not defined`. Strict mode is turned on with the line
`"use strict";` and works by itself inside modules; in detail — in course 2.

How do people catch such a bug in practice if strict mode is not on? There are three techniques, and all three
will be useful to you:

- **put `"use strict";` as the first line of the file** — the simplest
  way to turn quiet behavior into an honest error right today;
- **check `globalThis`** — if you suspect an accidental global,
  type `globalThis.totl` in the console. An answer other than `undefined` means
  that the variable was created “by itself”;
- **install a linter in the editor** — a program that reads code and finds such
  places before running. We will talk about it closer to the projects.

<TryIt>
Check it all yourself right in the lecture. Open the console and run two lines in turn:
`accidental = 1;`, then `globalThis.accidental`. The second one answers
`1` — the variable you never declared now has a place in the global object.
</TryIt>

## 11. Six messages of the day {#errors}

All the errors of this day are about variables. Here they are together, with the text from Chrome:

| Code | Message | What is wrong |
| --- | --- | --- |
| `const x = 1; x = 2;` | `TypeError: Assignment to constant variable.` | trying to replace the value of a constant |
| `const x;` | `SyntaxError: Missing initializer in const declaration` | the constant has no initial value |
| `var = 5;` | `SyntaxError: Unexpected token '='` | the variable name is forgotten |
| `console.log(a); let a = 1;` | `ReferenceError: Cannot access 'a' before initialization` | access in the dead zone |
| `"use strict"; b = 5;` | `ReferenceError: b is not defined` | assigning to an undeclared variable (strict mode only) |
| `const o = Object.freeze({ x: 1 }); o.x = 2;` | `TypeError: Cannot assign to read only property 'x' of object '#<Object>'` | a read-only property (strict mode only) |

The last two messages do not appear in normal mode: assigning to an undeclared variable silently works,
and writing to a frozen object silently does not. This is the main argument for strict mode —
it turns quiet oddities into honest errors.

All six are read by one algorithm, and it also works for any future error about variables.
**First look at the kind of error — it tells you when it happened.**

| Kind | When it happened | The first question to ask yourself |
| --- | --- | --- |
| `SyntaxError` | before running, while reading the file | what did I write against the rules in this line? |
| `ReferenceError` | while running, when reading a name | is this name declared at all — and above in the code? |
| `TypeError` | while running, when writing | am I trying to change something that must not be changed? |

The difference between the first one and the other two is especially useful. A `SyntaxError` means that
**not a single line of the file ran** — the engine did not even start. If you see such
an error, there is no point looking for the cause in the logic: it is a brace, a quote or a missing name.
A `ReferenceError` and a `TypeError` appear on the way, which means that everything
before them has already run — you can use this to narrow the search.

## 12. Expression statements and empty statements {#statements}

Two small topics that complete the picture from day 3.

An **expression statement** is when an expression stands on its own, as a whole statement.
Almost every line of your program looks like this:

```js
count = count + 1;        // assignment
console.log("Salam");     // a function call
count++;                  // increment
```

The result of such an expression is not saved anywhere — so it makes sense only when the expression
has a side effect: something changed or something was printed. The line `2 + 2;` is syntactically
correct but useless: calculated and thrown away.

An **empty statement** is a lone semicolon. It means “do nothing here”
and is needed where the language requires at least some statement. More often, though, it appears by accident —
and this is a classic trap:

```js
let n = 0;
for (let i = 0; i < 3; i++);   // ← an extra semicolon
  n++;

console.log(n);   // 1, not 3
```

The semicolon closed the loop. The loop did “nothing” three times, and `n++` ended up outside
and ran once. The indentation deceives the eye; there is no error — just a wrong answer.

## 13. How to choose and how to name {#style}

The rule of choice for the whole course is exactly two steps:

1. write `const`;
2. if it turns out that the value has to be replaced, change it to `let`.

Why in this order and not the other way round: `const` tells the reader “this value will not
change further” — one less thing to keep an eye on. And the engine will back you up if
you assign by mistake.

Now names. We have covered the rules of the language; here are the agreements between people:

| What | How it is written | Example |
| --- | --- | --- |
| an ordinary variable | camelCase — every word after the first starts with a capital | `firstName`, `totalPrice` |
| a setting that is not changed | UPPER_CASE with underscores | `MAX_SCORE`, `MIN_GOOD` |
| “yes / no” | starts with `is`, `has` | `isReady`, `hasError` |
| a list | in the plural | `marks`, `students` |

<ProTip>
A good name answers the question “what is inside”, not “what type is it”. `d` is
bad, `data` is almost as bad, `daysLeft` is good. A long clear
name is better than a short mysterious one: you will type it in a second, and read it for months.
</ProTip>

See how names alone change readability. Here is code that calculates the cost of an order:

<Compare>
<Wrong label="Unclear">
```js
let a = 12;
let b = 40;
let c = 0.05;
let d = a * b;
let e = d + d * c;
```
</Wrong>

<Right label="Clear">
```js
const price = 12;
const count = 40;
const TAX = 0.05;
const subtotal = price * count;
const total = subtotal + subtotal * TAX;
```
</Right>
</Compare>

Both programs calculate the same thing, and they are the same to the engine. But in the left one it is impossible to notice a mistake:
if you mix up `c` and `d`, nobody will be surprised. In the right one `subtotal * TAX`
reads like a sentence, and `total * price` would look strange at once.

At the same time, notice the second difference: on the left there are five `let`, although not a single value
changes. On the right there are five `const`, and this tells the reader that there is nothing to keep an eye on.

## 14. The “Report card” with variables {#tabel}

Let us go back to yesterday’s program and rewrite it by today’s rules. Three things changed,
and each one comes from today’s lecture.

**The thresholds became named constants.** Yesterday the condition had bare numbers,
`4.5` and `3.5`. Such numbers are called “magic”: a month later nobody will remember
what they mean, and if a threshold appears in three places, all three will have to be changed and one is sure to be
forgotten. A constant at the top of the file solves both problems at once.

**Marks are added to an array that is declared with `const`.**
This is a direct check of section 5: the name is locked, the contents are not.

**`verdict` is declared outside the block.** This is the most important change, and below
we will see what happens if you do not do this.

```js
const MIN_EXCELLENT = 4.5;      // the settings moved to the top and got names
const MIN_GOOD = 3.5;

const student = {
  name: "Aman",
  marks: [5, 4, 5, 3, 5],
};

student.marks.push(4);          // const does not get in the way: we change the contents, not the name

function average(numbers) {
  let sum = 0;                  // sum changes in the loop — so let
  for (const n of numbers) {
    sum += n;
  }
  return sum / numbers.length;
}

const score = average(student.marks);

let verdict;                    // declared HERE, outside the blocks
if (score >= MIN_EXCELLENT) {
  verdict = "excellent";
} else if (score >= MIN_GOOD) {
  verdict = "good";
} else {
  verdict = "needs work";
}

console.log(`${student.name}: ${score.toFixed(2)} — ${verdict}`);
```

<ResultBox>
Aman: 4.33 — good
</ResultBox>

The last piece is the most important today. Look at what happens if you declare
the verdict inside the condition. Let us call it `grade` so that it does not clash with `verdict` above:

```js
if (score >= MIN_GOOD) {
  const grade = "good";         // declared INSIDE the block
}
console.log(grade);             // ReferenceError: grade is not defined
```

The variable was born and died inside the braces. Hence a technique used every day:
**if a value is needed after a block, declare it before the block** with `let`,
and inside only assign.

## 15. Common mistakes of the day {#mistakes}

| Mistake | Why | How to do it right |
| --- | --- | --- |
| `const` for a value that changes | a `TypeError` on the very first assignment | `let` — but only when it really changes |
| `let` where the value does not change | the reader thinks it needs watching | `const` by default |
| declared a variable inside `if`, read it outside | the block ended — the variable is gone | declare it before the block, assign inside |
| assignment without `let` or `const` | a typo silently creates a new global | always declare |
| expecting `const` to freeze an array | the name is locked, not the contents | `Object.freeze`, if you really need it |
| `userName` declared, `username` read | case matters | copy the name, do not type it again |

<Selfcheck>
1. How is `let x;` different from `const x;`?
   <Answer>The first is allowed: `x` will hold `undefined`. The second is a
   `SyntaxError`: a constant must have an initializer.</Answer>
2. Why does `const arr = [1]; arr.push(2);` give no error?
   <Answer>`const` forbids replacing the value of the variable, that is, the address of the array.
   The array itself stays changeable; `push` changes the contents at the same address.</Answer>
3. What does this code print: `if (true) { var a = 1; let b = 2; } console.log(a);`?
   <Answer>`1`. For `var` a block is not a border. And `console.log(b)`
   would give a `ReferenceError`.</Answer>
4. How does the output of `console.log(v)` before `var v = 1`
   differ from the output before `let v = 1`?
   <Answer>With `var` — `undefined`: the declaration is hoisted, the assignment is not.
   With `let` — `ReferenceError: Cannot access 'v' before initialization`:
   the variable is in the dead zone.</Answer>
5. What is dangerous about the line `totl = 5;` without `let`?
   <Answer>In normal mode it silently creates a global variable. If it is a typo in the name,
   the program goes on working with wrong data and reports nothing.</Answer>
</Selfcheck>
