## 1. Динамическая и слабая типизация {#dynamic}

Вчера мы давали значениям имена. Сегодня смотрим на сами значения — и начинаем с двух слов,
которыми описывают JavaScript в любой документации.

**Динамическая типизация** означает, что тип есть у значения, а не у переменной.
Одна переменная сегодня хранит число, завтра строку, и язык не возражает:

```js
let foo = 42;      // сейчас число
foo = "салам";     // теперь строка
foo = true;        // теперь логическое значение
```

В языках со статической типизацией — в Java, C#, TypeScript — так нельзя: там тип объявляют
заранее, и компилятор не даст положить в переменную что-то другое. У обоих подходов своя цена.
Динамический язык быстрее писать, статический — надёжнее.

**Слабая типизация** — вторая половина. Когда в одной операции встречаются значения
разных типов, язык не ругается, а *сам* приводит одно к другому:

```js
const foo = 42;
const result = foo + "1";
console.log(result);   // "421" — число стало строкой, а не 43
```

Это удобно ровно до того момента, когда приведение случается там, где вы его не ждали. Такие
ошибки не падают с сообщением — они просто дают неверный ответ. Поэтому знать типы и уметь их
проверять важнее, чем кажется на первой неделе.

<Why>
Вспомните вчерашний совет называть переменные так, чтобы имя говорило о содержимом:
`marks` — список, `isReady` — «да / нет». Теперь понятно, почему это не
придирка: язык сам за типами не следит, и единственная защита — ваша дисциплина.
</Why>

## 2. Восемь типов и один важный признак {#eight}

Типов восемь: семь примитивов и объект. Главный признак, по которому их делят, — **изменяемость**.

<Scheme src="scheme-eight.svg">Слева — то, что нельзя изменить. Справа — то, что можно</Scheme>

«Неизменяемый» здесь значит буквально: у примитива нет частей, которые можно поменять. Строку нельзя
отредактировать — можно только собрать новую:

```js
let word = "Мары";
word[0] = "К";        // тихо ничего не делает
console.log(word);    // "Мары"

word = "К" + word.slice(1);   // а так получится новая строка
console.log(word);            // "Кары"
```

Все методы строк работают именно так: не портят оригинал, а возвращают новую строку. Подробно —
день 16.

### Два редких примитива

Пять типов из левой колонки вы будете встречать каждый день. Два оставшихся — `BigInt`
и `Symbol` — в Essentials не понадобятся, но знать, что они есть, надо: увидите в чужом коде.

**`BigInt`** нужен для очень больших целых чисел. Обычное число хранит
целые точно только до определённого предела, а дальше начинает округлять:

```js
console.log(Number.MAX_SAFE_INTEGER);   // 9007199254740991 — дальше точности нет

// обычные числа: два разных числа стали одним
Number.MAX_SAFE_INTEGER + 1 === Number.MAX_SAFE_INTEGER + 2;   // true (!)

// BigInt: пишется с буквой n на конце
const big = 9007199254740993n;
typeof big;   // "bigint"
```

Смешивать `BigInt` с обычными числами в одном выражении нельзя — язык специально
не разрешает, чтобы не потерять точность молча:

```js
1n + 1;   // TypeError: Cannot mix BigInt and other types, use explicit conversions
```

**`Symbol`** — значение, которое гарантированно ни с чем не совпадает.
Даже два символа с одинаковым описанием не равны:

{/* ahead-ok: курс 2 */}

```js
Symbol("id") === Symbol("id");   // false — это разные значения
typeof Symbol("id");             // "symbol"
```

Нужны символы для служебных ключей объектов, которые точно не столкнутся с чужими. Разбираем
в курсе 2.

### Строкой всё не опишешь

Раз типов много, встаёт вопрос: какой выбрать? У новичков есть соблазн хранить всё строками —
строки легко складывать, легко выводить, и из поля ввода всё равно приходит строка.

```js
const marks = "5,4,5,3";   // соблазнительно, но плохо
```

Плохо тут вот что: чтобы получить оценки по одной, строку придётся разбирать по запятой.
А если в одном из значений окажется запятая, разбор сломается. Дальше добавят экранирование,
потом правила экранирования — и вместо данных получится маленький собственный язык, который
надо поддерживать.

```js
const marks = [5, 4, 5, 3];   // так: массив чисел
marks.length;                 // сразу известно, сколько их
marks[0] + marks[1];          // и считать можно
```

Правило: **строки — для текста**. Для всего остального берите подходящий тип:
массив для списка, объект для набора свойств, число для числа. Пришла строка извне — разберите
её один раз на входе и дальше работайте с нормальными значениями.

## 3. Оператор typeof {#typeof}

Раз тип принадлежит значению, его можно спросить. Для этого есть оператор `typeof`.
Он возвращает **строку** с названием типа:

{/* ahead-ok: курс 2 */}

```js
typeof 42;              // "number"
typeof 9007199254740993n;  // "bigint"
typeof "Мары";          // "string"
typeof true;            // "boolean"
typeof Symbol("id");    // "symbol"
typeof undefined;       // "undefined"
typeof { };             // "object"
typeof function () { }; // "function"
```

Обратите внимание: результат — строка, поэтому сравнивают с ней в кавычках.

```js
const value = 42;

if (typeof value === "number") {       // правильно
  console.log("это число");
}

if (typeof value === number) {         // ReferenceError: number is not defined
  console.log("а так нельзя");
}
```

Список возможных ответов закрытый — их ровно восемь, и ничего другого `typeof`
не возвращает.

Зачем это нужно на практике? Затем, что функция часто должна работать по-разному в зависимости
от того, что ей дали. Вот живой пример: выводим оценку, а она может прийти и числом, и строкой,
и вообще не прийти:

```js
function showMark(mark) {
  if (typeof mark === "number") {
    return `оценка: ${mark}`;
  }
  if (typeof mark === "string") {
    return `оценка строкой: ${mark}`;
  }
  return "оценки нет";
}

showMark(5);       // "оценка: 5"
showMark("5");     // "оценка строкой: 5"
showMark();        // "оценки нет"
```

Такую проверку в работе пишут постоянно: данные приходят из поля ввода, из ответа сервера,
из чужого кода — и никто не обещает, что там будет нужный тип. К концу урока мы соберём из таких
проверок готовую шпаргалку.

А пока — восемь ответов на восемь типов? Не совсем, и вот тут начинается интересное.

## 4. Два места, где typeof врёт {#lies}

Типов восемь, ответов тоже восемь, но списки не совпадают. Сравните:

| Тип | Что отвечает `typeof` |  |
| --- | --- | --- |
| Number | `"number"` |  |
| BigInt | `"bigint"` |  |
| String | `"string"` |  |
| Boolean | `"boolean"` |  |
| Symbol | `"symbol"` |  |
| Undefined | `"undefined"` |  |
| Null | `"object"` | **← неправда** |
| Object | `"object"` |  |
| — функция (это объект) | `"function"` | **← лишний ответ** |

**Первая неправда: `typeof null` возвращает `"object"`.**
Это ошибка, допущенная в самой первой версии языка в 1995 году. Исправить её нельзя: на свете
миллионы страниц, которые на это поведение рассчитывают, и любое исправление их сломает.
Проверять на `null` приходится отдельно:

```js
const value = null;

typeof value === "object";   // true — но это не объект!
value === null;              // true — вот правильная проверка
```

**Вторая особенность мягче: функция — это объект**, мы говорили об этом на дне 3.
Но `typeof` для неё отвечает `"function"`. Тут формального вранья нет,
и ответ скорее полезный: проверить, можно ли значение вызвать, — частая задача.

И третье, о чём стоит знать сразу: **массив от объекта `typeof` не отличает**.

```js
typeof [1, 2, 3];        // "object" — не помогает
Array.isArray([1, 2, 3]);   // true  — вот правильный способ
Array.isArray({ });         // false
```

`Array.isArray` разберём на дне 19, а сегодня запомните сам факт: для массива нужен
отдельный вопрос.

<ProTip>
Есть у `typeof` и особая доброта: для **необъявленного имени** он
не бросает ошибку, а спокойно отвечает `"undefined"`.

```js
console.log(nikogdaNeObyavlyali);          // ReferenceError
console.log(typeof nikogdaNeObyavlyali);   // "undefined" — тихо
```

Это единственный оператор с таким поведением, и раньше им проверяли наличие переменной.
Правда, в мёртвой зоне (день 4) он всё-таки падает — там имя уже занято.
</ProTip>

## 5. undefined: значения нет {#undefined}

`undefined` означает «значения тут нет, и никто его не клал». Язык сам подставляет
его в четырёх случаях, и все четыре вы уже встречали:

| Случай | Пример |
| --- | --- |
| переменная объявлена без значения | `let x;` |
| у объекта спросили несуществующее свойство | `user.iDontExist` |
| функция ничего не вернула | `function f() { }` |
| функцию вызвали без аргумента | `f()` при `function f(a)` |

```js
let x;
console.log(x);              // undefined

const user = { name: "Аман" };
console.log(user.age);       // undefined — свойства нет

function greet() { }
console.log(greet());        // undefined — return не написали
```

<Important>
Во всех четырёх случаях **ошибки не будет**. Программа спокойно поедет дальше
с `undefined` внутри, и сломается позже — в другом месте и с непонятным сообщением.
Поэтому `undefined` в консоли — это почти всегда подсказка: где-то выше вы чего-то
не положили.
</Important>

## 6. null: пусто намеренно {#null}

`null` означает другое: «здесь пусто, и это решение программиста». Язык сам
`null` почти нигде не подставляет — его пишете вы.

```js
let selectedStudent = null;   // пока никого не выбрали — и мы об этом заявляем

// ... позже
selectedStudent = { name: "Гүлнар" };
```

Зачем нужна такая договорённость? Чтобы отличать «ещё не выбрали» от «забыли положить».
Если в переменной `null` — значит, всё идёт по плану, просто выбора пока нет.
Если `undefined` — скорее всего, где-то ошибка.

<Analogy>
Представьте графу «Отчество» в анкете. Пустая графа — `undefined`: неизвестно,
то ли отчества нет, то ли человек не дописал. Прочерк в графе — `null`: человек
дошёл до неё и сказал «у меня его нет». Разница в том, был ли ответ.
</Analogy>

## 7. null или undefined: что выбрать {#compare}

Технически они похожи, и в этом главная путаница. Вот все различия разом:

| Проверка | `null` | `undefined` |
| --- | --- | --- |
| `typeof` | `"object"` (ошибка языка) | `"undefined"` |
| кто кладёт | программист | язык |
| в числе | `null + 1` → `1` | `undefined + 1` → `NaN` |
| `Number()` | `0` | `NaN` |
| в условии | ложь | ложь |

Третья и четвёртая строки — настоящая ловушка. Два очень похожих значения ведут себя в арифметике
совершенно по-разному:

```js
console.log(null + 1);        // 1   — null превратился в 0
console.log(undefined + 1);   // NaN — undefined не превращается ни во что
```

А сравниваются они так:

```js
null == undefined;    // true  — нестрогое сравнение считает их одинаковыми
null === undefined;   // false — строгое видит разницу
```

Это, пожалуй, единственный случай, когда `==` бывает полезен: проверка
`value == null` отвечает `true` и для `null`,
и для `undefined` сразу. Приём распространённый, но на курсе мы всё равно будем писать
строго и явно. Подробно про два вида сравнения — день 7.

<ProTip>
Практическое правило: **в своём коде пишите `null`**, когда хотите
сказать «пусто». `undefined` оставьте языку — пусть он означает «что-то пошло не так
или ещё не дошли».
</ProTip>

## 8. NaN: число, которое не число {#nan}

`NaN` — сокращение от «Not a Number», «не число». Парадокс в том, что
**тип у него — число**:

```js
typeof NaN;   // "number"
```

Противоречия нет: `NaN` — это специальное числовое значение, которым отвечают,
когда посчитать не получилось. Появляется он пятью способами:

| Откуда | Пример |
| --- | --- |
| неудачное превращение в число | `Number("салам")`, `parseInt("blabla")` |
| математика без ответа | `Math.sqrt(-1)` |
| неопределённость | `0 * Infinity`, `Infinity - Infinity` |
| заражение от другого `NaN` | `7 * "blabla"`, `NaN + 5` |
| неверные данные вместо числа | `new Date("blabla").getTime()` |

И у него есть свойство, которого нет больше ни у одного значения в языке:

```js
NaN === NaN;   // false — единственное значение, не равное самому себе
```

Это не причуда JavaScript, а правило стандарта IEEE 754, по которому работают дробные числа
во всех языках. Логика такая: `NaN` означает «неизвестно что». Два неизвестных числа
не обязаны быть равны, поэтому ответ — «нет».

Из того же правила следует ещё одна особенность: **любое сравнение с `NaN`
даёт `false`** — даже то, которое кажется обязанным быть истинным:

```js
NaN > 1;      // false
NaN < 1;      // false
NaN >= NaN;   // false
```

## 9. Как поймать NaN {#findnan}

Раз `===` не работает, нужен другой способ. Их три, и выбирать надо с умом.

```js
const value = Number("салам");   // NaN

Number.isNaN(value);   // true  — правильный способ
isNaN(value);          // true  — тоже true, но осторожно
Object.is(value, NaN); // true  — работает, но пишут редко
```

Разница между первыми двумя видна на другом примере, и она важная:

<Compare>
<Wrong label="isNaN — старый">
```js
isNaN("салам");   // true
```

Сначала пытается превратить в число, потом проверяет. Строка «салам» — не `NaN`,
она просто строка, а ответ — `true`.
</Wrong>

<Right label="Number.isNaN — точный">
```js
Number.isNaN("салам");   // false
```

Ничего не превращает. Отвечает `true` только тогда, когда значение
действительно `NaN`.
</Right>
</Compare>

Правило: **пишем `Number.isNaN`**. Старый `isNaN` отвечает
на другой вопрос — «не получится ли из этого числа», — и если вам нужен именно он, лучше написать
это прямо.

<Mistake>
Самая частая ошибка с `NaN` — вообще его не заметить. Программа получает
`NaN` в одном месте, а падает или врёт совсем в другом:

```js
const input = "12 манат";       // пользователь ввёл с лишним словом
const price = Number(input);    // NaN
const total = price * 3;        // NaN — зараза пошла дальше
console.log(`Итого: ${total}`); // "Итого: NaN"
```

Поэтому число, пришедшее от пользователя, проверяют *сразу*, а не в конце расчёта.
</Mistake>

## 10. Infinity и деление на ноль {#infinity}

Второе особое числовое значение — `Infinity`, бесконечность. Тип у него тоже число.
Получается он в двух случаях:

```js
console.log(1 / 0);                  // Infinity
console.log(-1 / 0);                 // -Infinity
console.log(Number.MAX_VALUE * 2);   // Infinity — вышли за предел
typeof Infinity;                     // "number"
```

Обратите внимание: деление на ноль в JavaScript **не ошибка**. В школьной математике
так делать нельзя, а здесь получается вполне рабочее значение, с которым можно считать дальше.

С ним даже арифметика работает осмысленно, но до предела: там, где ответ становится
неопределённым, появляется `NaN`.

```js
Infinity + 1;          // Infinity
Infinity * 2;          // Infinity
Infinity - Infinity;   // NaN — что тут должно получиться, непонятно
0 * Infinity;          // NaN
```

В повседневном коде `Infinity` встречается редко, зато как признак ошибки —
постоянно: увидели в выводе бесконечность, значит, где-то поделили на ноль.

### Минус ноль

Раз уж речь о делении на ноль: в JavaScript нулей на самом деле два — `+0`
и `-0`. Это следствие того же стандарта IEEE 754. В обычной работе разницы почти нет:

```js
+0 === -0;         // true — сравнение их не различает
console.log(-0);   // -0 — а консоль Chrome минус показывает
String(-0);        // "0" — при превращении в строку минус теряется
```

В расчётах разница проявляется при делении:

```js
console.log(42 / +0);   // Infinity
console.log(42 / -0);   // -Infinity
```

Отрицательный ноль получается, например, при умножении на ноль отрицательного числа или при
округлении маленькой отрицательной дроби. Специально о нём думать не нужно; знать стоит, чтобы
не удивляться минусу перед бесконечностью там, где его вроде бы неоткуда взять.

## 11. Boolean: шесть лжецов {#boolean}

Логический тип устроен проще всех: в нём ровно два значения, `true` и `false`.
Интересное начинается, когда в условие ставят *не* логическое значение — а так делают
постоянно.

```js
const name = "Аман";

if (name) {                  // тут не true и не false, а строка
  console.log("имя есть");
}
```

Язык сам превращает значение в «да» или «нет». Правило короткое, и его стоит выучить наизусть —
это одно из немногого, что действительно надо запомнить:

<Important>
**Ложных значений шесть:** `false`, `0` — ноль в любом
виде (и `-0` из прошлого раздела, и `0n` — BigInt-ноль из раздела 2),
`""` (пустая строка), `NaN`, `null`, `undefined`.
\
**Всё остальное истинно.**
</Important>

<Scheme src="scheme-boolean.svg">Шесть слева — выучить. Справа — то, что чаще всего принимают за пустоту</Scheme>

«Всё остальное» — это и есть место, где спотыкаются. Вот значения, которые выглядят пустыми,
но считаются истиной:

```js
Boolean("0");     // true — строка непустая, а что в ней, неважно
Boolean(" ");     // true — пробел тоже символ
Boolean([]);      // true — пустой массив всё равно объект
Boolean({ });     // true — и пустой объект тоже
Boolean(-1);      // true — ложен только ноль
```

Проверить явно можно двумя способами, оба правильные:

```js
Boolean("текст");   // true — функция Boolean
!!"текст";          // true — двойное отрицание, короткая запись
```

Двойное отрицание `!!` — это просто `!` дважды: первое превращает значение
в логическое и переворачивает, второе переворачивает обратно. Запись короткая и очень
распространённая, так что узнавать её надо.

### Три функции превращения

`Boolean` — не единственная такая функция. Их три, по одной на каждый тип, в который
имеет смысл превращать:

```js
Number("42");      // 42
String(42);        // "42"
Boolean(42);       // true
```

Все три пишут **без `new`** — тогда это обычные функции превращения,
и результат получается примитивом. Вот что они делают с частыми значениями:

| Значение | `Number()` | `String()` | `Boolean()` |
| --- | --- | --- | --- |
| `"42"` | `42` | `"42"` | `true` |
| `"12px"` | `NaN` | `"12px"` | `true` |
| `""` | `0` | `""` | `false` |
| `true` | `1` | `"true"` | `true` |
| `null` | `0` | `"null"` | `false` |
| `undefined` | `NaN` | `"undefined"` | `false` |
| `[]` | `0` | `""` | `true` |
| `[5]` | `5` | `"5"` | `true` |
| `{ }` | `NaN` | `"[object Object]"` | `true` |

Две строки этой таблицы стоит разглядеть внимательно. **`Number("")` даёт ноль,
а не `NaN`** — пустая строка считается «нулём символов», и это регулярно ломает
проверку ввода: пользователь ничего не ввёл, а программа получила честное число 0.

И вторая: **пустой массив в числовом контексте — ноль, а в логическом — истина**.
Одно и то же значение, два разных ответа, потому что вопросы разные. Такие странности случаются
с объектами, и именно поэтому объекты не сравнивают и не складывают, а работают с их содержимым.

Заметьте: в таблице нет ни одной ошибки — только результаты. Язык всегда что-нибудь ответит.
Про то, когда он делает это сам, без вашей просьбы, — день 8.

## 12. Обёртки и ловушка new Boolean {#wrapper}

Остался вопрос, который наверняка уже возник. Если примитив — это простое значение без частей,
то почему у него есть методы?

```js
"Мары".length;        // 4
true.toString();      // "true"
(42).toFixed(2);      // "42.00"
```

Ответ: в момент обращения к свойству язык **временно заворачивает** примитив
в объект-обёртку, берёт у него нужное и тут же обёртку выбрасывает.

<Scheme src="scheme-wrapper.svg">Примитив не хранит методы — их на мгновение одалживает обёртка</Scheme>

Для пяти примитивов такие обёртки есть: `Number`, `String`,
`Boolean`, `BigInt`, `Symbol`. А вот у `null`
и `undefined` обёртки нет — поэтому обращение к их свойствам падает с ошибкой,
и мы увидим это через минуту.

Обёртку можно создать и руками, словом `new`. Делать этого не нужно — и вот почему:

```js
const myFalse = new Boolean(false);

typeof myFalse;        // "object" — это уже не примитив

if (myFalse) {
  console.log("сработало!");   // и это выведется
}
```

<Mistake>
`new Boolean(false)` — это **объект**, а любой объект истинен.
Получается значение, которое печатается как `false`, но в условии ведёт себя как
`true`. Лекарство простое: **никогда не писать `new` перед
`Boolean`, `Number` и `String`**. Без `new`
те же слова работают как обычные функции превращения, и это правильный способ.

```js
Boolean(значение);       // так — превращение, получается примитив
new Boolean(значение);   // так — объект-обёртка, почти всегда ошибка
```
</Mistake>

Если обёртка всё-таки откуда-то попала к вам в код, достать из неё примитив можно методом
`valueOf`, а превратить в строку — методом `toString`:

```js
const wrapped = new Boolean(false);
wrapped.valueOf();    // false — настоящий примитив
wrapped.toString();   // "false" — строка
true.toString();      // "true" — у обычного значения тоже работает
```

## 13. Две ошибки дня {#errors}

Обе связаны с типами, и обе вы уже видели.

**ReferenceError: x is not defined.** Обратились к имени, которого нет. Чаще всего
это опечатка или переменная, объявленная ниже по коду:

```js
console.log(schet);   // ReferenceError: schet is not defined
```

**TypeError: неожиданный тип.** Значение есть, но оно не умеет того, что от него
хотят. В подавляющем большинстве случаев виноваты `null` или `undefined` —
те самые два значения без обёртки:

```js
const student = null;
student.name;      // TypeError: Cannot read properties of null (reading 'name')

let user;
user.name;         // TypeError: Cannot read properties of undefined (reading 'name')

const count = 5;
count();           // TypeError: count is not a function
```

Читается такое сообщение задом наперёд и очень точно. `Cannot read properties of null
(reading 'name')` означает: «я пытался прочитать свойство `name`, а слева
от точки оказался `null`». То есть искать надо не `name`, а то, что стоит
до точки, — и выяснять, почему там пусто.

<Important>
Разница между двумя ошибками в одном слове. `ReferenceError` — **имени нет**.
`TypeError` — **имя есть, значение не то**. Первое чинят в объявлении,
второе — там, откуда значение пришло.
</Important>

Разберём `TypeError` на настоящем примере — так его и чинят в работе:

```js
const students = [
  { name: "Аман", marks: [5, 4] },
  { name: "Гүлнар", marks: [5, 5] },
];

const third = students[2];               // такого нет — получили undefined
console.log(third.marks.length);
// TypeError: Cannot read properties of undefined (reading 'marks')
```

Шаг первый: читаем сообщение. «Не могу прочитать свойство `marks`, потому что слева
`undefined`». Значит, виноват не `marks`, а то, что стоит перед точкой, —
`third`.

Шаг второй: идём **влево от точки** и смотрим, откуда там взялось пустое значение.
`third` — это `students[2]`, а в массиве всего два элемента с индексами 0 и 1.
Настоящая ошибка на строку выше, чем та, что указана в сообщении.

Шаг третий: чиним причину, а не симптом. Можно взять правильный индекс, а можно проверить:

```js
const third = students[2];

if (third === undefined) {
  console.log("такого студента нет");
} else {
  console.log(third.marks.length);
}
```

<ProTip>
Приём «иди влево от точки» работает для любого `TypeError` вида «Cannot read
properties». В длинной цепочке `a.b.c.d` сообщение точно называет, на каком звене
всё оборвалось: если написано `(reading 'd')`, то пустым оказалось `a.b.c`.
Смотреть надо туда, а не на `d`.
</ProTip>

## 14. Как проверять данные в программе {#check}

Соберём сегодняшнее в один практический приём. Всё, что приходит извне — из поля ввода,
из ответа сервера, из чужой функции, — проверяют **сразу**, до расчётов.

```js
function priceToNumber(input) {
  const price = Number(input);

  if (Number.isNaN(price)) {
    return null;                 // не получилось — говорим об этом честно
  }
  return price;
}

const result = priceToNumber("12 манат");

if (result === null) {
  console.log("Введите только число");
} else {
  console.log(`Итого: ${result * 3}`);
}
```

Здесь работает всё, что мы сегодня разобрали: `Number` превращает строку в число,
`Number.isNaN` ловит неудачу, `null` сообщает «пусто намеренно»,
а `=== null` проверяет это точно. Строгое сравнение важно: с `==` проверка
поймала бы ещё и `undefined`, а это другая ситуация.

<TryIt>
Допишите эту функцию в свой «Табель» и подайте ей строку с оценкой, введённой руками.
Попробуйте ввести `"5"`, `"пять"`, `""` и `"  4  "`.
Два из четырёх ответов вас удивят — разберитесь почему.
</TryIt>

### Шпаргалка проверок

Соберём в одном месте все способы спросить «что это такое». Эту таблицу удобно держать под рукой
весь курс:

| Что проверяем | Как |
| --- | --- |
| число (и не `NaN`) | `typeof x === "number" && !Number.isNaN(x)` |
| строка | `typeof x === "string"` |
| логическое значение | `typeof x === "boolean"` |
| функция | `typeof x === "function"` |
| массив | `Array.isArray(x)` |
| объект (не `null`, не массив) | `typeof x === "object" && x !== null && !Array.isArray(x)` |
| именно `null` | `x === null` |
| именно `undefined` | `x === undefined` |
| пусто: `null` или `undefined` | `x == null` (тот самый случай для `==`) |
| «ничего полезного»: любое ложное | `!x` |

Две строки требуют оговорки. Первая: проверка на число **обязана** включать
`Number.isNaN` — иначе `NaN` пройдёт как нормальное число, ведь
`typeof NaN` это `"number"`.

Вторая: проверка объекта отсекает `null` и массивы, но пропустит дату, ошибку и вообще
любой встроенный объект — они ведь тоже объекты. Если нужно отличить именно «простой объект
со свойствами», задача решается сложнее, и она подождёт до курса 2.

Последняя строка — самая короткая и самая опасная. `!x` отвечает «да» на все шесть
ложных значений сразу, включая `0` и `""`. Для проверки «пользователь
что-то ввёл» это часто ошибка: ноль — вполне законный ввод.

```js
function checkAge(age) {
  if (!age) {                        // ловушка: ноль тоже ложь
    return "укажите возраст";
  }
  return `возраст: ${age}`;
}

checkAge(0);   // "укажите возраст" — а человеку правда 0 лет

// правильнее спросить ровно то, что имеется в виду
function checkAge2(age) {
  if (age == null) {                 // только null и undefined
    return "укажите возраст";
  }
  return `возраст: ${age}`;
}
```

## 15. Частые ошибки дня {#mistakes}

| Ошибка | Почему | Как правильно |
| --- | --- | --- |
| `typeof x === "object"` как проверка объекта | для `null` тоже `"object"` | добавить `x !== null` |
| `typeof arr === "array"` | такого ответа не бывает | `Array.isArray(arr)` |
| `x === NaN` | `NaN` не равен себе | `Number.isNaN(x)` |
| `isNaN("текст")` как проверка на `NaN` | сначала превращает в число | `Number.isNaN` |
| `if (arr.length)` перепутали с `if (arr)` | пустой массив истинен | проверять именно `length` |
| `new Boolean(false)` | получается истинный объект | `Boolean(x)` или `!!x` |

<Selfcheck>
1. Почему `typeof null` отвечает `"object"` и как правильно
   проверить на `null`?
   <Answer>Это ошибка первой версии языка 1995 года; исправить нельзя — сломается старый код.
   Правильная проверка — `value === null`.</Answer>
2. Что выведут `null + 1` и `undefined + 1`?
   <Answer>`1` и `NaN`. `null` в числовом контексте
   превращается в 0, а `undefined` — в `NaN`.</Answer>
3. Чем `Number.isNaN("салам")` отличается от `isNaN("салам")`?
   <Answer>`false` и `true`. Старый `isNaN` сначала пытается
   превратить значение в число, а `Number.isNaN` проверяет, что перед ним
   действительно `NaN`. Пишем второй.</Answer>
4. Какие из этих значений истинны: `0`, `"0"`, `[]`,
   `""`, `{}`?
   <Answer>Истинны `"0"`, `[]` и `{}`. Ложны `0`
   и `""`. Пустой массив и пустой объект — это объекты, а объекты всегда истинны.</Answer>
5. Почему `if (new Boolean(false))` выполнит тело условия?
   <Answer>Потому что `new Boolean(false)` создаёт объект-обёртку, а не примитив
   `false`. Любой объект истинен. Поэтому `Boolean` пишут
   без `new`.</Answer>
