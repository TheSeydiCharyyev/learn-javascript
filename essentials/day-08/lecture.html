1. Долг из вчерашнего дня

Вчера мы приняли на веру три строки:

"0" == 0;     // true
"" == 0;      // true
"0" == "";    // false

Сегодня разберём механизм, который за этим стоит. Заодно закроем модуль: это последний день про синтаксис, типы и операторы. Дальше — управление потоком программы.

Тема называется приведение типов (или преобразование типов). Мы уже сталкивались с ней каждый день: "2" + 3 даёт "23", "10" - 5 даёт 5, пустой массив в условии истинен. Пора собрать это в систему.

Зачем разбираться, если можно просто «всегда писать === и превращать типы явно»? Затем, что читать чужой код вам придётся с первого рабочего дня. И затем, что приведение случается там, где вы его не просили: в условии, в шаблонной строке, при сложении. Знание механизма превращает загадочные баги в скучные.

3. Приведение к строке

Самое предсказуемое из трёх. Примитивы превращаются так, как выглядят:

String(42);          // "42"
String(true);        // "true"
String(null);        // "null"
String(undefined);   // "undefined"

Массив склеивает свои элементы через запятую, а обычный объект отвечает одинаково всегда:

String([1, 2, 3]);   // "1,2,3"
String([]);          // ""      — пустой массив даёт пустую строку
String({ a: 1 });    // "[object Object]"
[object Object] в выводе — всегда признак ошибки: вы вывели объект там, где ждали текст. Мы говорили об этом на дне 6. Чтобы увидеть содержимое, передавайте объект отдельным аргументом: console.log("данные:", obj).

4. Приведение к числу

Здесь правил больше всего, и именно здесь живут неожиданности. Начнём с простого:

Number("42");      // 42
Number("  42  ");  // 42    — пробелы по краям отбрасываются
Number("1e3");     // 1000  — научная запись понимается
Number("0x1f");    // 31    — и шестнадцатеричная тоже
Number("abc");     // NaN   — не вышло
Number("12px");    // NaN   — «почти число» не считается

А теперь три ответа, которые ловят всех:

Number("");          // 0   ← пустая строка это НОЛЬ, а не NaN
Number(" ");         // 0   ← и пробел тоже
Number(null);        // 0   ← а null тоже ноль
Number(undefined);   // NaN ← зато undefined — не ноль
Первая строка ломает проверку ввода чаще всех остальных вместе взятых. Пользователь ничего не ввёл — поле дало пустую строку — Number("") вернул честный ноль — программа решила, что человек ввёл 0. 
const input = "";              // ничего не ввели
const age = Number(input);     // 0
if (Number.isNaN(age)) {       // не сработает! ноль это не NaN
  console.log("введите возраст");
}
Проверять надо до превращения: if (input === "").

Логические значения превращаются очевидно: true — это 1, false — 0. Отсюда забавный приём подсчёта, который иногда встречается:

Number(true) + Number(true) + Number(false);   // 2 — сколько раз «да»

Есть и другие способы

Number() — не единственная функция превращения в число. Есть ещё две, parseInt и parseFloat, и ведут они себя иначе. Разбирать их будем на дне 17 вместе с числами, но разницу стоит увидеть сейчас — она объясняет, почему выбор функции важен:

СтрокаNumber()parseInt()parseFloat()
"42"424242
"42px"NaN4242
"px42"NaNNaNNaN
""0NaNNaN
"3.9"3.933.9

Разница в подходе. Number() требует, чтобы вся строка была числом; если мешает хоть один лишний символ — NaN. А parseInt читает с начала, сколько получится, и останавливается: из "42px" он спокойно достанет 42.

Отсюда правило выбора: для проверки ввода берите Number() — он честно скажет «это не число». Для вытаскивания числа из текста вроде "16px" берите parseInt. И обратите внимание на строку с пустой строкой: тут они расходятся ровно наоборот, и parseInt("") даёт NaN, что для проверки ввода как раз удобнее.

Number("42px");     // NaN — вся строка должна быть числом
parseInt("42px");   // 42 — читает с начала, сколько получится
parseInt("3.9");    // 3 — дробную часть отбросил
parseFloat("3.9");  // 3.9
parseInt("");       // NaN — а Number("") дал бы 0

5. Приведение к логическому

Самое простое из трёх, потому что правило одно и закрытое — мы выучили его на дне 5:

Ложны шесть значений из дня 5: false, 0 — ноль в любом виде (-0, 0n), "", NaN, null, undefined. Всё остальное истинно — включая "0", " ", [] и { }.

Главное отличие от двух других приведений: здесь никогда не бывает ошибок и сюрпризов вроде NaN. Любое значение уверенно превращается либо в «да», либо в «нет». Поэтому условия в JavaScript никогда не падают — они просто иногда ведут не в ту ветку.

Boolean(0);      // false
Boolean("0");    // true — непустая строка, хоть внутри и ноль
Boolean(" ");    // true — пробел тоже символ
Boolean([]);     // true — пустой массив истинен
!!"";            // false — двойное «не» работает как Boolean
!!"Мары";        // true

6. Когда язык делает это сам

Всё перечисленное срабатывает не только когда вы пишете Number(x). Гораздо чаще язык делает это молча. Вот полный список мест, которые вы уже встречали:

Обратите внимание, чего в таблице нет: === и !==. Они не приводят ничего и никогда. Вот почему весь курс мы пишем именно их — это единственные операторы сравнения, которые не требуют держать в голове таблицу правил.

Строки таблицы, проверенные в консоли:

"2" + 3;      // "23" — рядом строка, склейка
"10" - 5;     // 5 — минус бывает только числовой

"10" > "9";   // false — две строки сравниваются посимвольно: "1" меньше "9"

s++;          // 5 — вернул старое значение, но уже числом
s;            // 6
typeof s;     // "number"
// а "5"++ — SyntaxError: Invalid left-hand side expression in postfix operation

Одно значение, четыре ответа

Чтобы почувствовать, насколько всё зависит от места, проследим за одним значением — пустым массивом — по четырём контекстам:

const x = [];

if (x) { }        // войдёт!     — в условии массив истинен
`${x}`;           // ""          — к строке стал пустой строкой
x + 1;            // "1"         — сначала "", потом склейка
x - 1;            // -1          — сначала "", потом 0, потом вычитание
x == false;       // true        — через число: 0 == 0

Пять строк, пять разных поведений, одно и то же значение. И ни одной ошибки — язык везде уверенно что-нибудь ответил.

Вот в чём главная опасность молчаливого приведения: оно никогда не падает. Ошибка типов в JavaScript — это не красное сообщение в консоли, а неправильное число в отчёте. Поэтому привычка приводить типы явно стоит дороже, чем знание всех таблиц.

7. Ответ на вчерашний вопрос

Теперь можно разобрать те три строки. Правило == для разных типов такое: если типы не совпадают, значения приводятся к числу (с отдельными оговорками для null и объектов). А если типы совпадают — сравнение идёт напрямую, без превращений.

Разберём по шагам.

  1. "0" == 0 — строка и число, типы разные. Строка превращается в число: Number("0") даёт 0. Сравниваем 0 == 0 — истина.
  2. "" == 0 — снова строка и число. Number("") даёт 0. Снова 0 == 0 — истина.
  3. "0" == "" — обе строки. Типы совпали, приводить нечего, сравниваем как текст: "0" и "" — разные. Ложь.
Number("0");   // 0
Number("");    // 0 — две разные строки, одно число
"0" == "";     // false — а здесь до чисел не дошло: обе стороны строки

Весь фокус в том, что Number("0") и Number("") дают одинаковый ноль, хотя сами строки разные. Первые две пары этим нулём и сравниваются, а третья до чисел вообще не доходит.

Отсюда и практический вывод. Нетранзитивность == — не баг и не случайность, а прямое следствие того, что маршрут сравнения зависит от типов. Разные типы — разные правила. Именно поэтому ===, у которого маршрут один, предсказуем.

8. Как превращаются объекты

С объектами на шаг сложнее. Сам по себе объект нельзя ни сложить, ни сравнить, поэтому язык сначала превращает его в примитив — и только потом применяет обычные правила.

[] + 1;        // "1"   — [] стал "", потом склейка
[5] + 1;       // "51"  — [5] стал "5", потом склейка
[5] - 1;       // 4     — [5] стал "5", потом число 5, потом вычитание
[1, 2] - 1;    // NaN   — [1,2] стал "1,2", а это не число

Обратите внимание на вторую и третью строки. Массив [5] в обоих случаях превращается в строку "5". Но дальше + видит строку и склеивает, а - строк не понимает и делает из "5" число. Один и тот же операнд, два разных результата — из-за оператора.

Представьте почтовый перевод. Объект — это посылка, а операторы работают только с деньгами. Сначала посылку оценивают, превращая в сумму, и лишь потом складывают или сравнивают. Оценщик у массива один («перечисли содержимое через запятую»), у обычного объекта — другой, и он всегда отвечает "[object Object]".

Специально пользоваться этим не надо — складывать массивы никто не собирается. Знать нужно, чтобы не растеряться, увидев в консоли "51" или NaN там, где ждали число.

Откуда берётся [object Object]

Эта надпись встречается чаще всех остальных странностей вместе взятых, поэтому разберём её до конца. Вот как она появляется:

const student = { name: "Аман", marks: [5, 4] };

console.log("Студент: " + student);
// "Студент: [object Object]"

console.log(`Студент: ${student}`);
// "Студент: [object Object]"

В обеих строках объект попал в строковый контекст, а обычный объект умеет превращаться в строку ровно одним способом — этой самой надписью. Она означает буквально «здесь был объект» и больше ничего не сообщает.

Что делать — зависит от того, чего вы хотели:

// хотели одно свойство — возьмите его
console.log(`Студент: ${student.name}`);          // "Студент: Аман"

// хотели посмотреть содержимое — передайте отдельным аргументом
console.log("Студент:", student);                 // консоль раскроет объект

// хотели строку со всем содержимым — JSON.stringify (день 23)
console.log(JSON.stringify(student));             // {"name":"Аман","marks":[5,4]}
Разница между console.log("a: " + obj) и console.log("a:", obj) принципиальна. В первом случае вы склеиваете строки, и объект обязан превратиться в текст. Во втором вы передаёте два аргумента, никакого превращения нет, и консоль показывает объект как есть, с возможностью раскрыть. Запятая вместо плюса — и отладка становится осмысленной.

9. Как превращать самому

Вывод из всего предыдущего один: не полагайтесь на молчаливое приведение — превращайте сами и на входе. Вот как:

КудаКак писатьКороткая запись
в числоNumber(x)+x
в строкуString(x)`${x}`
в логическоеBoolean(x)!!x

Длинные записи лучше коротких: их видно при чтении. Короткие надо уметь узнавать в чужом коде. И помните с дня 5: никогда не пишите new перед этими словами — получится объект-обёртка, а не примитив.

const raw = "42";            // из поля ввода

const num = Number(raw);     // сразу превратили
if (Number.isNaN(num)) {
  console.log("это не число");
}
// дальше по всей программе num — точно число
Правило, которое снимает девять из десяти вопросов про типы: приводите данные к нужным типам один раз, на границе программы — там, где они приходят от пользователя или с сервера. Внутри программы пусть ходят уже нормальные значения. Тогда все сегодняшние таблицы вам просто не понадобятся.

Что значит «на границе»

Сравните два подхода к одной задаче — посчитать стоимость заказа по данным из формы.

Приведение размазано
const qty = "3";
const price = "250";

const total =
  Number(qty) * Number(price);

if (Number(qty) > 10) {
  // скидка
}
console.log(Number(qty) + " шт.");
Приведение на границе
const qty = Number("3");
const price = Number("250");

const total = qty * price;

if (qty > 10) {
  // скидка
}
console.log(qty + " шт.");

Слева Number() написан трижды, и стоит забыть его в одном месте — появится тихая ошибка. Справа превращение сделано один раз, и дальше по всей программе qty гарантированно число.

Но «на границе» значит не только «превратить». Значит ещё и «проверить»: превращение может не удаться, и лучше узнать об этом сразу, а не в конце расчёта.

function toMark(input) {
  if (typeof input !== "string" || input.trim() === "") {
    return null;                       // пусто — сразу отказ
  }

  const mark = Number(input);

  if (Number.isNaN(mark)) {
    return null;                       // не число — отказ
  }
  return mark;                         // дальше идёт только настоящее число
}

console.log(toMark("4"));      // 4
console.log(toMark("  5  "));  // 5
console.log(toMark(""));       // null
console.log(toMark("пять"));   // null

Такую функцию пишут один раз и зовут везде, где приходят данные. Внутри остальной программы после неё не нужны ни Number.isNaN, ни проверки на пустоту — всё это уже сделано на входе. Ровно этот приём мы применим в «Табеле» в разделе 14.

Из таблицы следуют две вещи, которые стоит запомнить.

Первая: сравнения считаются позже арифметики. Значит, скобки вокруг них не нужны:

1 + 2 === 3 && 2 > 1;       // true — работает как ожидается
((1 + 2) === 3) && (2 > 1); // то же самое, просто длиннее

Вторая: присваивание почти в самом низу. Поэтому const total = a + b * c; сначала считает всё справа и только потом кладёт результат.

А вот случай, где про приоритет забывают чаще всего. typeof стоит на третьей строке таблицы — выше арифметики. Значит, он «хватает» только то, что стоит сразу за ним:

typeof 1 + 1;      // "number1"  ← не то, что кажется
typeof (1 + 1);    // "number"   ← вот так правильно

В первой строке сначала сработал typeof 1 и дал строку "number", а потом к этой строке приклеилась единица. Ошибка тихая: результат есть, он даже похож на правдоподобный, и никто не ругается.

То же правило действует для ! и унарного минуса: они забирают только соседнее значение, а не всё выражение. Если нужно применить их к результату — ставьте скобки.

Разбираем выражение по шагам

Посмотрим, как таблица работает на длинной строке. Пусть цена 100, берут 3 штуки, скидка 10, покупатель — участник программы:

price * count - discount > 200 && isMember

Видно закономерность, которую полезно запомнить вместо всей таблицы: сначала считается арифметика, потом сравниваются результаты, потом соединяется логика. Это ровно тот порядок, в котором вы бы рассуждали словами: «посчитай сумму, сравни с порогом, и если ещё и участник — тогда да».

Поэтому в 90% случаев скобки в условиях не нужны — язык и так делает то, что вы имели в виду. Остаются два места, где они обязательны: смесь && с || и всё, что связано с ??.

11. Скобки — это оператор

Круглые скобки в документации называются оператором группировки, и стоят они на самом верху таблицы. Их работа — сказать «считай сначала это», отменив обычный порядок:

2 + 3 * 4;      // 14 — умножение раньше
(2 + 3) * 4;    // 20 — скобки победили

Правило простое и действует всегда: скобки считаются первыми, изнутри наружу.

((2 + 3) * 4) - 1;   // сначала 2+3=5, потом 5*4=20, потом 20-1=19
Скобки бесплатны. Они не замедляют программу и не занимают памяти — движок разбирает их при чтении файла. Поэтому единственный аргумент против лишних скобок — «стало длиннее», а за них — «стало понятно». Ставьте, когда сомневаетесь вы или может засомневаться читатель. Особенно там, где смешаны && и ||.

12. Слева направо и справа налево

Приоритет отвечает на вопрос «что раньше» для разных операторов. А если операторы одинаковые? Тогда работает ассоциативность — направление, в котором они считаются.

Почти всё в языке считается слева направо:

10 - 5 - 2;     // 3 — это (10 - 5) - 2, а не 10 - (5 - 2)
"1" + 2 + 3;    // "123" — склеили, потом ещё раз склеили

Но три вещи из тех, что мы знаем, считаются справа налево:

2 ** 3 ** 2;    // 512 — это 2 ** (3 ** 2), день 6
a = b = 7;      // сначала b = 7, потом a = 7, день 6
!!x;            // сначала внутреннее !, потом внешнее

Отдельно — тернарный оператор: он тоже справа налево, и потому «лестница» из дня 7 работает без скобок:

score >= 90 ? "5" : score >= 75 ? "4" : "3";
// читается как: score >= 90 ? "5" : (score >= 75 ? "4" : "3")

13. Семь синтаксических ошибок

Все ошибки этого дня — синтаксические. Напомню главное свойство SyntaxError из дня 4: она возникает до выполнения, и из-за неё не работает весь файл целиком. Если кажется, что «скрипт не подключился», — сначала ищите красное сообщение в консоли.

Каждая — отдельным блоком: сломанная строка в комментарии, сообщение Chrome и то, как правильно. Сломанную строку можно вставить в консоль и увидеть сообщение самим.

// const x = 3px;   → SyntaxError: Invalid or unexpected token — имя сразу после числа
const x = "3px";    // так правильно: это текст
// const c = “текст”;   → SyntaxError: Invalid or unexpected token — «умные» кавычки
const c = "текст";      // прямые кавычки
// const s = "первая
// вторая";          → SyntaxError: Invalid or unexpected token — перенос внутри кавычек
const s = "первая\nвторая";   // перенос пишут знаком \n
// 3 = x;   → SyntaxError: Invalid left-hand side in assignment — слева не переменная
let y = 1;
y = 3;      // слева от = стоит переменная
// function f() {   → SyntaxError: Unexpected end of input — не закрыли фигурную скобку
function f() { }
// if true) { }   → SyntaxError: Unexpected token 'true' — нет открывающей скобки
if (true) { }
// console.log(1,,2);   → SyntaxError: Unexpected token ',' — лишняя запятая
console.log(1, 2);

Как и на дне 4, помните: на MDN эти страницы озаглавлены формулировками Firefox, а Chrome говорит иначе. Firefox, например, скажет «illegal character» и «unterminated string literal» — понятнее, но искать вы будете по тому, что видите у себя.

Вторая из семи ошибок — самая обидная и самая частая. Она случается, когда код копируют из мессенджера, из документа Word или с сайта, который «улучшает» кавычки: 
const a = "правильные прямые кавычки";
// const b = “умные кавычки из Word”;   → SyntaxError: Invalid or unexpected token
На вид разница почти незаметна, а файл не работает целиком. Ещё один довод за то, чтобы печатать код руками, а не копировать.

Как искать причину

У SyntaxError есть особенность: браузер показывает место, где он споткнулся, а не место ошибки. Иногда это одна и та же строка — например, если забыть закрыть кавычку, укажут прямо на неё. Но не всегда.

Самый неприятный случай — незакрытая фигурная скобка:

function greet(name) {          // ← скобку не закрыли ЗДЕСЬ, строка 1
  console.log("Салам, " + name);

const city = "Мары";
console.log(city);
// SyntaxError: Unexpected end of input — в файле из этих пяти строк покажут строку 6, сразу за последней

Движок читал файл, ждал закрывающую скобку и дошёл до конца, так и не дождавшись. Сообщить он может только про то место, где кончился текст, — то есть про последнюю строку. А настоящая ошибка на первой.

Отсюда два приёма поиска. Первый: сообщение Unexpected end of input почти всегда означает незакрытую скобку — ищите её сверху, а не в указанной строке. Второй: следите за отступами. Если в редакторе код внезапно «уехал» вправо и не вернулся — там и не закрыли блок. Редактор подсвечивает парные скобки: поставьте курсор на открывающую и посмотрите, где её пара.

Общее правило: указанная строка — это конец поиска, а не начало. Смотрите на неё и выше. И проверяйте парность: каждой ( нужна ), каждой { — }, каждой кавычке — такая же кавычка.

Как их не делать

Синтаксические ошибки — единственный вид ошибок, который почти полностью лечится привычками и настройкой редактора. Четыре вещи, которые стоит завести прямо сегодня.

Закрывайте скобку сразу. Напечатали ( — тут же напечатайте ), и только потом пишите внутри. То же с кавычками и фигурными скобками. VS Code делает это сам, но привычка важнее настройки: она работает и в чужом редакторе, и в поле ввода на сайте.

Следите за отступами. Ровные отступы — не украшение, а способ увидеть незакрытый блок глазами. В VS Code есть автоформатирование (Shift + Alt + F): если после него код «уехал» вправо и не вернулся — там и потеряна скобка.

Не копируйте код из мессенджеров и документов. Кавычки, тире и пробелы там подменяются на похожие, но другие символы. Это та самая вторая из семи ошибок.

Сохраняйте и смотрите в консоль почаще. Одна ошибка в файле из двадцати строк ищется за минуту, в файле из двухсот — за полчаса. Чем короче промежуток между «написал» и «проверил», тем меньше места, где искать.

14. «Табель»: чистим ввод

Соберём день в программе. Вчера мы отбрасывали негодные оценки; сегодня научимся принимать их в том виде, в каком они приходят из формы, — строками.

const MIN_MARK = 2;
const MAX_MARK = 5;

// так данные приходят из полей ввода: всё строки, и кое-что пустое
const raw = ["5", "4", "", "  3  ", "пять", "9", "5"];

const marks = [];
const rejected = [];

for (const item of raw) {
  if (item.trim() === "") {          // пусто — проверяем ДО превращения
    rejected.push(`пусто`);
    continue;
  }

  const mark = Number(item);

  if (Number.isNaN(mark)) {
    rejected.push(`"${item}" не число`);
  } else if (mark < MIN_MARK || mark > MAX_MARK) {
    rejected.push(`${mark} вне диапазона`);
  } else {
    marks.push(mark);
  }
}

console.log("Приняты:", marks);
console.log("Отброшены:", rejected);
Приняты: (4) [5, 4, 3, 5]
Отброшены: (3) ['пусто', '"пять" не число', '9 вне диапазона']

Три места стоит разобрать.

item.trim() === "" — проверка на пустоту до превращения. Без неё пустая строка стала бы честным нулём, прошла бы Number.isNaN и упёрлась бы в проверку диапазона с непонятным сообщением «0 вне диапазона». Метод trim убирает пробелы по краям; разберём его на дне 16.

Number(" 3 ") даёт 3 — пробелы по краям язык отбрасывает сам. Поэтому оценка с лишними пробелами принимается, и это правильно: пользователь не виноват, что нажал пробел.

Порядок проверок. Сначала пустота, потом «не число», потом диапазон. Каждая следующая проверка рассчитывает, что предыдущая уже отсеяла свой случай. Поменяйте их местами — и сообщения станут врать.

Уберите проверку item.trim() === "" и запустите. Пустая строка попадёт в «вне диапазона» вместо «пусто». Затем попробуйте добавить в массив "0" и " " — и проверьте, что программа скажет про каждое.

  1. Почему "0" == 0 и "" == 0 истинны, а "0" == "" — нет?
    Ответ В первых двух парах типы разные, поэтому обе строки превращаются в число, и обе дают 0. В третьей паре типы совпали, приводить нечего, и строки сравниваются посимвольно.
  2. Что вернёт Number("") и чем это опасно?
    Ответ 0, а не NaN. Опасно тем, что пустое поле ввода даст честный ноль и пройдёт проверку Number.isNaN. Проверять пустоту надо до превращения.
  3. Чему равны [5] + 1 и [5] - 1 и почему по-разному?
    Ответ "51" и 4. Массив в обоих случаях становится строкой "5", но + видит строку и склеивает, а - строк не понимает и превращает её в число.
  4. Чему равно 2 ** 3 ** 2 и почему не 64?
    Ответ 512. Степень считается справа налево, то есть 2 ** (3 ** 2) = 2 ** 9. Для 64 нужны скобки: (2 ** 3) ** 2.
  5. В консоли SyntaxError на строке 12, но там всё верно. Где искать?
    Ответ Выше. Браузер показывает место, где разбор споткнулся, а не место ошибки. Проверьте предыдущую непустую строку и парность скобок и кавычек.
