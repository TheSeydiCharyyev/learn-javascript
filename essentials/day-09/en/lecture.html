1. Branching

For eight days the program went from top to bottom without turning anywhere. We have already used conditions — since day 3 — but we have never covered them seriously. It is time.

Branching is a fork: the program looks at a condition and chooses which road to take. Everything we learned in the last two days — comparisons, logic, truthiness — exists for this moment.

The main thing in this picture is that exactly one branch runs, and after it the program goes on as if nothing had happened. Branching does not create two programs, it chooses a path.

2. The if statement

The simplest form has one branch:

const mark = 5;

if (mark === 5) {
  console.log("excellent!");
}

console.log("we go on in any case");

Let us take it apart:

PartWhat it is
ifa keyword
( ... )parentheses — required
mark === 5the condition: any expression
{ ... }the block from day 4: what to do if it is true

Notice: no semicolon is needed after the closing curly brace. It is a common habit of beginners, and although there will be no error, people do not write it like this:

if (mark === 5) {
  console.log("excellent!");
};   // ← an extra semicolon, this is the empty statement from day 4

But here is where a semicolon breaks everything — right after the parentheses. We saw this trap on day 4 with a loop, and with if it works exactly the same way:

const mark = 2;

if (mark === 5);          // ← the condition ended here!
{
  console.log("excellent!");   // runs ALWAYS
}

The semicolon became the body of the condition — an empty statement that “does nothing”. And the block below turned out to be an ordinary block from day 4, which simply runs in order. No error, no message: “excellent!” is printed even for a two.

Both traps — this one and the one with indentation (section 4) — are caught by one habit: type if (…) { } in full, and only then write inside. Then neither an extra semicolon nor lost braces have anywhere to come from.

The condition in parentheses is any expression, not necessarily a comparison. Here are the forms you meet most often:

if (mark === 5) { }            // a comparison
if (mark >= 2 && mark <= 5) { } // a compound condition
if (isReady) { }               // a variable with a boolean value
if (marks.length) { }          // a number: 0 is false, the rest is true
if (!user) { }                 // a negation
if (getScore() > 50) { }       // the result of a function call

3. else and the else if ladder

The second branch is added with the word else — “otherwise”:

if (mark >= 3) {
  console.log("passed");
} else {
  console.log("retake");
}

else has no condition of its own: it works every time the if did not. That is why it is the last one and the only one.

And if there are more than two branches? Then else if is put between them:

if (mark === 5) {
  console.log("excellent");
} else if (mark === 4) {
  console.log("good");
} else if (mark === 3) {
  console.log("satisfactory");
} else {
  console.log("unsatisfactory");
}
There is no separate word elif as in Python — and else if is not one construct but two. We talked about this on day 3: it is an else with a single if inside it. It is just more convenient to write it on one line than with an indent: 
// what the engine actually sees
if (mark === 5) {
  // ...
} else {
  if (mark === 4) {
    // ...
  }
}
Knowing this is useful for one reason: a ladder is checked from top to bottom, and the first branch that matches cancels all the others.

4. Why we always put braces

Formally, if a branch has one statement, the curly braces can be left out:

const mark = 5;

if (mark === 5) console.log("excellent");

It works. But you should not do this, and here is why. Let us add a second line:

const mark = 3;

if (mark === 5)
  console.log("excellent");
  console.log("well done!");   // ← runs ALWAYS
The second line is not part of the condition. Without braces if takes exactly one statement — the first one. Everything else simply follows. The indentation fools the eye: the code looks right but works differently. No error, no message — “well done!” is simply printed for a student with a three.

The rule of the course: we always put curly braces, even for one line. This is also the recommendation of the MDN documentation itself. Two extra braces today are an hour of debugging saved a month later.

if (mark === 5) {
  console.log("excellent");
  console.log("well done!");   // now both lines are in the branch
}

There is one exception — an early exit on one line: if (score >= 90) return "5";. You will meet it in section 7, and from day 12 on it will come up often. The condition and return stand on one line, and the indentation will not fool anyone.

5. What counts as a condition

Any expression can stand in the parentheses, not necessarily a comparison. The language will turn it into “yes” or “no” by the rule from day 5:

There are six falsy values: false, 0 (zero in any form: both -0 and 0n), "", NaN, null, undefined. Everything else is truthy — including "0", " ", [] and { }. 
const name = "Aman";
const marks = [5, 4];

if (name) {                  // the string is not empty — true
  console.log(`Hello, ${name}`);
}

if (marks.length) {          // 0 is false, so “if the array is not empty”
  console.log("there are marks");
}

The second technique — if (marks.length) — is very common. It reads as “if the length is not zero”. But be careful: the short form works only where zero really means “empty”. We covered this on day 5 with the example of age.

A short check or an exact one

Since anything can be put into a condition, a question arises: write it short or explicitly? Compare two functions — they differ in one line:

Short
function show(count) {
  if (count) {
    return `showing ${count}`;
  }
  return "nothing to show";
}
Exact
function show(count) {
  if (count !== undefined) {
    return `showing ${count}`;
  }
  return "nothing to show";
}

On most values they behave the same. But not on all of them:

countif (count)if (count !== undefined)
5showing 5showing 5
0nothing to showshowing 0
""nothing to showshowing
undefinednothing to shownothing to show

The difference is in the row with zero — the same one that brought the ?? operator on day 7. The question is always the same: are zero and the empty string “no data” or legitimate data?

The rule of choice. The short check if (x) is good where all six falsy values suit you at once: a non-empty string, a non-empty array, “the flag is raised”. An exact check is needed when zero, the empty string or false are meaningful values: a counter, a temperature, a coordinate, the answer “no”. In doubt, write it exactly: it is longer, but the reader sees what exactly you are checking.
A separate trap from day 5, which the documentation also warns about. The wrapper object new Boolean(false) behaves like true in a condition, and like false in a comparison: 
const b = new Boolean(false);

if (b) { }           // it goes in here — the object is truthy
if (b == true) { }   // but not here — the comparison unwraps the wrapper
One more argument for not writing new before Boolean, Number and String.

6. The order of branches decides

Since a ladder is checked from top to bottom and stops at the first branch that fits, the order of the conditions becomes part of the logic. Look:

Wrong
if (score >= 50) {
  grade = "3";
} else if (score >= 75) {
  grade = "4";
} else if (score >= 90) {
  grade = "5";
}

With 95 points the first branch will work, and a top student will get a three. The two lower ones will never work.

Right
if (score >= 90) {
  grade = "5";
} else if (score >= 75) {
  grade = "4";
} else if (score >= 50) {
  grade = "3";
}

First the narrowest condition, then wider and wider. Each branch catches only what the upper ones did not catch.

The rule for a ladder with ranges: the strictest condition goes on top. If branches overlap, the higher one wins.

The mistake is easy to miss, because the program does not crash and even works correctly on part of the data — with 60 points both versions give a three.

Checking at the boundaries

Hence a technique worth making a habit right now. Conditions break at the edges of ranges, not in the middle. So you should check them not on random numbers but on three values around each boundary: on the boundary itself, one less and one more.

For a ladder with the thresholds 90 and 75 these are six checks:

console.log(grade(89), grade(90), grade(91));   // around the first boundary
console.log(grade(74), grade(75), grade(76));   // around the second one

Such a set immediately catches the two most common mistakes in conditions.

The first is a mixed-up sign. You wrote > instead of >=, and exactly 90 points stopped being a five. In the middle of the range there is no difference, on the boundary there is.

The second is a hole between branches. If the upper branch catches > 90 and the lower one < 90, the value 90 itself will not get anywhere:

if (score > 90) {
  grade = "5";
} else if (score < 90) {
  grade = "4";
}
// with score === 90 the variable grade stays undefined
The technique works not only with numbers. For strings the boundaries are the empty string and a string of spaces only. For arrays — an empty array and an array of one element. For any input — null and undefined. Mistakes live at the edges; in the middle everything usually works anyway.

7. Nested conditions and how to avoid them

A condition inside a condition is a common thing:

if (isLoggedIn) {
  if (hasTicket) {
    console.log("come in");
  }
}

But when there are three or four such levels, the code drifts to the right and stops being readable. This even has a name — the “pyramid of doom”. Here are three ways to straighten it out.

The first: join the conditions with &&, if there is no separate else inside:

if (isLoggedIn && hasTicket) {
  console.log("come in");
}

The second: exit early. First filter out everything bad, and leave the useful work at the end, without nesting:

Nested
function check(mark) {
  if (mark !== undefined) {
    if (mark >= 2) {
      if (mark <= 5) {
        return "valid";
      }
    }
  }
  return "invalid";
}
With an early exit
function check(mark) {
  if (mark === undefined) {
    return "invalid";
  }
  if (mark < 2 || mark > 5) {
    return "invalid";
  }
  return "valid";
}

On the right the code reads from top to bottom like a list of rules: “no mark — refuse; out of range — refuse; otherwise valid”. On the left you have to keep three open braces in your head. The technique is called early return, and we will come back to it on day 12, when we cover functions.

The third way: give the condition a name. When the condition itself is long, nesting is sometimes not the problem at all — what gets in the way is that there is too much in one line:

Everything in the condition
if (user !== null
    && user.age >= 18
    && user.ticket !== null
    && !user.banned) {
  console.log("come in");
}
By names
const exists = user !== null;
const isAdult = exists && user.age >= 18;
const hasTicket = exists && user.ticket !== null;

if (isAdult && hasTicket && !user.banned) {
  console.log("come in");
}

On the right there are more lines, but each one answers one question, and the condition in if can be read out loud. Plus debugging becomes simple: you can print any flag to the console and see which one exactly did not work. With a long condition you would have to guess.

Notice exists && in two lines — this is the short-circuit evaluation from day 7. Without it, user.age on an empty user would give a TypeError.

Three typical tasks

Conditions at work almost always look the same. Here are three forms that cover most cases — it is worth recognizing them on sight.

Checking data: a chain of refusals. Each rule is a separate if with an early exit, and the order goes from the roughest to the finest:

function validate(name, age) {
  if (name.trim() === "") {
    return "enter a name";
  }

  const n = Number(age);

  if (Number.isNaN(n)) {
    return "age must be a number";
  }
  if (n < 0 || n > 120) {
    return "check the age";
  }
  return "";                   // an empty string = all is well
}

Notice: Number(age) stands between the checks, not at the top. First we filtered out an empty name, then converted the age, then checked the result of the conversion — exactly the “at the boundary” technique from day 8.

Choosing by range: a ladder from top to bottom. The biggest value first, and each next branch catches the rest:

function discount(total) {
  if (total >= 5000) {
    return 15;
  }
  if (total >= 2000) {
    return 10;
  }
  if (total >= 1000) {
    return 5;
  }
  return 0;
}

Here else is not needed at all — return exits the function anyway. Such code is shorter than a ladder with else if and reads like a table of rates.

A complex condition: move it into a flag. When a check no longer fits in a line, it is given a name — we talked about this on day 7:

const isWeekend = day === "Sat" || day === "Sun";
const isHoliday = date === "01.01";

if (isWeekend || isHoliday) {
  console.log("day off");
}
A trap that hides in the first two forms. If a function has no last branch for “everything else”, it silently returns undefined: 
function grade(score) {
  if (score >= 90) return "5";
  if (score >= 75) return "4";
  // and what if it is 50?
}

grade(95);   // "5"
grade(50);   // undefined ← and it will go on through the program
Remember day 5: undefined does not crash, it just quietly travels on and breaks something in another place. Always close a ladder with a last branch.

8. The switch statement

When there are many branches and all of them compare one and the same value with different options, an else if ladder starts to repeat itself:

if (mark === 5) { word = "excellent"; }
else if (mark === 4) { word = "good"; }
else if (mark === 3) { word = "satisfactory"; }
else if (mark === 2) { word = "unsatisfactory"; }

The word mark is written four times, and so is ===. For such cases there is switch:

switch (mark) {
  case 5:
    word = "excellent";
    break;
  case 4:
    word = "good";
    break;
  case 3:
    word = "satisfactory";
    break;
  case 2:
    word = "unsatisfactory";
    break;
  default:
    word = "unknown";
}

How it works: the value in parentheses is compared in turn with each case, and control passes to the first one that matches. If none matches, it goes to default.

switch compares strictly, with ===. No type conversions, as with ==: 
switch ("1") {
  case 1:  console.log("number");  break;  // will not work
  case "1": console.log("string"); break;  // this one
}
This is good news: yesterday’s conversion tables are not needed here. But remember that a value from an input field is a string, and case 5 will not work for it.

Where switch fits especially well

The classic case is handling a command. The user pressed a button, typed a word, a message arrived — and you need to choose what to do. There are many options, all of them specific:

function runCommand(cmd, list) {
  switch (cmd) {
    case "add":
      list.push("new task");
      return `added, ${list.length} in total`;

    case "clear":
      list.length = 0;
      return "the list is cleared";

    case "count":
      return `tasks: ${list.length}`;

    case "help":
    case "?":
      return "commands: add, clear, count";

    default:
      return `unknown command "${cmd}"`;
  }
}

You can see right away the three things for which switch was taken here. The list of commands reads like a table of contents — one line per option. Two commands, "help" and "?", are handled together through grouping. And default catches everything unfamiliar instead of staying silent.

A similar choice by string will come up on day 29 in the mini project “To-do list”: the filter buttons send the strings "all", "active" and "done", and the program decides which tasks to show.

9. break and fall-through

The word break means “exit the switch”. And here is the main oddity of this construct: if you forget break, execution does not stop but continues into the next branch — even if it does not fit.

This is called fall-through.

const action = "draw";

switch (action) {
  case "draw":
    console.log("drawing");
    // forgot break!
  case "eat":
    console.log("eating");
    // and forgot it here too
  default:
    console.log("nothing");
}
// prints all three lines: drawing, eating, nothing

Here is the key to understanding switch: a case is not a branch but an entry label. A match says from which line to start, and then the code runs in order until it meets break or the switch ends.

So the rule is simple: put break in every branch. The last branch does not need it — there is nowhere further to fall. But if you add a branch below it, do not forget to put break into the one that used to be last.

There is one word break in the language, but it works in two places, and it always means “exit the nearest construct”. In switch — exit the switch. In a loop (tomorrow, day 10) — exit the loop. And if a switch stands inside a loop, a break inside it exits only the switch, and the loop goes on. This surprises people regularly.

There is also a third way to exit a switch — return, if the whole switch stands inside a function. It exits the function right away, so no break is needed after it. The program in section 14 is written this way, and you will meet this form often.

10. Fall-through as a technique

Sometimes fall-through is needed on purpose — when several values are handled the same way. Then the case labels are put in a row, with no code between them:

switch (day) {
  case "Sat":
  case "Sun":
    console.log("day off");
    break;
  default:
    console.log("working day");
}

Here case "Sat" has no code of its own, so execution falls through into case "Sun" — and both options end up on one line. This is a legitimate and common technique, the only case where fall-through is used on purpose.

When fall-through is intentional but there is some code between the case labels, be sure to leave a comment: 
switch (mark) {
  case 5:
    excellent++;
  // intentional fall-through: a five also counts as passed
  case 4:
  case 3:
    passed++;
    break;
}
Otherwise any reader, including you, will decide that you forgot break, and will “fix” it.

11. Three traps of switch

The first: all the branches live in one scope. A separate case has no curly braces, so the whole switch is one block:

switch (x) {
  case 1:
    let a = 1;
    break;
  case 2:
    let a = 2;   // SyntaxError: Identifier 'a' has already been declared
    break;
}

It is cured by giving the branch its own braces — and this is exactly that block from day 4:

const x = 2;

switch (x) {
  case 1: {
    let a = 1;
    break;
  }
  case 2: {
    let a = 2;   // now a different scope, all is fine
    break;
  }
}

The second: default does not have to be last. By tradition it is written at the bottom, but the language allows it anywhere — and then it works only if nothing matched, and execution starts from its line. Do not use this: always put default last.

The third: ranges cannot be checked with switch. case compares with a specific value, not with a condition. For “90 and above” you need an else if ladder.

Always write default

Formally default is optional: if nothing matched and there is no default, switch simply does nothing. That is exactly why it is worth writing — silence is the most dangerous thing here.

function markToWord(mark) {
  switch (mark) {
    case 5: return "excellent";
    case 4: return "good";
  }
}

markToWord(3);   // undefined — and it will travel on through the program

This is the same hole as in a ladder without a last branch, only hidden better. Add default — and an unfamiliar value will announce itself right away, at least with the word “unknown”.

12. What to choose: if or switch

TaskWhat to write it with
one check, two branchesif...else
ranges: “greater”, “less”, “from … to”an else if ladder
a complex condition with && and ||if
one value, many specific optionsswitch
several values are handled the same wayswitch with grouping
you need to choose a value, not perform actionsthe ternary operator (day 7)

A short rule: switch — when you compare one variable with enumerable options. In all other cases, if.

You can check yourself like this: try rewriting the code with the other construct. If it turns out worse, the choice was right.

A ladder instead of switch
if (cmd === "add") {
  add();
} else if (cmd === "remove") {
  remove();
} else if (cmd === "clear") {
  clear();
} else {
  unknown();
}

cmd === is repeated three times. A switch is asking to be used.

switch instead of a ladder
switch (true) {
  case score >= 90:
    grade = "5";
    break;
  case score >= 75:
    grade = "4";
    break;
}

Formally it works, but switch (true) is a trick for connoisseurs. A ladder is asking to be used.

The switch (true) technique really exists: since the comparison goes through ===, and score >= 90 gives true, a match is found. The MDN documentation shows it as a legitimate replacement for a ladder. But the reader has to puzzle out the trick instead of reading the logic, so we do not use it in the course.

There is also a third option that we will come to later: when there really are many options and they simply map a value to a value, a lookup object is taken instead of switch. That is day 21 — for now remember that a long switch made of nothing but return often means the data is asking to be put into a table.

13. A couple of words about try...catch

The guide chapter this day is built on is called “Control flow and error handling”. We will cover its second half — try, catch, throw — on day 11, together with iterating values.

For now it is enough to know that this is branching too, just of a special kind: “try to do this, and if it breaks — do that”.

const text = "{ broken";

try {
  const data = JSON.parse(text);   // what if the text is broken
} catch (e) {
  console.error("could not parse:", e);
}

How this differs from an ordinary if is worth understanding already today. In if you know in advance what to check: there is a condition, there are two roads. In try...catch there is no condition — you say “do it”, and the catch branch works only if something broke along the way.

if...elsetry...catch
what makes the choiceyour conditionan error while running
when it is knownbefore runningonly after the fact
what it is forthe ordinary logic of the programthings that may fail

A rule worth remembering in advance: try...catch is not a replacement for checks. What can be checked with a condition is checked with a condition. try is taken for things that cannot be checked: parsing someone else’s data, a request to a server, working with a file.

const total = 10;
const count = 0;

// bad: hiding something checkable inside try
try {
  const half = total / count;
} catch (e) { }

// good: checking with a condition
if (count > 0) {
  const half = total / count;
}

Besides, the second example is more honest: division by zero in JavaScript does not throw an error at all, it quietly gives Infinity — as we covered on day 5. The catch here would never work.

14. The “Report card”: marks in words

Let us use both tools in one program: switch to turn a digit into a word, an else if ladder for a verdict by range.

const MIN_MARK = 2;
const MAX_MARK = 5;

const marks = [5, 4, 5, 3, 5, 4];

function markToWord(mark) {
  switch (mark) {
    case 5:
      return "excellent";
    case 4:
      return "good";
    case 3:
      return "satisfactory";
    case 2:
      return "unsatisfactory";
    default:
      return "unknown";
  }
}

let sum = 0;
let excellent = 0;
let failed = 0;

for (const mark of marks) {
  sum += mark;

  if (mark === MAX_MARK) {
    excellent++;
  } else if (mark === MIN_MARK) {
    failed++;
  }
}

const average = sum / marks.length;

let verdict;
if (average >= 4.5) {
  verdict = "top student";
} else if (average >= 3.5) {
  verdict = "good student";
} else if (average >= 2.5) {
  verdict = "average student";
} else {
  verdict = "needs work";
}

console.log(`Average: ${average.toFixed(2)} — ${verdict}`);
console.log(`Fives: ${excellent}, twos: ${failed}`);

for (const mark of marks) {
  console.log(`${mark} — ${markToWord(mark)}`);
}
Average: 4.33 — good student
Fives: 3, twos: 0
5 — excellent
4 — good
5 — excellent
3 — satisfactory
5 — excellent
4 — good

Notice two things.

There is not a single break in markToWord — and this is not a mistake. Instead there is return, which exits not only the switch but the whole function at once. This is a common way to write it: when every branch returns something, break is simply not needed. We will cover functions on day 12.

The verdict is written as a ladder, not with switch — because here there are ranges, not specific values. Exactly the split that the table above talks about. And the order of the branches goes from the strictest condition down.

Two experiments with this program.

The first. Replace the marks with [5, 5, 4, 5] first — the average is 4.75, the verdict is “top student”. Then swap the first two branches of the verdict — >= 4.5 and >= 3.5. Run it and explain why the top student became a good student.

The second. Rewrite markToWord so that instead of return it puts the answer into a variable and exits with break. Then remove one break and see what happens to the answer for that mark.

const mark = 4;
const day = "Sat";
let word;

if (mark === 5) {
  word = "excellent";        // one branch
}

if (mark >= 3) {
  word = "passed";           // true
} else {
  word = "retake";           // false
}

// a ladder: the strictest condition on top
if (mark === 5) {
  word = "excellent";
} else if (mark === 4) {
  word = "good";
} else {
  word = "other";
}
word;                        // "good"

// we put braces ALWAYS — without them only one line gets into the branch
// the exception is an early exit on one line: if (x) return y;

// any expression can be a condition; falsy are only:
// false 0 "" NaN null undefined

switch (mark) {
  case 5:
    word = "excellent";
    break;                   // forgot it — it falls through further!
  case 4:
    word = "good";
    break;
  default:
    word = "unknown";
}
word;                        // "good"

switch (day) {
  case "Sat":
  case "Sun":                // grouping: shared code for two values
    word = "day off";
    break;
  default:
    word = "working day";
}
word;                        // "day off"

// switch compares with === , without type conversion
// the whole switch is ONE block:
// case 1: let a = 1; break; case 2: let a = 2;
//   → SyntaxError: Identifier 'a' has already been declared
// need let in a branch? give the case its own { }

// switch  — one value, enumerable options
// else if — ranges and complex conditions
// ? :     — choose a value, not perform actions
  1. Why does only one line get into a branch without curly braces?
    Answer Because if takes exactly one statement. The block from day 4 is a way to make one statement out of several. Without it, the second line simply follows and always runs.
  2. What does a switch print if you forget break in the matching branch?
    Answer Everything that comes after it, up to the first break or the end of the switch — including default, even if it does not fit. A case is an entry label, not a separate branch.
  3. Why is the ladder if (score >= 50) ... else if (score >= 90) wrong?
    Answer A ladder is checked from top to bottom and stops at the first branch that fits. With 95 points the first one works, and the second one is never reached. The strictest condition must be on top.
  4. Why does let a in two case labels give a SyntaxError?
    Answer A separate case has no curly braces of its own, so the whole switch is one block, and it has two declarations with the same name. It is cured by giving each branch its own { }.
  5. When should you take switch, and when an else if ladder?
    Answer switch — when you compare one variable with specific enumerable values. A ladder — when you need ranges, complex conditions with && and ||, or a comparison of different quantities.
