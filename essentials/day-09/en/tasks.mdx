# Day 9. Tasks

<Subtitle>Lessons 2 and 3, 90 minutes. Warm-up — 20 minutes, main tasks — 50 minutes, starred tasks — 20 minutes. Tasks 1–3 are done in the console, the rest in the folder `day-09`.</Subtitle>

## Warm-up

<Task title="1. The first fork" level="easy" time="6">
<Goal>write `if` and `else` with your own hands.</Goal>

For each task write a condition with two branches and check it on two values:

- whether a number is even or odd;
- whether a string is empty or not;
- whether an age is 18 or more, or less.

<Hint>
Parity — with the remainder from day 6: `n % 2 === 0`.
</Hint>

<Criteria>
- three conditions are written, each one has both branches;
- each one is checked on two values;
- curly braces are everywhere;
- there is no semicolon after a closing brace anywhere.
</Criteria>
</Task>

<Task title="2. First predict: what will run" level="easy" time="7">
<Goal>catch the trap with curly braces and the order of branches.</Goal>

Predict the output of each fragment, then check.

```js
// A
const mark = 3;
if (mark === 5)
  console.log("excellent");
  console.log("well done!");

// B
const score = 95;
if (score >= 50) {
  console.log("a three");
} else if (score >= 90) {
  console.log("a five");
}

// C
const list = [];
if (list) {
  console.log("there is a list");
}
if (list.length) {
  console.log("there is something in the list");
}
```

<Criteria>
- the predictions are written down before the check;
- it is explained why fragment A prints “well done!”;
- it is explained why in fragment B a top student got a three;
- it is explained why in fragment C one line out of two worked.
</Criteria>
</Task>

<Task title="3. Fall-through in switch" level="easy" time="7">
<Goal>see with your own eyes what a forgotten `break` does.</Goal>

Type it in and run it. Write down the output. Then add `break` to every branch
and run it again.

```js
const action = "draw";

switch (action) {
  case "draw":
    console.log("drawing");
  case "eat":
    console.log("eating");
  default:
    console.log("nothing");
}
```

<Criteria>
- the output before and after adding `break` is written down;
- it is explained why `default` ran although the value matched
  the first `case`;
- it is written down what the same program prints with `action = "eat"`
  without `break`;
- what a `case` is is put in your own words.
</Criteria>
</Task>

## Main tasks

<Task title="4. A mark from points" level="medium" time="12">
<Goal>build a ladder and check it at the boundaries.</Goal>

Write `grade(score)`: 90 and above — “5”, 75 and above — “4”, 50 and above — “3”,
otherwise “2”. Check it on **nine** values — three around each boundary:

```js
49  50  51    74  75  76    89  90  91
```

Then break the function on purpose: change one `>=` to `>`
and find which of the nine values changed its answer.

<Criteria>
- all nine values give the right mark;
- the ladder is closed with a last branch — there is no `undefined`;
- after the damage exactly one changed value is found;
- it is written down why the other eight did not change.
</Criteria>
</Task>

<Task title="5. A command menu" level="medium" time="13">
<Goal>apply `switch` where it really fits.</Goal>

Write `runCommand(cmd, list)`, where `list` is an array of tasks:

- `"add"` — add a task, return “added, N in total”;
- `"count"` — return “tasks: N”;
- `"clear"` — empty the list, return “the list is cleared”;
- `"help"` and `"?"` — the same answer with the list of commands;
- anything else — “unknown command "…"”.

<Hint>
Two commands with the same answer are `case` grouping, not a copy of the code.
You can empty an array like this: `list.length = 0;`.
</Hint>

<Criteria>
- all five options work;
- “help” and “?” are done with grouping, the code is not duplicated;
- there is a `default`, and it shows the unknown command itself;
- the sequence is checked: count → add → count → clear → count.
</Criteria>
</Task>

<Task title="6. Untangle the nesting" level="medium" time="13">
<Goal>turn a ladder of nested conditions into a flat list of rules.</Goal>

Rewrite this function in **two** ways: by joining the conditions
and with an early exit. The behavior must not change.

```js
function canEnter(user) {
  if (user !== null) {
    if (user.age >= 18) {
      if (user.ticket !== null) {
        if (!user.banned) {
          return "come in";
        }
      }
    }
  }
  return "refused";
}
```

Check both versions on five cases: all is fine, a child, without a ticket, banned,
`null`.

<Criteria>
- both versions are written and give the same answer in all five cases;
- the early-exit version has no nesting at all;
- it is written down which version you would keep and why;
- it is explained why `user !== null` must be checked first.
</Criteria>
</Task>

<Task title="7. The “Report card”: marks in words" level="medium" time="12">
<Goal>use both tools in one program, each for its purpose.</Goal>

Copy the folder `day-08` to `day-09` and improve the “Report card”:

- `markToWord(mark)` with `switch`: 5 — “excellent”, 4 — “good”,
  3 — “satisfactory”, 2 — “unsatisfactory”, otherwise — “unknown”;
- the verdict by the average — with an `else if` ladder, four branches;
- counting fives and twos with `if...else if`;
- printing each mark as a word.

<Criteria>
- all four items work;
- `switch` is used for specific values, the ladder for ranges;
  it is written down why exactly so;
- the verdict is checked at the boundaries: sets of marks that give exactly 4.5 and exactly 3.5;
- `markToWord` has a `default`.
</Criteria>
</Task>

## Starred tasks

<Task title="8. A hole between branches" level="hard" time="10">
<Goal>find a value that does not get anywhere.</Goal>

In each function there is a value for which it returns `undefined`.
Find it, explain it and fix it.

```js
function a(score) {
  if (score > 90) return "5";
  if (score < 90) return "4";
}

function b(mark) {
  if (mark >= 4) return "good";
  else if (mark <= 2) return "bad";
}

function c(age) {
  if (age > 0 && age < 18) return "child";
  if (age > 18) return "adult";
}
```

<Hint>
Check at the boundaries. For the first function 89, 90 and 91 are interesting; in the second
and the third, find the boundaries yourself.
</Hint>

<Criteria>
- for each function all the problem values are found;
- for function `c` more than one such value is found;
- all three are fixed and checked at the boundaries;
- a rule for not letting such holes happen is put into words.
</Criteria>
</Task>

<Task title="9. Five traps" level="hard" time="10">
<Goal>bring together everything that behaves unexpectedly today.</Goal>

For each fragment **first** write down a prediction, then check it
and explain the difference in one sentence.

```js
// 1
switch ("5") {
  case 5: console.log("number"); break;
  case "5": console.log("string"); break;
  default: console.log("nothing");
}

// 2
switch (1) {
  case 1: let a = 1; break;
  case 2: let a = 2; break;
}

// 3
const b = new Boolean(false);
if (b) { console.log("entered the if"); }
if (b == true) { console.log("entered the comparison"); }

// 4
let x = 5;
if (x = 0) { console.log("entered"); }
console.log(x);

// 5
if ([]) { console.log("an empty array is truthy"); }
if ([] == false) { console.log("and it equals false"); }
```

<Hint>
One fragment will not run at all — and it will break **the whole file**, not only
itself. Find it first and move it into a separate file, otherwise you will not be able to check the others.
</Hint>

<Criteria>
- the predictions are written down before running;
- the fragment with a `SyntaxError` is found, the text of the error and its cause are written down;
- for the other four the cause is named: strict comparison in `switch`,
  a wrapper object, assignment instead of comparison, the truthiness of objects;
- fragments 2 and 4 are rewritten so that they do what is expected of them;
- it is explained why fragment 5 prints both lines.
</Criteria>
</Task>
