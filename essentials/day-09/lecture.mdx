## 1. Ветвление {#why}

Восемь дней программа шла сверху вниз, не сворачивая. Мы уже пользовались условиями —
с третьего дня, — но ни разу не разбирали их всерьёз. Пора.

**Ветвление** — это развилка: программа смотрит на условие и выбирает, по какой
дороге пойти. Всё, что мы учили последние два дня — сравнения, логика, истинность, —
существует ради этого момента.

<Scheme src="scheme-why.svg">Дороги расходятся и тут же сходятся: выполнится ровно одна ветка</Scheme>

Главное в этой картинке — **выполнится ровно одна ветка**, и после неё программа
продолжится как ни в чём не бывало. Ветвление не создаёт двух программ, оно выбирает путь.

## 2. Инструкция if {#if}

Самая простая форма — одна ветка:

```js
const mark = 5;

if (mark === 5) {
  console.log("отлично!");
}

console.log("дальше идём в любом случае");
```

Разберём по частям:

| Часть | Что это |
| --- | --- |
| `if` | ключевое слово |
| `( ... )` | круглые скобки — **обязательны** |
| `mark === 5` | условие: любое выражение |
| `{ ... }` | блок из дня 4: что делать, если истина |

Обратите внимание: **после закрывающей фигурной скобки точка с запятой не нужна**.
Это частая привычка новичков, и хотя ошибки не будет, так не пишут:

```js
if (mark === 5) {
  console.log("отлично!");
};   // ← лишняя точка с запятой, это пустая инструкция из дня 4
```

А вот где точка с запятой **ломает всё** — сразу после круглых скобок.
Мы видели эту ловушку на дне 4 с циклом, и с `if` она работает точно так же:

```js
const mark = 2;

if (mark === 5);          // ← условие кончилось здесь!
{
  console.log("отлично!");   // выполнится ВСЕГДА
}
```

Точка с запятой стала телом условия — пустой инструкцией «ничего не делать». А блок ниже
оказался обычным блоком из дня 4, который просто выполняется подряд. Ошибки нет, сообщения нет,
«отлично!» печатается и при двойке.

<ProTip>
Обе ловушки — и эта, и та, что с отступами (раздел 4), — ловятся одной привычкой: **набирать
`if (…) { }` целиком, а потом дописывать внутрь**. Тогда ни лишней точке
с запятой, ни потерянным скобкам просто неоткуда взяться.
</ProTip>

Условие в скобках — это любое выражение, не обязательно сравнение. Вот формы, которые
встречаются чаще всего:

```js
if (mark === 5) { }            // сравнение
if (mark >= 2 && mark <= 5) { } // составное условие
if (isReady) { }               // переменная с логическим значением
if (marks.length) { }          // число: 0 — ложь, остальное истина
if (!user) { }                 // отрицание
if (getScore() > 50) { }       // результат вызова функции
```

## 3. else и лестница else if {#else}

Вторая ветка добавляется словом `else` — «иначе»:

```js
if (mark >= 3) {
  console.log("сдал");
} else {
  console.log("пересдача");
}
```

У `else` нет своего условия: он срабатывает всегда, когда не сработал
`if`. Поэтому он последний и единственный.

А если веток больше двух? Тогда между ними ставят `else if`:

```js
if (mark === 5) {
  console.log("отлично");
} else if (mark === 4) {
  console.log("хорошо");
} else if (mark === 3) {
  console.log("удовлетворительно");
} else {
  console.log("неудовлетворительно");
}
```

<Why>
Отдельного слова `elif`, как в Python, в языке нет — и `else if`
это не одна конструкция, а две. Мы говорили об этом на дне 3: это `else`,
внутри которого стоит один `if`. Просто писать его на одной строке удобнее,
чем с отступом:

```js
// то, что движок видит на самом деле
if (mark === 5) {
  // ...
} else {
  if (mark === 4) {
    // ...
  }
}
```

Знать это полезно ради одного: **лестница проверяется сверху вниз, и первая
сработавшая ветка отменяет все остальные**.
</Why>

## 4. Почему скобки ставят всегда {#braces}

Формально, если в ветке одна инструкция, фигурные скобки можно не писать:

```js
const mark = 5;

if (mark === 5) console.log("отлично");
```

Работает. Но так делать не нужно, и вот почему. Допишем вторую строку:

```js
const mark = 3;

if (mark === 5)
  console.log("отлично");
  console.log("молодец!");     // ← выполнится ВСЕГДА
```

<Mistake>
Вторая строка **не входит в условие**. Без скобок `if` забирает
ровно одну инструкцию — первую. Всё остальное просто идёт следом. Отступ обманывает глаз:
код выглядит правильно, а работает не так. Ошибки нет, сообщения нет — просто «молодец!»
печатается троечнику.
</Mistake>

Правило курса: **фигурные скобки ставим всегда**, даже для одной строки.
Это рекомендация и самой документации MDN. Две лишние скобки сегодня — сэкономленный час
отладки через месяц.

```js
if (mark === 5) {
  console.log("отлично");
  console.log("молодец!");     // теперь обе строки в ветке
}
```

Исключение одно — ранний выход в одну строку: `if (score >= 90) return "5";`.
Он встретится в разделе 7, а с дня 12 будет попадаться часто. Условие и `return`
стоят на одной строке, и отступ никого не обманет.

## 5. Что считается условием {#truthy}

В круглых скобках может стоять **любое** выражение, не обязательно сравнение.
Язык превратит его в «да» или «нет» по правилу из дня 5:

<Important>
**Ложных значений шесть:** `false`, `0` (ноль в любом
виде: и `-0`, и `0n`), `""`, `NaN`, `null`,
`undefined`.
**Всё остальное истинно** — включая `"0"`, `" "`,
`[]` и `{ }`.
</Important>

```js
const name = "Аман";
const marks = [5, 4];

if (name) {                  // строка непустая — истина
  console.log(`Привет, ${name}`);
}

if (marks.length) {          // 0 это ложь, значит «если массив не пуст»
  console.log("оценки есть");
}
```

Второй приём — `if (marks.length)` — встречается очень часто. Он читается как
«если длина не ноль». Но осторожно: короткая форма работает только там, где ноль действительно
означает «пусто». Мы разбирали это на дне 5 на примере возраста.

### Короткая проверка или точная

Раз в условие можно поставить что угодно, встаёт вопрос: писать коротко или явно?
Сравните две функции — они отличаются одной строкой:

<Compare>
<Wrong label="Коротко">
```js
function show(count) {
  if (count) {
    return `показываем ${count}`;
  }
  return "нечего показывать";
}
```
</Wrong>

<Right label="Точно">
```js
function show(count) {
  if (count !== undefined) {
    return `показываем ${count}`;
  }
  return "нечего показывать";
}
```
</Right>
</Compare>

На большинстве значений они ведут себя одинаково. Но не на всех:

| `count` | `if (count)` | `if (count !== undefined)` |
| --- | --- | --- |
| `5` | показываем 5 | показываем 5 |
| `0` | **нечего показывать** | **показываем 0** |
| `""` | нечего показывать | показываем |
| `undefined` | нечего показывать | нечего показывать |

Разница в строке с нулём — той же самой, из-за которой на дне 7 появился оператор
`??`. Вопрос всегда один: **ноль и пустая строка — это «нет данных»
или законные данные?**

<ProTip>
Правило выбора. Короткая проверка `if (x)` хороша там, где вас устраивают
все шесть ложных значений сразу: непустая строка, непустой массив, «флаг поднят».
Точная проверка нужна, когда ноль, пустая строка или `false` — **осмысленные
значения**: счётчик, температура, координата, ответ «нет». Сомневаетесь — пишите точно:
длиннее, зато читатель видит, что именно вы проверяете.
</ProTip>

<Mistake>
Отдельная ловушка из дня 5, про которую предупреждает и документация. Объект-обёртка
`new Boolean(false)` в условии ведёт себя как истина, а при сравнении —
как ложь:

```js
const b = new Boolean(false);

if (b) { }           // сюда войдёт — объект истинен
if (b == true) { }   // а сюда нет — сравнение разворачивает обёртку
```

Ещё один довод не писать `new` перед `Boolean`, `Number`
и `String`.
</Mistake>

## 6. Порядок веток решает {#order}

Раз лестница проверяется сверху вниз и останавливается на первой подошедшей ветке, порядок
условий становится частью логики. Посмотрите:

<Compare>
<Wrong label="Неверно">
```js
if (score >= 50) {
  grade = "3";
} else if (score >= 75) {
  grade = "4";
} else if (score >= 90) {
  grade = "5";
}
```

При 95 баллах сработает **первая** ветка, и отличник получит тройку.
Две нижние не сработают никогда.
</Wrong>

<Right label="Верно">
```js
if (score >= 90) {
  grade = "5";
} else if (score >= 75) {
  grade = "4";
} else if (score >= 50) {
  grade = "3";
}
```

Сначала самое узкое условие, потом всё шире. Каждая ветка ловит только то,
что не поймали верхние.
</Right>
</Compare>

<Scheme src="scheme-order.svg">Одно и то же значение, один и тот же набор условий — разный ответ из-за порядка</Scheme>

**Правило для лестницы с диапазонами: сверху — самое строгое условие.**
Если ветки перекрываются, выигрывает та, что выше.

Ошибку легко не заметить, потому что программа не падает и на части данных даже работает
правильно — при 60 баллах обе версии дадут тройку.

### Проверка на границах

Отсюда приём, который стоит завести привычкой прямо сейчас. Условия ломаются **на краях
диапазонов**, а не в середине. Поэтому проверять их надо не на случайных числах,
а на трёх значениях вокруг каждой границы: **на самой границе, на единицу меньше
и на единицу больше**.

Для лестницы с порогами 90 и 75 это шесть проверок:

```js
console.log(grade(89), grade(90), grade(91));   // вокруг первой границы
console.log(grade(74), grade(75), grade(76));   // вокруг второй
```

Такой набор сразу ловит две самые частые ошибки в условиях.

**Первая — перепутанный знак.** Написали `>` вместо
`>=`, и ровно 90 баллов перестали быть пятёркой. В середине диапазона разницы нет,
на границе — есть.

**Вторая — дырка между ветками.** Если верхняя ветка ловит `> 90`,
а нижняя `< 90`, то само значение 90 не попадёт никуда:

```js
if (score > 90) {
  grade = "5";
} else if (score < 90) {
  grade = "4";
}
// при score === 90 переменная grade останется undefined
```

<ProTip>
Приём работает не только с числами. У строк границы — это пустая строка и строка
из одних пробелов. У массивов — пустой массив и массив из одного элемента. У любого
ввода — `null` и `undefined`. **Ошибки живут на краях;
в середине всё обычно и так работает.**
</ProTip>

## 7. Вложенные условия и как их избегать {#nested}

Условие внутри условия — обычное дело:

```js
if (isLoggedIn) {
  if (hasTicket) {
    console.log("проходите");
  }
}
```

Но когда таких уровней становится три-четыре, код уезжает вправо и перестаёт читаться.
У этого даже есть название — «пирамида гибели» (по-английски pyramid of doom). Три способа
её выпрямить.

**Первый: объединить условия через `&&`**, если внутри нет
отдельного `else`:

```js
if (isLoggedIn && hasTicket) {
  console.log("проходите");
}
```

**Второй: выйти пораньше.** Сначала отсеять всё плохое, а полезную работу
оставить в конце без вложенности:

<Compare>
<Wrong label="Вложенно">
```js
function check(mark) {
  if (mark !== undefined) {
    if (mark >= 2) {
      if (mark <= 5) {
        return "годится";
      }
    }
  }
  return "негодная";
}
```
</Wrong>

<Right label="С ранним выходом">
```js
function check(mark) {
  if (mark === undefined) {
    return "негодная";
  }
  if (mark < 2 || mark > 5) {
    return "негодная";
  }
  return "годится";
}
```
</Right>
</Compare>

Справа код читается сверху вниз как список правил: «нет оценки — отказ; вне диапазона —
отказ; иначе годится». Слева приходится держать в голове три открытых скобки. Приём называется
**ранний возврат**, и мы вернёмся к нему на дне 12, когда разберём функции.

**Третий способ: дать условию имя.** Когда само условие длинное, вложенность
иногда вообще ни при чём — мешает то, что в одной строке слишком много всего:

<Compare>
<Wrong label="Всё в условии">
```js
if (user !== null
    && user.age >= 18
    && user.ticket !== null
    && !user.banned) {
  console.log("проходите");
}
```
</Wrong>

<Right label="По именам">
```js
const exists = user !== null;
const isAdult = exists && user.age >= 18;
const hasTicket = exists && user.ticket !== null;

if (isAdult && hasTicket && !user.banned) {
  console.log("проходите");
}
```
</Right>
</Compare>

Справа строк больше, но каждая отвечает на один вопрос, и условие в `if` читается
вслух. Плюс отладка становится простой: можно вывести любой флаг в консоль и увидеть, какой
именно не сработал. С длинным условием пришлось бы гадать.

Обратите внимание на `exists &&` в двух строках — это короткое замыкание
из дня 7. Без него `user.age` на пустом `user` дал бы
`TypeError`.

### Три типовые задачи

Условия в работе выглядят почти всегда одинаково. Вот три формы, которые покрывают
большинство случаев, — стоит узнавать их в лицо.

**Проверка данных: цепочка отказов.** Каждое правило — отдельный
`if` с ранним выходом, и порядок от самого грубого к самому тонкому:

{/* ahead-ok: день 16 */}

```js
function validate(name, age) {
  if (name.trim() === "") {
    return "введите имя";
  }

  const n = Number(age);

  if (Number.isNaN(n)) {
    return "возраст должен быть числом";
  }
  if (n < 0 || n > 120) {
    return "проверьте возраст";
  }
  return "";                   // пустая строка = всё в порядке
}
```

Заметьте: `Number(age)` стоит *между* проверками, а не наверху. Сначала
отсеяли пустое имя, потом превратили возраст, потом проверили результат превращения —
ровно приём «на границе» из дня 8.

**Выбор по диапазону: лестница сверху вниз.** Самое большое значение первым,
и каждая следующая ветка ловит остаток:

```js
function discount(total) {
  if (total >= 5000) {
    return 15;
  }
  if (total >= 2000) {
    return 10;
  }
  if (total >= 1000) {
    return 5;
  }
  return 0;
}
```

Здесь `else` не нужен вовсе — `return` и так выходит из функции.
Такая запись короче лестницы с `else if` и читается как таблица тарифов.

**Сложное условие: вынести во флаг.** Когда проверка перестаёт умещаться
в строку, ей дают имя — мы говорили об этом на дне 7:

```js
const isWeekend = day === "сб" || day === "вс";
const isHoliday = date === "01.01";

if (isWeekend || isHoliday) {
  console.log("выходной");
}
```

<Mistake>
Ловушка, которая прячется в первых двух формах. Если у функции нет последней ветки
на «всё остальное», она молча вернёт `undefined`:

```js
function grade(score) {
  if (score >= 90) return "5";
  if (score >= 75) return "4";
  // а если 50?
}

grade(95);   // "5"
grade(50);   // undefined ← и дальше пойдёт по программе
```

Вспомните день 5: `undefined` не падает, он просто тихо едет дальше и ломает
что-нибудь в другом месте. **Всегда закрывайте лестницу последней веткой**.
</Mistake>

## 8. Инструкция switch {#switch}

Когда веток много и все они сравнивают **одно и то же значение** с разными
вариантами, лестница `else if` начинает повторяться:

```js
if (mark === 5) { word = "отлично"; }
else if (mark === 4) { word = "хорошо"; }
else if (mark === 3) { word = "удовлетворительно"; }
else if (mark === 2) { word = "неудовлетворительно"; }
```

Слово `mark` написано четыре раза, `===` тоже. Для таких случаев есть
`switch`:

```js
switch (mark) {
  case 5:
    word = "отлично";
    break;
  case 4:
    word = "хорошо";
    break;
  case 3:
    word = "удовлетворительно";
    break;
  case 2:
    word = "неудовлетворительно";
    break;
  default:
    word = "неизвестно";
}
```

Как это работает: значение в скобках сравнивается по очереди с каждым `case`,
и управление передаётся первому совпавшему. Если не совпало ни одно — в `default`.

<Important>
**`switch` сравнивает строго, через `===`.**
Никаких приведений типов, как у `==`:

```js
switch ("1") {
  case 1:  console.log("число");  break;   // не сработает
  case "1": console.log("строка"); break;  // вот сюда
}
```

Это хорошая новость: вчерашние таблицы приведения тут не нужны. Но помните, что значение
из поля ввода — строка, и `case 5` для неё не сработает.
</Important>

### Где switch особенно уместен

Классический случай — **разбор команды**. Пользователь нажал кнопку, ввёл слово,
пришло сообщение — и надо выбрать, что делать. Вариантов много, все конкретные:

```js
function runCommand(cmd, list) {
  switch (cmd) {
    case "добавить":
      list.push("новая задача");
      return `добавлено, всего ${list.length}`;

    case "очистить":
      list.length = 0;
      return "список очищен";

    case "сколько":
      return `задач: ${list.length}`;

    case "помощь":
    case "?":
      return "команды: добавить, очистить, сколько";

    default:
      return `не знаю команду "${cmd}"`;
  }
}
```

Видно сразу три вещи, ради которых `switch` тут и взят. Список команд читается
как оглавление — по одной строке на вариант. Две команды, `"помощь"` и
`"?"`, обрабатываются вместе через группировку. И `default` ловит всё
незнакомое, а не молчит.

Похожий выбор по строке встретится на дне 29 в мини-проекте «Список дел»: кнопки фильтра
присылают строки `"all"`, `"active"` и `"done"`, и программа
решает, какие задачи показать.

## 9. break и провал {#break}

Слово `break` означает «выйти из `switch`». И вот главная странность
этой конструкции: **если `break` забыть, выполнение не останавливается,
а продолжается в следующую ветку** — даже если она не подходит.

Это называется **провалом** (по-английски fall-through).

```js
const action = "draw";

switch (action) {
  case "draw":
    console.log("рисуем");
    // break забыли!
  case "eat":
    console.log("едим");
    // и тут забыли
  default:
    console.log("ничего");
}
// напечатает все три строки: рисуем, едим, ничего
```

<Scheme src="scheme-break.svg">Совпавший `case` — это точка входа, а не отдельная ветка</Scheme>

Вот ключ к пониманию `switch`: **`case` — это не ветка,
а метка входа**. Совпадение говорит, с какой строки начать, а дальше код выполняется
подряд, пока не встретит `break` или не кончится `switch`.

Поэтому правило простое: **в каждой ветке ставьте `break`**.
В последней ветке он не нужен — проваливаться дальше некуда. Но если допишете ветку ниже,
не забудьте поставить `break` и в ту, что была последней.

<Important>
Слово `break` в языке одно, но работает в двух местах, и означает оно всегда
«выйти из ближайшей конструкции». В `switch` — выйти из `switch`.
В цикле (завтра, день 10) — выйти из цикла. А если `switch` стоит внутри цикла,
то `break` внутри него выйдет **только из `switch`**,
и цикл продолжится. Это регулярно удивляет.
</Important>

Есть и третий способ выйти из `switch` — `return`, если весь
`switch` стоит внутри функции. Он выходит сразу из функции, поэтому
`break` после него не нужен. Так написана программа в разделе 14, и такую запись
вы будете встречать часто.

## 10. Провал как приём {#fallthrough}

Иногда провал нужен нарочно — когда несколько значений обрабатываются одинаково.
Тогда `case` ставят подряд, без кода между ними:

```js
switch (day) {
  case "сб":
  case "вс":
    console.log("выходной");
    break;
  default:
    console.log("рабочий");
}
```

Здесь `case "сб"` не имеет своего кода, поэтому выполнение проваливается
в `case "вс"` — и оба варианта попадают в одну строку. Это законный и распространённый
приём, единственный случай, когда провал используют специально.

<ProTip>
Когда провал намеренный, но между `case` всё-таки есть код, — обязательно
оставьте комментарий:

```js
switch (mark) {
  case 5:
    excellent++;
  // провал намеренный: пятёрка тоже считается сданной
  case 4:
  case 3:
    passed++;
    break;
}
```

Иначе любой читатель, включая вас, решит, что вы забыли `break`, и «починит».
</ProTip>

## 11. Три ловушки switch {#switchtraps}

**Первая: все ветки живут в одной области видимости.** Фигурных скобок
у отдельного `case` нет, поэтому весь `switch` — это один блок:

```js
switch (x) {
  case 1:
    let a = 1;
    break;
  case 2:
    let a = 2;   // SyntaxError: Identifier 'a' has already been declared
    break;
}
```

Лечится своими скобками у ветки — и это как раз тот блок из дня 4:

```js
const x = 2;

switch (x) {
  case 1: {
    let a = 1;
    break;
  }
  case 2: {
    let a = 2;   // теперь другая область, всё в порядке
    break;
  }
}
```

**Вторая: `default` не обязан быть последним.** По традиции его
пишут внизу, но язык разрешает поставить где угодно — и тогда он сработает только если
не совпало ничего, а выполнение пойдёт с его строки. Не пользуйтесь этим: ставьте
`default` последним всегда.

**Третья: диапазоны через `switch` не проверить.**
`case` сравнивает с конкретным значением, а не с условием. Для «от 90 и выше»
нужна лестница `else if`.

### Пишите default всегда

Формально `default` необязателен: если ничего не совпало и его нет,
`switch` просто ничего не делает. Именно поэтому его и стоит писать — молчание
здесь опаснее всего.

```js
function markToWord(mark) {
  switch (mark) {
    case 5: return "отлично";
    case 4: return "хорошо";
  }
}

markToWord(3);   // undefined — и дальше это поедет по программе
```

Это та же дырка, что в лестнице без последней ветки, только спрятанная лучше. Добавьте
`default` — и незнакомое значение сразу о себе заявит, хотя бы словом
«неизвестно».

## 12. Что выбрать: if или switch {#choose}

| Задача | Чем писать |
| --- | --- |
| одна проверка, две ветки | `if...else` |
| диапазоны: «больше», «меньше», «от и до» | лестница `else if` |
| сложное условие с `&&` и `\|\|` | `if` |
| одно значение, много конкретных вариантов | `switch` |
| несколько значений обрабатываются одинаково | `switch` с группировкой |
| надо выбрать значение, а не выполнить действия | тернарный оператор (день 7) |

Короткое правило: **`switch` — когда сравниваете *одну* переменную
с *перечислимыми* вариантами. Во всех остальных случаях `if`.**

Проверить себя можно так: попробуйте переписать код другой конструкцией. Если получается
хуже — выбор был верный.

<Compare>
<Wrong label="Лестница вместо switch">
```js
if (cmd === "добавить") {
  add();
} else if (cmd === "удалить") {
  remove();
} else if (cmd === "очистить") {
  clear();
} else {
  unknown();
}
```

`cmd ===` повторяется трижды. Просится `switch`.
</Wrong>

<Right label="switch вместо лестницы">
```js
switch (true) {
  case score >= 90:
    grade = "5";
    break;
  case score >= 75:
    grade = "4";
    break;
}
```

Формально работает, но `switch (true)` — приём для знатоков.
Просится лестница.
</Right>
</Compare>

Приём `switch (true)` действительно существует: раз сравнение идёт через
`===`, а `score >= 90` даёт `true`, совпадение находится.
Документация MDN показывает его как законную замену лестнице. Но читателю приходится
разгадывать трюк вместо того, чтобы читать логику, **поэтому в курсе мы его
не используем**.

Есть и третий вариант, к которому мы придём позже: когда вариантов действительно много
и они просто сопоставляют значение значению, вместо `switch` берут объект-справочник.
Это день 21 — а пока запомните, что длинный `switch` из одних `return`
часто означает, что данные просятся в таблицу.

## 13. Про try...catch — два слова {#errors}

Глава учебника, по которой построен этот день, называется «Управление потоком и обработка
ошибок». Вторую половину — `try`, `catch`, `throw` — мы
разберём **на дне 11**, вместе с перебором значений.

Пока достаточно знать, что это тоже ветвление, просто особого рода: «попробуй сделать это,
а если сломается — сделай вот то».

{/* ahead-ok: день 11 */}

```js
const text = "{ испорчен";

try {
  const data = JSON.parse(text);   // вдруг текст испорчен
} catch (e) {
  console.error("разобрать не вышло:", e);
}
```

Чем это отличается от обычного `if`, стоит понять уже сегодня. В `if`
вы **заранее знаете, что проверять**: есть условие, есть две дороги.
В `try...catch` условия нет — вы говорите «делай», и ветка `catch`
срабатывает, только если по дороге что-то сломалось.

|  | `if...else` | `try...catch` |
| --- | --- | --- |
| что решает выбор | ваше условие | ошибка во время работы |
| когда известно | до выполнения | только по факту |
| для чего | обычная логика программы | то, что может не получиться |

Правило, которое стоит запомнить заранее: **`try...catch` — не замена
проверкам**. То, что можно проверить условием, проверяют условием. `try`
берут для вещей, которые проверить нельзя: разбор чужих данных, запрос к серверу, работа
с файлом.

{/* ahead-ok: день 11 */}

```js
const total = 10;
const count = 0;

// плохо: проверяемое прячем в try
try {
  const half = total / count;
} catch (e) { }

// хорошо: проверяем условием
if (count > 0) {
  const half = total / count;
}
```

Вдобавок второй пример честнее: деление на ноль в JavaScript вообще не бросает ошибку,
оно тихо даёт `Infinity` — как мы разбирали на дне 5. `catch` тут
не сработал бы никогда.

## 14. «Табель»: словесные оценки {#tabel}

Применим оба инструмента в одной программе: `switch` — для превращения цифры
в слово, лестницу `else if` — для вердикта по диапазону.

```js
const MIN_MARK = 2;
const MAX_MARK = 5;

const marks = [5, 4, 5, 3, 5, 4];

function markToWord(mark) {
  switch (mark) {
    case 5:
      return "отлично";
    case 4:
      return "хорошо";
    case 3:
      return "удовлетворительно";
    case 2:
      return "неудовлетворительно";
    default:
      return "неизвестно";
  }
}

let sum = 0;
let excellent = 0;
let failed = 0;

for (const mark of marks) {
  sum += mark;

  if (mark === MAX_MARK) {
    excellent++;
  } else if (mark === MIN_MARK) {
    failed++;
  }
}

const average = sum / marks.length;

let verdict;
if (average >= 4.5) {
  verdict = "отличник";
} else if (average >= 3.5) {
  verdict = "хорошист";
} else if (average >= 2.5) {
  verdict = "троечник";
} else {
  verdict = "надо подтянуть";
}

console.log(`Средний балл: ${average.toFixed(2)} — ${verdict}`);
console.log(`Пятёрок: ${excellent}, двоек: ${failed}`);

for (const mark of marks) {
  console.log(`${mark} — ${markToWord(mark)}`);
}
```

<ResultBox>
Средний балл: 4.33 — хорошист\
Пятёрок: 3, двоек: 0\
5 — отлично\
4 — хорошо\
5 — отлично\
3 — удовлетворительно\
5 — отлично\
4 — хорошо
</ResultBox>

Обратите внимание на две вещи.

**В `markToWord` нет ни одного `break`** — и это не ошибка.
Вместо него стоит `return`, который выходит не только из `switch`,
но и сразу из функции. Так пишут часто: когда каждая ветка что-то возвращает,
`break` просто не нужен. Функции разберём на дне 12.

**Вердикт написан лестницей, а не через `switch`** — потому что тут
диапазоны, а не конкретные значения. Ровно то разделение, о котором говорит таблица выше.
И порядок веток — от самого строгого условия вниз.

<TryIt>
Два опыта на этой программе.
\
\
**Первый.** Сначала замените оценки на `[5, 5, 4, 5]` — средний 4.75,
вердикт «отличник». Затем поменяйте местами первые две ветки вердикта — `>= 4.5`
и `>= 3.5`. Запустите и объясните, почему отличник стал хорошистом.
\
\
**Второй.** Перепишите `markToWord` так, чтобы вместо
`return` она складывала ответ в переменную и выходила по `break`.
Затем уберите один `break` и посмотрите, что станет с ответом для этой оценки.
</TryIt>

## 15. Частые ошибки дня {#mistakes}

| Ошибка | Почему | Как правильно |
| --- | --- | --- |
| `if (x = 5)` | одна палочка присваивает | `if (x === 5)` |
| `if` без фигурных скобок | в ветку попадёт только первая строка | скобки всегда |
| широкое условие выше узкого | нижние ветки не сработают никогда | сверху самое строгое |
| забыли `break` в `switch` | выполнение провалится дальше | `break` в каждой ветке |
| `case "5"` для числа 5 | `switch` сравнивает строго | привести тип на входе (день 8) |
| `let` в двух `case` | весь `switch` — один блок | свои `{ }` у ветки |
| `switch` для диапазонов | `case` сравнивает со значением | лестница `else if` |

<Selfcheck>
1. Почему в ветку без фигурных скобок попадает только одна строка?
   <Answer>Потому что `if` забирает ровно одну инструкцию. Блок из дня 4 —
   это способ сделать из нескольких инструкций одну. Без него вторая строка
   просто идёт следом и выполняется всегда.</Answer>
2. Что напечатает `switch`, если в совпавшей ветке забыть `break`?
   <Answer>Всё, что идёт после неё, до первого `break` или до конца
   `switch` — включая `default`, даже если он не подходит.
   `case` это метка входа, а не отдельная ветка.</Answer>
3. Почему лестница `if (score >= 50) ... else if (score >= 90)` неверна?
   <Answer>Лестница проверяется сверху вниз и останавливается на первой подошедшей ветке.
   При 95 баллах сработает первая, и до второй дело не дойдёт никогда.
   Сверху должно стоять самое строгое условие.</Answer>
4. Почему `let a` в двух `case` даёт `SyntaxError`?
   <Answer>У отдельного `case` нет своих фигурных скобок, поэтому весь
   `switch` — один блок, и в нём два объявления с одним именем.
   Лечится своими `{ }` у каждой ветки.</Answer>
5. Когда брать `switch`, а когда лестницу `else if`?
