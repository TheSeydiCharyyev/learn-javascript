Day 11. Iteration and errors

A summary of the lecture: for...of, for...in, try...catch, throw.

The main points

for...of gives values — for arrays and strings. for...in gives property names — for objects. The difference is one word, the result is completely different.
The keys from for...in are always strings, even for an array. That is why i + 1 gives "01", not 1.

for...of

for (const mark of marks) { }     // the values of an array
for (const letter of "Mary") { }  // the characters of a string

// we declare it with const: on every pass it is a NEW variable
// break and continue work as usual
// there is no index — if you need one, take an ordinary for
for...of does not work with an object, a number, null and undefined: TypeError: x is not iterable. The last two are the most common cause of crashes on real data.

If you need a number

for (let i = 0; i < marks.length; i++) { }          // the simplest
for (const [i, mark] of marks.entries()) { }        // day 22; entries — course 2

for...in

const user = { name: "Aman", age: 17 };

for (const key in user) {
  console.log(key, user[key]);    // the value — with brackets, not with a dot
}

// or the same thing, more reliably:
for (const key of Object.keys(user)) { }   // day 21
Three traps of for...in on an array: keys as strings, it sees extra properties (arr.meta), it skips holes in a sparse array. The rule: for...in is for objects, for...of is for arrays.

try...catch...finally

try {
  JSON.parse(text);
} catch (e) {
  e.name;      // "SyntaxError"
  e.message;   // the text
  e.stack;     // where
} finally {
  // runs ALWAYS — to clean up
}

try { /* … */ } catch { /* … */ }   // without a parameter — allowed
On an error the rest of try does not run — control jumps to catch immediately. return in finally overrides the return from try — people do not write it that way.

throw

throw new Error("text");            // not throw "text"!
throw new TypeError("not a number");
throw new RangeError("out of range");

if (e instanceof RangeError) { /* ours */ } else { throw e; }   // rethrow what is not ours

A thrown error goes up the chain of calls until it meets a catch. The rest of all the functions it passes through does not run. try is put where you know what to do with the error — not necessarily next to the dangerous line.

throw or return null

SituationHow to report it
“not found”, bad input — this happensreturn null
the function’s contract is broken — this must not happenthrow
Where try is needed: JSON.parse, a request to a server, the browser storage, someone else’s library, your own function with throw. Everything else — division, properties, conversions — is checked with if.
An empty catch is almost always a mistake: the program pretends that everything is fine. try goes inside the loop, not around it, otherwise the first error will break off the iteration.
