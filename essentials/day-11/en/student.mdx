# Day 11. Iteration and errors

<Subtitle>A summary of the lecture: `for...of`, `for...in`, `try...catch`, `throw`.</Subtitle>

## The main points

<Definition>
`for...of` gives **values** — for arrays and strings.
`for...in` gives **property names** — for objects.
The difference is one word, the result is completely different.
</Definition>

<KeyPoint>
The keys from `for...in` are always **strings**, even for an array.
That is why `i + 1` gives `"01"`, not 1.
</KeyPoint>

## for...of

```js
for (const mark of marks) { }     // the values of an array
for (const letter of "Mary") { }  // the characters of a string

// we declare it with const: on every pass it is a NEW variable
// break and continue work as usual
// there is no index — if you need one, take an ordinary for
```

<Remember>
`for...of` **does not work** with an object, a number, `null`
and `undefined`: `TypeError: x is not iterable`. The last two are
the most common cause of crashes on real data.
</Remember>

## If you need a number

```js
for (let i = 0; i < marks.length; i++) { }          // the simplest
for (const [i, mark] of marks.entries()) { }        // day 22; entries — course 2
```

## for...in

```js
const user = { name: "Aman", age: 17 };

for (const key in user) {
  console.log(key, user[key]);    // the value — with brackets, not with a dot
}

// or the same thing, more reliably:
for (const key of Object.keys(user)) { }   // day 21
```

<Remember>
**Three traps of `for...in` on an array:** keys as strings, it sees
extra properties (`arr.meta`), it skips holes in a sparse array.
The rule: `for...in` is for objects, `for...of` is for arrays.
</Remember>

## Five loops

| Loop | When |
| --- | --- |
| `for` | you need an index, the step is not one, you go backward |
| `for...of` | simply go through an array or a string |
| `for...in` | the properties of an object |
| `while` | the number of passes is unknown |
| `do...while` | at least once |

## try...catch...finally

```js
try {
  JSON.parse(text);
} catch (e) {
  e.name;      // "SyntaxError"
  e.message;   // the text
  e.stack;     // where
} finally {
  // runs ALWAYS — to clean up
}

try { /* … */ } catch { /* … */ }   // without a parameter — allowed
```

<Remember>
On an error **the rest of `try` does not run** — control jumps
to `catch` immediately. `return` in `finally` overrides
the `return` from `try` — people do not write it that way.
</Remember>

## throw

```js
throw new Error("text");            // not throw "text"!
throw new TypeError("not a number");
throw new RangeError("out of range");

if (e instanceof RangeError) { /* ours */ } else { throw e; }   // rethrow what is not ours
```

A thrown error **goes up the chain of calls** until it meets
a `catch`. The rest of all the functions it passes through does not run. `try` is put
where you know what to do with the error — not necessarily next to the dangerous line.

## throw or return null

| Situation | How to report it |
| --- | --- |
| “not found”, bad input — this happens | `return null` |
| the function’s contract is broken — this must not happen | `throw` |

<NoteBox>
**Where `try` is needed:** `JSON.parse`, a request to a server,
the browser storage, someone else’s library, your own function with `throw`. Everything else —
division, properties, conversions — is checked with `if`.
\
**An empty `catch`** is almost always a mistake: the program pretends
that everything is fine. **`try` goes inside the loop**, not around it, otherwise
the first error will break off the iteration.
</NoteBox>
