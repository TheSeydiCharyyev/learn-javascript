1. Два дела на сегодня

Сегодня закрываем модуль, и дел два.

Первое. Вчера мы ходили по массиву через счётчик i. Работает, но многовато букв ради того, чтобы просто посмотреть на каждый элемент:

for (let i = 0; i < marks.length; i++) {
  console.log(marks[i]);
}

Есть запись короче — for...of. Мы ей уже пользовались в «Табеле», не объясняя. Пора объяснить, а заодно разобрать её близнеца for...in, который выглядит похоже и делает совсем другое.

Второе. Долг с дня 9: try...catch и throw. Это вторая половина главы про управление потоком — то самое «попробуй, а если сломается, сделай вот это».

2. Цикл for...of

Он берёт элементы по значению, без индексов и без счётчика:

const marks = [5, 4, 3];

for (const mark of marks) {
  console.log(mark);   // 5 4 3
}

Сравните с вчерашней записью. Исчезли три вещи: объявление счётчика, условие с length и обращение marks[i]. Вместе с ними исчезли и вчерашние ошибки — «на единицу», лишний проход, забытый шаг. Их просто негде сделать.

Переменную объявляют через const, а не let. Мы разбирали это на дне 4: в for...of на каждом проходе создаётся новая переменная, её никто не меняет — значит, константа подходит. В обычном for переменная одна на весь цикл, там нужен let.

break и continue работают как вчера:

for (const mark of marks) {
  if (mark === 2) {
    continue;          // двойки пропускаем
  }
  if (mark === 5) {
    break;             // на первой пятёрке выходим
  }
  console.log(mark);
}

А если нужен номер

Чего у for...of нет — это номера элемента. Это его главное ограничение, и обходят его тремя способами.

Самый честный — взять обычный for. Раз нужен индекс, это его работа:

for (let i = 0; i < marks.length; i++) {
  console.log(`${i + 1}. ${marks[i]}`);
}
// 1. 5   2. 4   3. 3

Второй — завести счётчик рядом. Так пишут, когда индекс нужен изредка, а весь остальной код читается лучше с for...of:

let i = 0;
for (const mark of marks) {
  console.log(`${i + 1}. ${mark}`);
  i++;                              // не забыть!
}

Третий — метод entries(), который отдаёт сразу пару «индекс и значение»:

for (const [index, mark] of marks.entries()) {
  console.log(`${index + 1}. ${mark}`);
}

Запись [index, mark] — это деструктуризация из дня 22, а entries() — метод массива из дня 20. Показываю сейчас, чтобы вы узнали её в чужом коде: она встречается часто и выглядит загадочно, пока не знаешь, что это.

Выбор простой. Индекс нужен всегда — берите for. Индекс не нужен — for...of. Второй способ со своим счётчиком — компромисс, и у него есть та же беда, что у while из дня 10: про i++ можно забыть.

3. Что можно перебрать

for...of работает не со всем подряд, а только с тем, что документация называет перебираемым. В Essentials это три вещи:

ЧтоЧто даст цикл
массивэлементы по порядку
строкасимволы по одному
NodeList — найденные элементы страницыэлементы; день 24
 
for (const letter of "Мары") {
  console.log(letter);   // М а р ы
}

А вот обычный объект перебрать нельзя — и это первое, обо что спотыкаются:

const user = { name: "Аман", age: 17 };

for (const value of user) {
  console.log(value);
}
// TypeError: user is not iterable

То же самое с числом, null и undefined:

for (const x of 42) { }          // TypeError: 42 is not iterable
for (const x of null) { }        // TypeError: null is not iterable
for (const x of undefined) { }   // TypeError: undefined is not iterable

Последние два встречаются в работе постоянно: данные не пришли, переменная пустая, и цикл падает. Отсюда привычка проверять данные до цикла — или ловить ошибку, чему мы научимся во второй половине урока.

4. Цикл for...in

Второй цикл выглядит почти так же — отличается одним словом. И делает другое: перебирает имена свойств объекта.

const user = { name: "Аман", age: 17, city: "Мары" };

for (const key in user) {
  console.log(key);            // name age city
}

Обратите внимание: цикл даёт ключи, а не значения. Чтобы получить значение, берут его по ключу:

for (const key in user) {
  console.log(`${key}: ${user[key]}`);
}
// name: Аман
// age: 17
// city: Мары

Запись user[key] — это доступ к свойству через скобки из дня 3. Точка тут не подойдёт: user.key искало бы свойство с именем «key», а нам нужно то, что лежит в переменной key. Подробно объекты разберём на дне 21.

5. Почему их путают

Оба цикла можно натравить на массив — и вот тут начинается путаница:

const marks = [5, 4, 3];

for (const x of marks) { console.log(x, typeof x); }
// 5 "number"  4 "number"  3 "number"

for (const x in marks) { console.log(x, typeof x); }
// "0" "string"  "1" "string"  "2" "string"
Ключи — строки, даже для массива. Значит, арифметика с ними даст не то, что ждёте: 
for (const i in marks) {
  console.log(i + 1);     // "01", "11", "21" — склейка, а не сложение!
}
Вспомните день 6: плюс со строкой склеивает. Чтобы получить число, нужен Number(i) + 1. Или просто не используйте for...in для массивов.

6. Ловушки for...in

Помимо строковых ключей у for...in есть ещё две особенности, из-за которых его не советуют для массивов.

Первая: он видит все свойства, а не только индексы. Массив — это объект (день 3), и если кто-то добавил ему обычное свойство, цикл его тоже покажет:

const marks = [5, 4];
marks.meta = "экзамен";

for (const key in marks) {
  console.log(key);      // "0", "1", "meta"  ← откуда третий?
}

for (const value of marks) {
  console.log(value);    // 5, 4  ← а тут всё как надо
}

Вторая: он пропускает дырки. Если в массиве есть незаполненные места — те самые разреженные массивы из дня 3, — for...in их не покажет, а for...of покажет как undefined:

const a = [1];
a[5] = 6;                      // между ними четыре пустых места

for (const k in a) { }         // "0", "5" — две штуки
for (const v of a) { }         // 1, undefined × 4, 6 — шесть штук
Правило простое и почти без исключений: for...in — для объектов, for...of — для массивов и строк. Если тянет написать for...in по массиву, вам почти наверняка нужен обычный for с индексом.

Чем заменяют for...in

Раз у for...in столько оговорок, возникает вопрос: а нужен ли он вообще? Для объектов — да, но и там у него есть соперник. Метод Object.keys отдаёт ключи обычным массивом, который дальше перебирают через for...of:

const user = { name: "Аман", age: 17 };

for (const key in user) {              // вариант 1
  console.log(key, user[key]);
}

for (const key of Object.keys(user)) { // вариант 2 — то же самое
  console.log(key, user[key]);
}

console.log(Object.keys(user));        // ["name", "age"]
console.log(Object.values(user));      // ["Аман", 17]

Чем второй вариант лучше: Object.keys берёт только собственные свойства объекта, а for...in заглядывает ещё и в унаследованные. В простом коде разницы не будет, но как только появятся классы (курс 2), она станет заметной.

А Object.values и вовсе избавляет от user[key], если ключи не нужны. Подробно все эти методы — на дне 21.

Практическое правило на сегодня: for...in знать обязательно — он встречается в любом коде, и без него не прочитать чужую программу. Писать в своём коде — по желанию: Object.keys с for...of надёжнее и читается не хуже.

Теперь у нас пять циклов. Вот вся картина на одной таблице:

По частоте в настоящем коде: первое место у for...of, второе у for, дальше с большим отрывом остальные. А на дне 20 появятся методы массива, которые потеснят и for...of.

8. Три ошибки перебора

Что написалиСообщение в Chrome
for (const x of user) по объекту TypeError: user is not iterable
for (const v = 1 of arr) SyntaxError: for-of loop variable declaration may not have an initializer
for (let k = 0 in obj) SyntaxError: for-in loop variable declaration may not have an initializer

Первая — самая частая, и она возникает во время работы: значит, файл выполнился, а упал уже на данных. Обычно причина — пустая переменная вместо массива.

Две другие синтаксические: в заголовке этих циклов переменной нельзя задать начальное значение, потому что цикл присваивает его сам на каждом проходе.

У третьей есть историческая странность, о которой предупреждает и документация. Запись for (var k = 0 in obj) — наследие старых версий языка. В обычном режиме она не падает, а просто игнорирует = 0: 
for (var k = 0 in { a: 1, b: 2 }) {
  console.log(k);   // "a", "b" — работает, инициализатор проигнорирован
}
Ошибку вы увидите только в строгом режиме или если написать let вместо var. Ещё один довод за то и другое.

9. try...catch: ловим ошибку

Переходим ко второй теме. Мы знаем с дня 5: когда движок не может что-то сделать, он бросает ошибку, и программа останавливается. Иногда этого допускать нельзя.

const text = "{это не JSON}";
const data = JSON.parse(text);   // SyntaxError — и всё, программа мертва
console.log("сюда не дойдём");

Конструкция try...catch позволяет перехватить ошибку и продолжить работу:

try {
  const data = JSON.parse(text);
  console.log(data);
} catch (error) {
  console.log("Не удалось разобрать данные");
}

console.log("а сюда дойдём");   // выполнится в любом случае

Ключевая деталь: при ошибке остаток блока try не выполняется. Управление прыгает в catch немедленно, с той самой строки, где сломалось.

В скобках после catch — переменная, в которую попадает сама ошибка. Имя любое, обычно пишут e или error. У неё есть полезные свойства:

try {
  JSON.parse("{плохо}");
} catch (error) {
  console.log(error.name);      // "SyntaxError" — вид ошибки
  console.log(error.message);   // текст, что именно не так
  console.log(error.stack);     // где произошло, строка за строкой
}

Если ошибка вам не нужна, скобки можно вообще не писать:

try {
  JSON.parse(text);
} catch {
  console.log("не вышло");
}

Как читать stack

Свойство stack мы упоминали с дня 3, но ни разу не разбирали. А это самая полезная часть ошибки: она показывает весь путь вызовов, по которому программа дошла до поломки.

Возьмём файл app.js из четырёх строк — три функции вызывают друг друга, и самая глубокая ломается:

function level3() { throw new RangeError("сломалось"); }
function level2() { level3(); }
function level1() { level2(); }
level1();

Страница с этим файлом, открытая через Live Server, напечатает в консоли такой стек:

RangeError: сломалось
    at level3 (http://127.0.0.1:5500/app.js:1:27)
    at level2 (http://127.0.0.1:5500/app.js:2:21)
    at level1 (http://127.0.0.1:5500/app.js:3:21)
    at http://127.0.0.1:5500/app.js:4:1

Числа после имени файла — строка и символ. 1:27 указывает прямо на new RangeError: там ошибку создали.

Читается он сверху вниз, от места поломки к началу:

  • верхняя строка — где ошибка произошла: функция level3, строка 1;
  • каждая следующая — кто вызвал предыдущую;
  • нижняя — откуда всё началось: сам файл, строка 4.
Практика чтения стека такая. Верхняя строка говорит «что сломалось», а нужная вам обычно вторая или третья — «почему туда попали плохие данные». Если level3 упал на undefined, чинить надо не его, а того, кто передал undefined.

И ещё: в стеке бывают строки из чужих библиотек — их можно пропускать. Ищите глазами свои файлы, они обычно ближе к низу.

В браузере стек показывается так же, и каждая строка кликается — как мы разбирали на дне 3. Один клик, и вы в нужной функции на нужной строке.

10. finally

Третий, необязательный блок. Он выполняется всегда — и когда ошибки не было, и когда была:

try {
  console.log("try");
  throw new Error("сломалось");
} catch (e) {
  console.log("catch");
} finally {
  console.log("finally");
}
// try, catch, finally

// а без ошибки:
// try, finally

Зачем он нужен: чтобы прибраться независимо от исхода. Убрать надпись «Загрузка…», закрыть соединение, разблокировать кнопку. Такой код должен выполниться в любом случае, а писать его дважды — в конце try и в конце catch — плохо.

function load() {
  showSpinner();                    // показали «Загрузка…»

  try {
    const data = fetchData();
    render(data);
  } catch (e) {
    showError("Не удалось загрузить");
  } finally {
    hideSpinner();                  // убрали — получилось или нет
  }
}

Без finally пришлось бы вызвать hideSpinner() дважды. И стоит забыть одно из двух — надпись «Загрузка…» останется висеть навсегда. Именно так и выглядят подвисшие спиннеры на сайтах: кто-то забыл убрать его в ветке с ошибкой.

Настоящую загрузку данных разберём на дне 31, но приём вы теперь узнаете.

Одна странность, о которой лучше знать заранее: return в finally перебивает return из try. 
function f() {
  try {
    return "из try";
  } finally {
    return "из finally";   // победит это
  }
}
f();   // "из finally"
Выглядит как ловушка — потому и не пишут return в finally. Его дело — прибраться, а не возвращать значения.

11. throw: бросаем свою

Ошибки бросает не только движок — вы тоже можете. Для этого есть throw:

function checkMark(mark) {
  if (mark < 2 || mark > 5) {
    throw new RangeError(`оценка ${mark} вне диапазона`);
  }
  return mark;
}

throw немедленно прекращает функцию — как return, только «аварийно». Управление уходит в ближайший catch, а если его нет, программа останавливается с красным сообщением в консоли.

Бросить можно что угодно, даже строку. Но так не делают:

Плохо
throw "что-то не так";

// в catch:
e.name      // undefined
e.message   // undefined
e.stack     // undefined
Хорошо
throw new Error("что-то не так");

// в catch:
e.name      // "Error"
e.message   // "что-то не так"
e.stack     // где произошло

Объект Error несёт с собой название, текст и место — то, без чего отладка превращается в гадание.

Куда летит брошенная ошибка

Самое важное про throw: ошибка не остаётся в той функции, где произошла. Она поднимается вверх по цепочке вызовов, пока не встретит catch. Если не встретит — программа останавливается.

Проверим это кодом — порядок сообщений говорит сам за себя:

function level3() {
  console.log("level3 начал");
  throw new RangeError("сломалось глубоко");
}

function level2() {
  console.log("level2 начал");
  level3();
  console.log("level2 закончил");     // не выполнится!
}

function level1() {
  console.log("level1 начал");
  try {
    level2();
  } catch (e) {
    console.log("level1 поймал:", e.name);
  }
  console.log("level1 закончил");
}

level1();
// level1 начал
// level2 начал
// level3 начал
// level1 поймал: RangeError
// level1 закончил

Обратите внимание, чего в выводе нет: строки «level2 закончил». Ошибка выкинула нас из level3 и level2 разом, не дав им договорить.

Отсюда важный вывод про то, где ставить try. Он не обязан быть рядом с опасной строкой — его ставят там, где вы знаете, что делать с ошибкой. Функция, которая просто считает, не должна показывать сообщения пользователю: она бросает ошибку, а ловит её тот, кто вызвал и умеет реагировать.

12. Виды ошибок и instanceof

У Error есть готовые разновидности — те самые, что мы встречали с дня 4:

ВидКогда бросают
Errorобщий случай, когда не подходит ничего другого
TypeErrorзначение не того типа
RangeErrorчисло вне допустимых пределов
SyntaxErrorтекст не по правилам — бросает в основном движок
ReferenceErrorимени не существует — тоже движок
 
throw new TypeError("оценка должна быть числом");
throw new RangeError("оценка вне диапазона 2–5");

Зачем выбирать вид, если текст всё равно свой? Затем, что по виду можно различать ошибки в catch — через оператор instanceof:

try {
  checkMark(mark);
} catch (e) {
  if (e instanceof RangeError) {
    console.log("Поправьте оценку:", e.message);
  } else if (e instanceof TypeError) {
    console.log("Это не число:", e.message);
  } else {
    throw e;               // чужую ошибку пробрасываем дальше
  }
}
Последняя строка важна. В catch попадают все ошибки из try — не только те, которых вы ждали. Если поймали что-то незнакомое, честнее бросить это дальше, чем молча проглотить: иначе настоящая поломка спрячется под вашим сообщением.

Отдельного «условного catch» в языке нет, поэтому такая развилка внутри catch — обычная практика.

Различать вид можно и без instanceof — по свойству name:

if (e.name === "RangeError") { }     // то же самое, что instanceof

Разница тонкая: instanceof сработает и для «потомков» типа, а сравнение имени — только для точного совпадения. В Essentials обе записи равноценны, берите ту, что понятнее.

И ещё одна возможность, которая пригодится: к объекту ошибки можно добавить свои поля — он же обычный объект (день 3):

const error = new Error("нет такой оценки");
error.mark = 9;                      // своё поле
throw error;

// а в catch:
console.log(e.message, e.mark);      // "нет такой оценки" 9

Так передают в catch подробности, которых не втиснуть в текст сообщения: какое значение подвело, какая строка файла, какой номер записи.

throw или return null

Когда функция не может сделать своё дело, у неё два способа сообщить об этом. Мы пользовались обоими: на дне 8 функция toMark возвращала null, а сегодня checkMark бросает ошибку. Чем они отличаются?

return null
function toMark(input) {
  const n = Number(input);
  if (Number.isNaN(n)) {
    return null;
  }
  return n;
}

const m = toMark("пять");
if (m === null) {
  // разбираемся
}
throw
function checkMark(mark) {
  if (mark < 2 || mark > 5) {
    throw new RangeError("вне диапазона");
  }
  return mark;
}

try {
  checkMark(9);
} catch (e) {
  // разбираемся
}

Разница в том, можно ли не заметить проблему. Возвращённый null легко проигнорировать: забыли проверку — и null поехал дальше по программе, ломая что-нибудь в другом месте. Брошенную ошибку проигнорировать нельзя: либо вы её поймаете, либо программа остановится.

КогдаЧем сообщать
«не нашлось» — обычный, ожидаемый исходreturn null
плохой ввод от пользователяreturn null и сообщение
нарушен договор функции: дали не то, что обещалиthrow
дальше работать нельзя и чинить нечегоthrow

Грубое правило: null — для «так бывает», throw — для «так быть не должно». Пользователь, который ввёл «пять» вместо цифры, — это «так бывает». А функция, которой вместо массива подсунули undefined, — это «так быть не должно».

13. Когда ловить, а когда нет

Главный вопрос дня: где ставить try...catch? Правило из дня 9 остаётся в силе, и оно же главное.

try...catch — не замена проверкам. То, что можно проверить условием, проверяют условием. try берут для того, что проверить нельзя: разбор чужих данных, запрос к серверу, работа с файлом.
Не надо
try {
  const half = total / count;
} catch (e) { }

try {
  console.log(user.name);
} catch (e) { }

Оба случая проверяются условием. К тому же деление на ноль вообще не бросает ошибку — catch не сработает никогда.

Надо
try {
  const data = JSON.parse(text);
} catch (e) {
  showError("плохие данные");
}

Проверить строку на «разбирается ли она» можно только попыткой разобрать. Вот тут try на месте.

И второе правило: пустой catch — почти всегда ошибка.

try {
  risky();
} catch (e) { }      // ошибка исчезла бесследно

Программа сделает вид, что всё хорошо, а данные окажутся неверными. Минимум, что должно быть в catch, — сообщение в консоль. Лучше — понятное сообщение пользователю и запасной сценарий.

Вот список мест, где try действительно нужен. Он короткий, и это не случайно:

ГдеПочему нельзя проверить заранееКогда у нас
JSON.parse годность строки узнаётся только попыткой разобрать день 23
запрос к серверу сеть может отвалиться в любой момент день 31
чтение хранилища браузера может быть отключено настройками день 31
чужая функция из библиотеки вы не знаете, что у неё внутри по мере появления
своя функция с throw вы сами решили сообщать об ошибке так сегодня

Всё остальное — деление, обращение к свойству, преобразование типов — проверяется условием. Если тянет обернуть в try обычную арифметику, скорее всего, вы прячете проблему, а не решаете её.

14. «Табель»: данные извне

Соберём оба сегодняшних инструмента. Представим, что данные о студенте приходят строкой — из файла или с сервера, как будет на дне 31.

const MIN_MARK = 2;
const MAX_MARK = 5;

const raw = `{"name": "Аман", "marks": [5, 4, 9, 3, 5]}`;

function parseStudent(text) {
  try {
    return JSON.parse(text);
  } catch (e) {
    console.log("Не удалось прочитать данные:", e.name);
    return null;                    // честно говорим: не вышло
  }
}

function checkMark(mark) {
  if (typeof mark !== "number" || Number.isNaN(mark)) {
    throw new TypeError(`оценка должна быть числом, получено: ${mark}`);
  }
  if (mark < MIN_MARK || mark > MAX_MARK) {
    throw new RangeError(`оценка ${mark} вне диапазона ${MIN_MARK}–${MAX_MARK}`);
  }
  return mark;
}

const student = parseStudent(raw);

if (student !== null) {
  let sum = 0;
  let count = 0;

  for (const mark of student.marks) {        // for...of — по значениям
    try {
      sum += checkMark(mark);
      count++;
    } catch (e) {
      console.log(`Пропущено: ${e.message}`);
    }
  }

  console.log(`${student.name}: ${count} оценок, средний ${(sum / count).toFixed(2)}`);

  console.log("Поля объекта:");
  for (const key in student) {               // for...in — по свойствам
    console.log(`  ${key}: ${student[key]}`);
  }
}
Пропущено: оценка 9 вне диапазона 2–5
Аман: 4 оценок, средний 4.25
Поля объекта:
  name: Аман
  marks: 5,4,9,3,5

Три места стоит разобрать.

try стоит внутри цикла, а не снаружи. Это важно: если обернуть весь цикл целиком, первая же плохая оценка прервёт перебор и остальные не проверятся. А так плохая оценка пропускается, и цикл идёт дальше.

parseStudent возвращает null при неудаче. Мы разбирали это на дне 5: null означает «пусто намеренно». Вызывающий код проверяет результат и решает, что делать. Так функция не обязана знать, как показывать ошибки.

for...in по student показал marks строкой. Это не ошибка — шаблонная строка превратила массив в "5,4,9,3,5" по правилам дня 8. Для красивого вывода массив надо обходить отдельно.

Три опыта.

Первый. Испортите строку raw — уберите кавычки у "name". Программа должна сказать «Не удалось прочитать данные: SyntaxError» и не упасть.

Второй. Добавьте в массив оценок строку "пять" и посмотрите, какое из двух сообщений сработает.

Третий. Перенесите try наружу, обернув весь цикл, и объясните, почему средний балл изменился.

// пустой catch = ошибка исчезла бесследно
// try внутри цикла, а не вокруг него
  1. Что даст for...in по массиву [5, 4, 3] и какого типа будут значения?
    Ответ Ключи "0", "1", "2" — и все они строки, а не числа. Поэтому i + 1 даст "01", а не 1.
  2. Почему for (const v of user) по обычному объекту падает?
    Ответ Обычный объект не является перебираемым: у него нет порядка значений. Получится TypeError: user is not iterable. Для объектов — for...in.
  3. Что выполнится, если в try случилась ошибка на второй строке из пяти?
    Ответ Первая строка, затем сразу catch, затем finally, если он есть. Строки с третьей по пятую пропускаются полностью.
  4. Чем throw new Error("x") лучше, чем throw "x"?
    Ответ У объекта Error есть name, message и stack — вид ошибки, текст и место. У строки нет ничего, и отладка превращается в гадание.
  5. Почему try лучше ставить внутри цикла, а не вокруг него?
    Ответ Ошибка прерывает весь блок try. Если он охватывает цикл целиком, первый же плохой элемент оборвёт перебор и остальные не обработаются. Внутри цикла плохой элемент просто пропускается.
