## 1. Why functions {#why}

We have been writing functions since day 3 — several of them have piled up in the “Report card”. Today we
finally take apart how they work.

A function solves three problems at once.

**The first — not repeating yourself.** The same calculation in three places is three places
you will have to edit if the formula changes. And three chances to forget one of them.

**The second — giving an action a name.** The line `const valid = selectValid(marks);`
reads like a sentence. Five lines of a loop with a condition in its place would need to be worked out.

**The third — dividing a task into parts.** You cannot hold a big program in your head
as a whole. A program of ten functions of five lines each — you easily can: you think about one, and the rest
simply work.

<Analogy>
A function is like a button on a device. To turn on the light, you do not think about the wiring —
you press the switch. Whoever made the switch thought about the wiring once.
A good function works the same way: a clear name outside, and inside — details
you can forget about.
</Analogy>

## 2. Declaration and call {#declare}

The simplest form looks like this:

```js
function greet(name) {
  return `Salam, ${name}!`;
}

console.log(greet("Aman"));   // "Salam, Aman!"
```

Let us take it apart:

| Part | Name | What it does |
| --- | --- | --- |
| `function` | a keyword | says “a function follows” |
| `greet` | the name | the function is called by it |
| `(name)` | parameters | what the function takes |
| `{ ... }` | the body | what it does |
| `return` | the return | what it gives back |

<Important>
Declaring a function and calling it are **two different things**. A declaration does not run
anything, it only creates a name. The work begins with a call — when the name is followed by
**parentheses**.

```js
greet;          // the function as a value, nothing happened
greet("Aman");  // now we called it
```

Forgotten parentheses are one of the most common mistakes, and they are insidious because nothing crashes:
you simply get the function itself instead of the result.
</Important>

## 3. Parameters and arguments {#params}

Two words that are constantly confused, although the difference is simple:

- a **parameter** is a name in the declaration. Parameters are written once;
- an **argument** is a value in a call. New arguments are put in every time.

```js
function add(x, y) {     // x and y are parameters
  return x + y;
}

add(2, 3);               // 2 and 3 are arguments
add(10, 20);             // and here they are different
```

<Scheme src="scheme-params.svg">The call passes values, the function gives them its own names and returns the result</Scheme>

The last line of the scheme matters: **the link goes by order, not by names**.
The call `add(y, x)` with the variables `x = 2` and `y = 3`
will pass 3 into the parameter `x` — matching names mean nothing.

<Mistake>
Hence the classic mistake — the order of arguments mixed up:

```js
function divide(a, b) {
  return a / b;
}

divide(2, 10);   // 0.2 — but we wanted 5
```

No error, the program works, the number is wrong. With two numbers this is noticeable, but
`createUser("Mary", "Aman")` instead of `createUser("Aman", "Mary")`
can go unnoticed for a week. It is cured either by very clear names or by passing
an object instead of a list — a technique from day 22.
</Mistake>

## 4. When the number of arguments is off {#count}

The language does not check how many arguments you passed. More or fewer — the call
will happen:

```js
function add(x, y) {
  return x + y;
}

add(2, 3);        // 5
add(2, 3, 4);     // 5   — the extra argument is silently thrown away
add(2);           // NaN — y turned out undefined, 2 + undefined
add();            // NaN
```

Missing parameters get `undefined` — the very one from day 5. And then everything
depends on what is done with them: in arithmetic you get `NaN`, in a string —
the word “undefined”, in a condition — false.

<Important>
This is one of the main features of the language: **a call with the wrong number of arguments
is not an error**. No warning, no message — only a strange
result later. That is why important functions check their arguments themselves:

```js
function add(x, y) {
  if (typeof x !== "number" || typeof y !== "number") {
    throw new TypeError("add expects two numbers");
  }
  return x + y;
}
```

This is yesterday’s `throw` in its typical use: the function reports that
its contract has been broken.
</Important>

You can find out how many parameters are declared through the `length` property:

```js
console.log(add.length);   // 2
```

### When there are many parameters

With two parameters you remember the order. With five you no longer do, and the call turns into a riddle:

```js
createStudent("Aman", "Mary", 17, 5, true);
// which is which? is the third one the age or the grade?
```

On top of that: to pass the fifth argument, you have to pass all the previous ones too, even if
they are not needed.

The solution is to **pass one object instead of a list**:

```js
createStudent({
  name: "Aman",
  city: "Mary",
  age: 17,
  grade: 5,
  isActive: true,
});
```

Now each value has a label, the order no longer matters, and the fields you do not need
can simply be left out. Inside the function they are taken out as properties:

```js
function createStudent(options) {
  console.log(options.name, options.age);
  return options;
}
```

There is also a shorter form — **destructuring right in the parameters**,
which we met on day 3:

```js
function createStudent({ name, age }) {
  console.log(name, age);          // right away as separate variables
}
```

<ProTip>
A practical rule: **up to three parameters — an ordinary list, beyond that — an object**.
Especially if there are boolean values among them: `true` in a call
tells the reader nothing, while `isActive: true` tells everything.
</ProTip>

We will cover objects on day 21 and destructuring on day 22. Ways to accept any number
of arguments and to set default values are on day 14.

## 5. return: give the result back {#return}

A function usually calculates something — and the result has to be given back outside. This is done by
`return`:

```js
function double(n) {
  return n * 2;
}

const result = double(21);   // 42
```

You can return anything: a number, a string, a boolean, an array, an object and even
another function.

```js
function makeStudent(name, marks) {
  return { name: name, marks: marks };   // we returned an object
}
```

But what you **cannot** do is return several values separated by commas. For that,
people gather them into an array or an object:

```js
function stats(numbers) {
  return { count: numbers.length, sum: 10 };   // like this
}
```

## 6. What happens without return {#noreturn}

A function without `return` works too — it just returns `undefined`:

```js
function log(message) {
  console.log(message);
  // there is no return
}

const x = log("hello");
console.log(x);   // undefined
```

And that is fine: not every function has to give something back. There are two kinds of functions,
and it is useful to tell them apart:

| Kind | What it does | Example |
| --- | --- | --- |
| calculates and returns | changes nothing outside | `average`, `verdict` |
| performs an action | prints, changes the page, saves | `console.log`, `showError` |

The first kind is more convenient: it is easy to check — give it values, compare the result. The second is needed
so that the program does anything at all. It is bad when a function mixes both and is still named
as if it only calculates.

<Compare>
<Wrong label="Mixed">
```js
function average(marks) {
  let sum = 0;
  for (const m of marks) {
    sum += m;
  }
  const avg = sum / marks.length;
  console.log("average:", avg);
  return avg;
}
```

The name promises only a calculation, but the function also prints. Call it in a loop
over a hundred students — and you get a hundred lines in the console that nobody asked for.
</Wrong>

<Right label="Separated">
```js
function average(marks) {
  let sum = 0;
  for (const m of marks) {
    sum += m;
  }
  return sum / marks.length;
}

console.log("average:", average(marks));
```

The function calculates, the one who called it prints. Now `average`
is good for output, for calculation and for checking.
</Right>
</Compare>

An action inside a function is called a **side effect**: something changed
outside besides the returned value. Printing to the console, writing to the page, changing
an outside variable — all of these are side effects.

<ProTip>
A rule worth getting used to: **a function either calculates or acts**.
You can mix them, but then the name should say so —
`calculateAndShowAverage`. And if “and” appears in the name, remember the rule
from section 12: there is more than one job now.
</ProTip>

<Mistake>
An empty `return` is `undefined` too. And a trap hides here
with a line break, which we talked about back on day 3:

```js
function getCity() {
  return
    "Mary";
}
getCity();   // undefined!
```

The engine put a semicolon right after `return` — the automatic
insertion from day 3 worked. **The value is written on the same line as `return`.**
</Mistake>

## 7. return exits immediately {#exit}

An important property: `return` does not just give a value back — it **ends
the function right here**. Everything below will not run:

```js
function check(mark) {
  console.log("checking");
  return mark >= 2;
  console.log("we will not get here");   // dead code
}
```

Notice: this is **not an error**. The program works, the last
line is just pointless. Firefox will show the warning
“unreachable code after return statement” in the console; Chrome will say nothing at all.

But this property gives rise to a technique we saw on day 9 — the **early
exit**. We filter out everything bad at the top, and write the useful work without nesting:

<Compare>
<Wrong label="With else">
```js
function grade(score) {
  if (score >= 90) {
    return "5";
  } else {
    if (score >= 75) {
      return "4";
    } else {
      return "3";
    }
  }
}
```
</Wrong>

<Right label="With an early exit">
```js
function grade(score) {
  if (score >= 90) return "5";
  if (score >= 75) return "4";
  return "3";
}
```
</Right>
</Compare>

On the right `else` is not needed at all: if the first `return` worked,
the second one is never reached. It reads like a list of rules from top to bottom.

<ProTip>
In this form one-line `if` statements without curly braces are acceptable — this is
the only exception to the rule of day 9. It works because the body consists of exactly
one `return`, and adding a second line there unnoticed simply will not happen.
In doubt, put the braces — it will not hurt.
</ProTip>

### Where the value goes back to

When a function calls another one, and that one calls a third, you get a chain — the very one along which
the error went up yesterday. Only now it is not errors but results that travel along it.

<Scheme src="scheme-exit.svg">Each function waits for a result from the one it called</Scheme>

Until `isValidMark` returns an answer, `selectValid` is paused.
Until `selectValid` finishes, `makeReport` waits. You have already seen this chain —
yesterday, in the `stack` property: it is exactly the list of functions
that are waiting for a result at that moment.

## 8. What is inside stays inside {#scope}

Variables declared in a function are not visible outside. This is the function scope
from day 4:

```js
function calculate() {
  const secret = 42;
  return secret;
}

calculate();
console.log(secret);   // ReferenceError: secret is not defined
```

But a function looks outside freely — it sees everything declared around it:

```js
const TAX = 0.05;

function withTax(price) {
  return price + price * TAX;   // TAX is visible, it is outside
}
```

The direction is one way: **you can see in from the inside, not out from the outside**. We already
put it this way on day 4; now it is clear why: the function becomes a closed box,
whose contents the rest of the program does not need to know about.

<Important>
Hence the rule of a good function: **everything it needs, it gets through
its parameters**, and does not take from outside variables. Such a function can be moved
to another file, and it will keep working. A function that reaches outside for data
is tied to its place.
\
\
The exception is settings constants like `TAX` or `MAX_MARK`:
they are taken from outside, and that is fine.
</Important>

### A parameter is the function’s own variable

A parameter is a new variable inside the function, into which the value of the argument is put
at the call. Even if its name matches an outside variable, it is a different variable:

```js
let count = 1;

function addOne(count) {
  count = count + 1;   // the parameter changes — the function’s own variable
  return count;
}

addOne(count);   // 2
count;           // 1 — the outside variable did not change
```

With arrays and objects it is subtler: a reference gets into the parameter, and if the function changes
the contents of the array, it will be visible outside. In detail — on day 19.

## 9. Calling before declaring {#hoisting}

We covered this on day 4, but now the topic is in its place. A function declared with the word
`function` is hoisted **completely** — it can be called above
the place where it is written:

```js
console.log(greet("Aman"));   // it works!

function greet(name) {
  return `Salam, ${name}!`;
}
```

This property gives freedom in arranging code: you can write the main logic first,
and move the helper functions to the bottom of the file. Many people do exactly that — the main things on top,
the details below.

But a function put into a variable follows the rules of a variable and cannot do this:

```js
hi();                        // ReferenceError: Cannot access 'hi' before initialization
const hi = function () { };
```

This is what Chrome writes when these lines are in a file. In the console the message is shorter —
`hi is not defined`, but the meaning is the same: on this line there is no value yet.

We will cover the forms of writing functions tomorrow, on day 13.

## 10. A function is a value {#value}

We talked about this on day 3: a function is not a special construct of the language but an **ordinary
value**, just one that can be called. So you can do with it everything
you can do with a number or a string:

```js
function add(a, b) { return a + b; }

const sum = add;             // put it into a variable
console.log(sum(2, 3));      // 5 — it works under a new name

const ops = [add];           // put it into an array
console.log(ops[0](2, 3));   // 5

console.log(typeof add);     // "function"
console.log(add.name);       // "add" — a function has a name
console.log(add.length);     // 2 — and a number of parameters
```

And the most important consequence: a function can be **passed into another function**:

```js
function twice(fn, value) {
  return fn(fn(value));
}

function increment(n) { return n + 1; }

console.log(twice(increment, 5));   // 7
```

The function `twice` does not know what exactly it calls — it was passed in.
Such a passed function has a name: it is called a **callback**.
You will hear this word all the time,
and it means exactly this: a function that was passed so that it gets called.

Here is what a callback looks like in real code — these are array methods that we will cover
on day 20:

```js
const marks = [5, 4, 3, 5];

const doubled = marks.map(double);            // calls double for each one
const fives = marks.filter(isFive);           // keeps those where isFive returned true

function double(n) { return n * 2; }
function isFive(n) { return n === 5; }
```

The `map` method does not know what to do with numbers — it can only go through an array
and gather the results. What exactly to do is decided by the passed function. This way one method is good
for any task.

The same in event handlers — day 27:

{/* ahead-ok: day 27 */}

```js
button.addEventListener("click", handleClick);   // we passed it, it will be called later

function handleClick() {
  console.log("clicked");
}
```

<Mistake>
The main trap with callbacks is **extra parentheses**. You have to pass the function
itself, not the result of calling it:
{/* ahead-ok: day 27 */}

```js
button.addEventListener("click", handleClick);     // right: we passed the function
button.addEventListener("click", handleClick());   // a mistake: we called it right away,
                                                   // and passed undefined
```

In the second line the function runs *immediately*, before any click,
and the handler becomes whatever it returned. If that is `undefined`, nothing will happen
on a click.
</Mistake>

## 11. How to name functions {#naming}

The rules for names are the same as on day 4, but there are some conventions of their own.

| What the function does | How to name it | Example |
| --- | --- | --- |
| performs an action | a verb | `showError`, `saveData` |
| calculates something and returns it | `get`, `calc`, a noun | `getAverage`, `average` |
| answers “yes / no” | `is`, `has`, `can` | `isValidMark`, `hasErrors` |
| creates and returns an object | `create`, `make` | `createStudent` |

<ProTip>
A test for a good name: **can you tell from the name alone what the function returns,
without looking inside?** `isValidMark(9)` — obviously
`true` or `false`. `check(9)` — unclear:
will it return an answer, throw an error, print a message?
\
\
And the second sign: **if there is “and” in the name, the function does too much**.
`validateAndSave` is asking to be split in two.
</ProTip>

## 12. Splitting a task into functions {#split}

The main skill of the day is not syntax but the ability to divide a task. The rule is simple:
**one function — one job**.

How do you know the job is one? Three signs.

**The first: the name describes everything the function does**, without the word “and”.

**The second: the function can be described in one sentence.** If the explanation
takes a paragraph, several functions are hiding inside.

**The third: the function fits on the screen.** There is no hard limit, but if
you have to scroll to see all of it, it is worth looking for something to move out.

<Compare>
<Wrong label="One function for everything">
```js
function processMarks(marks) {
  const valid = [];
  for (const m of marks) {
    if (m >= 2 && m <= 5) {
      valid.push(m);
    }
  }
  let sum = 0;
  for (const m of valid) {
    sum += m;
  }
  const avg = sum / valid.length;
  let v;
  if (avg >= 4.5) v = "top student";
  else v = "good student";
  return `${avg} — ${v}`;
}
```
</Wrong>

<Right label="Four functions">
```js
function isValidMark(m) {
  return m >= 2 && m <= 5;
}

function selectValid(marks) { /* … */ }

function average(numbers) { /* … */ }

function verdict(avg) { /* … */ }

function report(marks) {
  const valid = selectValid(marks);
  const avg = average(valid);
  return `${avg} — ${verdict(avg)}`;
}
```
</Right>
</Compare>

On the right there is formally more code. But the last function reads like a table of contents: pick,
calculate, evaluate. And each part can be checked separately — `average([5, 4])`
should give 4.5, and you can see that in a second.

<Scheme src="scheme-split.svg">Splitting does not remove work — it makes each part checkable</Scheme>

### How to split in practice

Splitting in advance is hard — usually people first write it as it comes, and then move things out. Here is an order
that works.

**Step 1: find the comments in the code.** If you wrote
`// we pick the valid ones`, with five lines below it, that is a ready-made function, and its name
is already invented.

**Step 2: find repeats.** Two similar pieces are a reason to move them into one
function with a parameter that tells them apart.

**Step 3: find nesting.** A loop inside a loop inside a condition is almost
always a sign that the inner part is asking to be moved out.

```js
// before: a loop with a condition inside a loop
for (const student of students) {
  let sum = 0;
  for (const mark of student.marks) {
    if (mark >= 2 && mark <= 5) {
      sum += mark;
    }
  }
  console.log(sum);
}

// after: the inside is moved out
for (const student of students) {
  console.log(sumValid(student.marks));
}
```

The outer loop became four lines shorter and reads at once. And `sumValid` can now
be called anywhere else.

<ProTip>
A common question: will the program run slower if you split it into many functions?
Practically — no. A function call costs almost nothing, and browser engines can
put short functions right into the place of the call. **Split for the sake
of clarity**; it will not affect the speed.
</ProTip>

## 13. Recursion and its limit {#recursion}

A function can call itself. This is called **recursion**:

```js
function factorial(n) {
  if (n <= 1) {
    return 1;          // the exit condition
  }
  return n * factorial(n - 1);
}

console.log(factorial(5));   // 120
```

It works like this: `factorial(5)` waits for `factorial(4)`, that one waits for
`factorial(3)` and so on down to one. Then the results come back, being multiplied.

<Important>
Any recursion **must have an exit condition**, and it must be reachable.
Otherwise the calls will pile up on each other until space runs out:

```js
function forever() {
  return forever();
}
forever();   // RangeError: Maximum call stack size exceeded
```

This is yesterday’s infinite loop in new clothes. The good news: unlike a loop, the browser
does not hang here — it honestly crashes with an error after about ten thousand calls.
</Important>

In Essentials recursion will hardly be needed: everything we do is simpler to write with a loop.
You need to know it because it is irreplaceable for tree-like data — for example, for going through
a page, which we will run into on day 24.

## 14. Seven errors of the day {#errors}

| What was written | The message in Chrome | When |
| --- | --- | --- |
| `const n = 5; n();` | `TypeError: n is not a function` | while running |
| `obj.go()`, and there is no such method | `TypeError: obj.go is not a function` | while running |
| `function f(1) { }` | `SyntaxError: Unexpected number` | before running |
| `function f(a b) { }` | `SyntaxError: Unexpected identifier 'b'` | before running |
| `function () { }` as a declaration | `SyntaxError: Function statements require a function name` | before running |
| `console.log(1, 2;` | `SyntaxError: missing ) after argument list` | before running |
| recursion without an exit | `RangeError: Maximum call stack size exceeded` | while running |

Plus an eighth — not an error but a warning: **code after `return`**.
Firefox will write “unreachable code after return statement”, Chrome will say nothing.
The program works, part of the code is just dead.

<Mistake>
Separately about `x is not a function` — this is **the most common message**
when working with functions, and it has three causes:

1. a typo in the name: `consle.log`, `toUperCase`;
2. accessing something that does not exist: `obj.method` returned `undefined`,
   and `undefined` cannot be called;
3. the name is taken by something else: a variable overwrote the function.

By the rule of day 5, look **to the left of the parentheses**: the message names what
turned out not to be a function.
</Mistake>

A separate case is a function that was not given a required argument. The language does not check this,
but some built-in functions check it themselves:

```js
Object.create();
// TypeError: Object prototype may only be an Object or null: undefined
```

Firefox in this case will say it more clearly: “Object.create requires at least 1 argument”.
As we have already seen on days 4 and 8, **browsers word things differently**,
and MDN pages are titled with the Firefox version.

You can teach your own functions to do the same — check and report clearly:

```js
function makeReport(name, marks) {
  if (name === undefined || marks === undefined) {
    throw new TypeError("makeReport needs two arguments: a name and marks");
  }
  // ...
}

makeReport("Aman");
// TypeError: makeReport needs two arguments: a name and marks
```

Compare it with what would happen without the check: the function would get to a loop over
`undefined` and crash with `TypeError: marks is not iterable` —
a message from yesterday that does not immediately tell you the argument was simply forgotten.

Not every function needs such a check — only those that are called from many places
or given to other people. Internal helpers like `countFives` do not need
it.

## 15. The “Report card”: built from functions {#tabel}

Let us rewrite the program so that each part becomes a separate function. This is the main
exercise of the day.

```js
const MIN_MARK = 2;
const MAX_MARK = 5;

function isValidMark(mark) {
  return typeof mark === "number"
    && !Number.isNaN(mark)
    && mark >= MIN_MARK
    && mark <= MAX_MARK;
}

function selectValid(marks) {
  const valid = [];
  for (const mark of marks) {
    if (isValidMark(mark)) {
      valid.push(mark);
    }
  }
  return valid;
}

function average(numbers) {
  if (numbers.length === 0) {
    return 0;                     // protection from division by zero
  }
  let sum = 0;
  for (const n of numbers) {
    sum += n;
  }
  return sum / numbers.length;
}

function verdict(avg) {
  if (avg >= 4.5) return "top student";
  if (avg >= 3.5) return "good student";
  if (avg >= 2.5) return "average student";
  return "needs work";
}

function countFives(marks) {
  let n = 0;
  for (const mark of marks) {
    if (mark === MAX_MARK) {
      n++;
    }
  }
  return n;
}

function makeReport(name, marks) {
  const valid = selectValid(marks);
  const avg = average(valid);

  return `${name}: ${valid.length} of ${marks.length} marks, `
    + `average ${avg.toFixed(2)} — ${verdict(avg)}, `
    + `fives ${countFives(valid)}`;
}

console.log(makeReport("Aman", [5, 4, 9, 3, 5, 0, 4, 5]));
console.log(makeReport("Meret", [3, 3, 4]));
console.log(makeReport("Gülnar", [9, 0, "five"]));
console.log(makeReport("Sapar", [5, 5, 4, 5]));
```

<ResultBox>
Aman: 6 of 8 marks, average 4.33 — good student, fives 3\
Meret: 3 of 3 marks, average 3.33 — average student, fives 0\
Gülnar: 0 of 3 marks, average 0.00 — needs work, fives 0\
Sapar: 4 of 4 marks, average 4.75 — top student, fives 3
</ResultBox>

Compare it with what we had yesterday. Before, all the lines went one after another and worked with one student.
Now the program handles four with one line each — **because the logic
is moved into functions**. This is the very benefit for which it was all started.

Notice something else too: the four students are chosen so that **every branch
of `verdict` worked at least once**. This is no accident — this is how
functions with several branches are checked. If some branch never ran, you do not know
whether it works.

Notice four decisions.

**`isValidMark` returns `true` or `false`** —
a name with `is` promises exactly that. Inside is one long condition, moved out of the loop
by the rule of day 7.

**`average` is protected from an empty array.** Without the first line,
`0 / 0` would give `NaN` — as with Gülnar, who has not a single valid mark.
One check, and instead of the contagious `NaN`, an honest zero.

**`verdict` is written with an early exit** — four lines instead of
a ladder with `else`.

**`makeReport` calculates nothing itself** — it only builds a string
from the results. It reads like the table of contents of the program.

<Selfcheck>
1. How is a parameter different from an argument?
   <Answer>A parameter is a name in the declaration of a function, written once. An argument is a value
   in a call, new every time. They are linked by order, not by names.</Answer>
2. What does `add(2)` return if the function is declared as `add(x, y)`?
   <Answer>`NaN`. The missing parameter `y` gets
   `undefined`, and `2 + undefined` gives `NaN`.
   There will be no error — the language does not check the number of arguments.</Answer>
3. Why does code after `return` not run, and is it an error?
   <Answer>`return` ends the function immediately. It is not an error: the program
   works, part of the code is just dead. Firefox will show a warning,
   Chrome will say nothing.</Answer>
4. Why does `greet()` work before its declaration, while `hi()` does not?
   <Answer>A declaration with `function` is hoisted completely, together with its body.
   A function in a variable follows the rules of a variable and falls into the dead zone
   from day 4.</Answer>
5. How do you know a function does too much?
   <Answer>Three signs: there is the word “and” in the name; you cannot explain it in one sentence;
   it does not fit on the screen. Any one of the three is enough
   to look for something to move out.</Answer>
</Selfcheck>
