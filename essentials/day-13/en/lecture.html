1. Three ways to write the same thing

Yesterday we wrote functions in one way. Today we will learn two more — and all three do exactly the same thing:

// 1. Declaration — from yesterday
function add(a, b) {
  return a + b;
}
// 2. Function expression
const add = function (a, b) {
  return a + b;
};
// 3. Arrow function
const add = (a, b) => a + b;

All three are called the same way — add(2, 3) — and all three return 5. Why three, then?

Because they behave differently in small things, and each form is handier in its own place. Here is the whole difference in one picture — we will come back to it throughout the lesson:

Let us go through them one by one, and at the end we will put together a rule for choosing.

The main thing to understand today: the second and third forms are not a “function declaration” but an ordinary assignment. To the right of = stands a value that is put into a variable. We said on day 12 that a function is a value; here is a direct consequence.

2. Function expression

Let us take yesterday’s declaration and remove the name. We get an anonymous function — a function without a name:

// function (a, b) {
//   return a + b;
// }
// → SyntaxError: Function statements require a function name

On its own it does not work — we saw this error yesterday. But if you put it to the right of =, everything is fine:

const add = function (a, b) {
  return a + b;
};

add(2, 3);   // 5

This is what is called a function expression: the function stands where the language expects a value. Notice the semicolon at the end — it is needed because this is an ordinary assignment, not a declaration.

Where this form is met most often — where the function is passed somewhere right away:

button.addEventListener("click", function () {
  console.log("clicked");
});

The function is not put into a variable at all — it is only needed here and now. It has no use for a name.

Why it is needed today

A fair question: if there are arrows, which are shorter, why a function expression at all? Three answers.

The first — old code. Arrows appeared in 2015, and by then JavaScript was twenty years old. Everything written before uses this form, and you will have to read such code all the time.

The second — object methods. As we will see in section 11, an arrow cannot be a method, while a function expression can:

const student = {
  name: "Aman",
  say: function () { return this.name; },   // works
  sayShort() { return this.name; },         // a short form of the same
};

The second line is the shortened method syntax, which appeared at the same time as arrows. It is the one used today; we will take it apart together with objects on day 21.

The third — when a name is needed. A named function expression from section 8 gives something arrows do not have at all.

3. Arrow function

The third form appeared in 2015 and quickly became the most common. It is obtained from a function expression in two steps: remove the word function and put the arrow => between the parameters and the body.

The most useful thing here is the implicit return. If the body consists of one expression, the curly braces and the word return are not written: the result is returned by itself.

const double = (n) => n * 2;
const isFive = (n) => n === 5;
const greet = (name) => `Salam, ${name}!`;

One line instead of three — this is why arrows caught on so well.

4. How to shorten

You cannot always shorten. Here are all the rules at once:

CaseSyntaxParentheses around parameters
one simple parametern => n * 2can be removed
several parameters(a, b) => a + brequired
no parameters() => 42required
a default value(n = 1) => nrequired

Now about the body. It comes in two kinds, and it is easy to make a mistake here:

const f = (n) => n * 2;              // short body: the return is implied
const g = (n) => { return n * 2; };  // a block: return is required
const h = (n) => { n * 2; };         // a block without return — returns undefined!
The third line is the most common beginner mistake with arrows. As soon as curly braces appear, the implicit return switches off: the braces mean “there will be several statements here”, and the language expects an explicit return.

The check is simple: there is a { after the arrow — there must be a return.

Let us practice converting. Here is one function in all the allowed forms:

SyntaxCorrect?Why
(n) => n * 2yesshort body, implicit return
n => n * 2yesone simple parameter — no parentheses needed
(n) => { return n * 2; }yesa block with an explicit return
(n) => { n * 2; }noreturns undefined
(n) => return n * 2;noSyntaxError: return only in a block
const f = n, m => n + m;notwo parameters — parentheses are required

The last line deserves an explanation: the error there is not the one you expect.

// const add = n, m => n + m;   → SyntaxError: Missing initializer in const declaration
const add = (n, m) => n + m;    // two parameters — only in parentheses

The language did not see an arrow function with two parameters — it saw a list of declarations from day 4: first const add = n, then after a comma m => n + m. And it complained about the second one: m has no value, and a const cannot be declared without a value.

This is a typical story with missing parentheses: the message speaks of something completely different from what you did wrong. See an unclear SyntaxError next to an arrow — first check the parentheses around the parameters.

A block is needed when the body does not fit into one expression:

const sum = (numbers) => {
  let total = 0;
  for (const n of numbers) {
    total += n;
  }
  return total;
};

5. The trap with returning an object

A separate case that everyone stumbles over. Let us try to return an object with a short body:

const makeStudent = (name) => { name: name };

console.log(makeStudent("Aman"));   // undefined

There is no error, but there is no result either. Why: the language saw { right after the arrow and decided it was a block of code, not an object. And it took name: inside the block for a label — the very one from day 10. The block returned nothing, and we got undefined.

The cure is parentheses around the object:

const makeStudent = (name) => ({ name: name });

console.log(makeStudent("Aman"));   // { name: "Aman" }

The parentheses say: “an expression follows, not a block”. This is the same grouping operator from day 8, just in an unexpected use.

If the phrase “parentheses around the object” does not stick, there is a fallback — write a block with an explicit return: 
const makeStudent = (name) => {
  return { name: name };
};
Two lines longer, but not a single trap.

6. Why a declaration can be called earlier

Yesterday we accepted this as a fact. Now let us take the mechanism apart — it is simple if you remember day 4.

Expression — not allowed
add(2, 3);
// ReferenceError:
// Cannot access 'add'
// before initialization

const add = (a, b) => a + b;
Declaration — allowed
add(2, 3);   // 5, works

function add(a, b) {
  return a + b;
}

The message on the left is what Chrome writes when the code is in a file. In the console it is shorter: add is not defined. The explanation is entirely in day 4. A declaration with function is hoisted together with its body — by the time of the call the function is already ready. And a function expression, arrow or not, is an ordinary variable: before the line of its declaration it is in the dead zone.

If such a function is declared with var, the message will be different, but the result is the same:

add(2, 3);
// TypeError: add is not a function

var add = function (a, b) { return a + b; };

The name add already exists — var hoisted it — but it still holds undefined, and undefined cannot be called. Hence TypeError instead of ReferenceError: yesterday’s error “x is not a function” in a new form.

7. Names of nameless functions

An anonymous function technically has no name — but if you put it into a variable, a name does appear:

function named() { }
const myVar = function () { };
const arrowFn = () => { };

console.log(named.name);     // "named"
console.log(myVar.name);     // "myVar"   ← taken from the variable
console.log(arrowFn.name);   // "arrowFn"

The language substitutes the name of the variable. This is no small thing: the name is visible in error messages and in the call stack — the very one from day 11. Let us check it on the file app.js: three functions throw the same error, and we print the stack:

function named() { throw new Error("it broke!"); }
const anon = function () { throw new Error("it broke!"); };

try { named(); } catch (e) { console.log(e.stack); }
try { anon(); } catch (e) { console.log(e.stack); }
try { (function () { throw new Error("it broke!"); })(); } catch (e) { console.log(e.stack); }

A page with this file, opened via Live Server, will print three stacks. Their first lines look like this:

at named (http://127.0.0.1:5500/app.js:1:26)   ← the function name
at anon (http://127.0.0.1:5500/app.js:2:34)    ← the name came from the variable
at http://127.0.0.1:5500/app.js:6:28           ← no name at all

The numbers after the file name are the line and the character: 1:26 points to new Error in the first line. In the third stack the second line is line 6 again, character 54: the place where the nameless function was called. Without a name you have to search by these numbers.

In the first two cases you see right away where to look. In the third — only the line number, and if the function is passed into someone else’s library, the line will be someone else’s too.

Hence a practical conclusion: a name is worth creating a variable for. A one-line callback can be written right in place — it is clear without a name there. But a function of ten lines is better named, even if it is used once: on the day it breaks, you will thank yourself.

So a callback passed right in place is better moved into a named variable if it is longer than a line:

In the stack — anonymous
button.addEventListener(
  "click",
  function () {
    // twenty lines
  }
);
In the stack — handleClick
function handleClick() {
  // twenty lines
}

button.addEventListener(
  "click", handleClick
);

8. Named function expression

There is such a form too — a function expression that does have a name:

const outer = function inner() {
  return "result";
};

console.log(outer());        // "result"
console.log(outer.name);     // "inner"
console.log(typeof inner);   // "undefined" ← no name outside!

The name inner is visible only inside the function itself. Outside it does not exist. Why such a thing is needed — for recursion from day 12: the function can call itself by this name even if the variable outside is renamed.

const factorial = function fact(n) {
  if (n <= 1) return 1;
  return n * fact(n - 1);   // call itself by the inner name
};

This form is rare. You need to know it so as not to get lost when you see two names in a row in code.

9. Where arrows are especially good

Their main area is short callbacks, which we took apart yesterday. Compare the same chain:

With ordinary functions
marks
  .filter(function (m) {
    return m >= 3;
  })
  .map(function (m) {
    return m * 10;
  });
With arrows
marks
  .filter((m) => m >= 3)
  .map((m) => m * 10);

On the right you can see what the code does. On the left you have to wade through function and return to see the same thing. We will take apart the methods filter and map on day 20, but you already recognize the syntax.

Hence the practical rule: the shorter the function, the bigger the gain from an arrow. For a one-liner the gain is huge, for a function of twenty lines — none, there the form no longer matters.

Here are three places where arrows are met most often. We will cover all three in the coming weeks, and you will recognize the syntax already now.

Sorting — day 20. An array on its own sorts strangely, and a compare function is required:

[10, 9, 100].sort();                  // [10, 100, 9] — as strings!
[10, 9, 100].sort((a, b) => a - b);   // [9, 10, 100] — as numbers

A delayed call — day 30. The function is passed so that it gets called after a while:

setTimeout(() => console.log("a second passed"), 1000);

An event handler — day 27:

button.addEventListener("click", () => {
  console.log("clicked");
});

When arrows get in the way

The other side of brevity is code that stops being readable. Two signs that you have overdone it.

The first: an arrow inside an arrow.

const add = (a) => (b) => (c) => a + b + c;
add(1)(2)(3);   // 6

It works, but you cannot make sense of it at first sight. The language has such a technique, and it even got a name, but in learning code it is better not to meet it.

The second: nested ternaries in a short body.

const size = (n) => n > 10 ? n > 100 ? "very many" : "many" : "few";

Formally it is one expression, but you cannot read it without a pencil. Three branches are already a reason to take function with an early exit from day 12.

A check that works: does the function fit into one line without making you squint? If yes — an arrow with a short body. If not — either a block, or an ordinary declaration. Brevity is good as long as it saves the reader time, rather than taking it.

10. A line break and the arrow

One syntactic subtlety. The arrow must stand on the same line as the parameters:

// const f = (a)
//   => a + 1;   → SyntaxError: Unexpected token '=>' — a line break before the arrow
const f = (a) => a + 1;   // the arrow on the same line as the parameters

But after the arrow you can break lines as much as you like:

const f = (a) =>
  a + 1;              // works

const g = (a) =>
  a > 10
    ? "many"
    : "few";          // works too

The reason is the same automatic semicolon insertion from day 3 that breaks return with a line break. The rule is simple: break after the arrow, not before.

11. What arrow functions lack

An arrow function is not just a short syntax. It lacks two things that an ordinary one has.

The first: no own this. The word this we will take apart in course 2 — it is a reference to the object in which the function is called. For now it is enough to see the difference:

const student = {
  name: "Aman",
  sayNormal() { return this.name; },        // "Aman"
  sayArrow: () => this.name,                // will not work
};

Look at the difference more closely — it is worth it, because the error is silent:

const student = {
  name: "Aman",
  marks: [5, 4],

  sayNormal() { return `I am ${this.name}`; },  // "I am Aman"
  sayArrow: () => `I am ${this.name}`,          // "I am undefined"
};

The second line does not crash — it just lies. this.name in an arrow function points not to the student, and we get undefined from day 5. The program will keep working, and the report will say “I am undefined”.

And sometimes it does crash — when another access follows this:

const broken = {
  marks: [1, 2],
  count: () => this.marks.length,
};

broken.count();
// TypeError: Cannot read properties of undefined (reading 'length')

This is yesterday’s rule of day 5 in action: look to the left of the dot — this.marks turned out to be undefined, and undefined has no length.

A rule that will come in handy right away, even before studying this: arrow functions are not made into object methods. For methods take the short syntax sayNormal() { ... } or function. Details are in course 2.

The second: no arguments. An ordinary function has a service object with all the passed arguments:

function countArgs() {
  return arguments.length;
}
countArgs(1, 2, 3);   // 3

const countArrow = () => arguments.length;
countArrow(1, 2, 3);  // ReferenceError: arguments is not defined

The loss is small: arguments has a modern replacement — rest parameters, which we will take apart tomorrow. They work in arrow functions too.

And a third one, in passing: an arrow function cannot be called with new. What that means will become clear in course 2 together with classes.

const F = () => { };
new F();   // TypeError: F is not a constructor

12. A function called right away

Since a function expression is a value, it can be called right in place without giving it a name:

(function () {
  console.log("ran right away");
})();

(() => {
  console.log("and this one too");
})();

The technique is called an immediately invoked function expression. Let us take the syntax apart: the function in parentheses — so that the language understands it is an expression, not a declaration — and right away a second pair of parentheses that calls it.

Why it was needed: before let and const appeared, the only way to hide variables from the rest of the program was a function. We saw on day 4 that var does not know about blocks — but it does know about functions.

(function () {
  var temp = "not visible outside";
})();

console.log(typeof temp);   // "undefined"

Today a block with const is enough for that — as we did on day 4. But in code older than ten years this construction is met at every step, and you need to recognize it.

The technique has a second use that is alive to this day — hiding data while leaving only access to it outside:

const counter = (function () {
  let count = 0;                      // not reachable from outside

  return {
    inc: () => ++count,
    get: () => count,
  };
})();

counter.inc();
counter.inc();
console.log(counter.get());     // 2
console.log(typeof count);      // "undefined" — the variable cannot be reached

The function ran once and returned an object with two arrow functions. The variable count stayed inside — it cannot be seen or spoiled from outside, and it can be changed only through inc.

Why this works: nested functions see the variables of the outer one — we noted this on days 4 and 12. This property is called a closure, and it is covered in course 2. Today it is enough to see that this is done and to understand why.

13. What to choose

TaskForm
an ordinary program functionfunction — a declaration
a short one-line callbackan arrow function
an object methodfunction, not an arrow
a function in a variable that may be replacedan arrow or an expression
needs to be called before its declarationonly function

There is no single opinion here — teams agree differently, and this debate has been going on for about ten years. Here are both camps, honestly.

“Arrows everywhere”
  • one form for the whole file — no need to choose;
  • shorter on every function;
  • no surprises with this;
  • impossible to call a function before its declaration by accident — the language will not let you.
“function for the main things”
  • important functions are visible by the word function;
  • the order in the file is free: the main thing on top, details below;
  • object methods cannot be arrows anyway;
  • a long arrow function reads no better than an ordinary one.

Pay attention to the last argument on the left: it is more serious than it seems. If a file has not a single declaration, then the error “called before declaring” cannot occur either — the variable simply will not allow it. Some teams choose arrows exactly for this.

And the argument on the right about the order in the file is the other side of the same coin. When functions are declared with function, they can be placed in any order, and the reader will see the main thing first.

The agreement of our course, so that the code is uniform: function for program functions, arrows for callbacks. This way the most important functions are visible at first glance — by the word function, — and short helpers do not take up extra lines.

The main thing is not to mix them in one file without a reason. The reader does not care which form you chose; what matters to them is that the choice is the same throughout.

How to read someone else’s code with arrows

The main difficulty with arrows is not writing them but reading dense code written by others. Here is a technique that helps: unfold it back in your head.

You see this:

const top = marks.filter(m => m >= 4).map(m => m * 10);

Read it step by step, inserting what is left out:

  1. m => m >= 4 is a function: it takes m and returns m >= 4;
  2. filter will call it for every mark and keep those where it came out true;
  3. m => m * 10 is the second function: it takes m and returns m * 10;
  4. map will replace every mark with the result.

The same thing unfolded takes nine lines:

function isTop(m) {
  return m >= 4;
}

function toPercent(m) {
  return m * 10;
}

const filtered = marks.filter(isTop);
const top = filtered.map(toPercent);

Nobody writes like that, but this is exactly how you should read until your eye gets used to it. In a couple of weeks you will no longer need to unfold.

Three places in an arrow to look at first:
  1. what is to the left of the arrow — these are the parameters, that is, what the function receives;
  2. whether there is a { on the right — if there is, look for return inside; if not, the whole expression is returned;
  3. where it is passed — filter, map, addEventListener: this tells who will call it and when.

14. The “Report card”: three forms at work

Let us rewrite yesterday’s program, choosing the form for the task.

const MIN_MARK = 2;
const MAX_MARK = 5;

// short checks — arrow functions, in one line
const isValidMark = (mark) =>
  typeof mark === "number"
  && !Number.isNaN(mark)
  && mark >= MIN_MARK
  && mark <= MAX_MARK;

const isFive = (mark) => mark === MAX_MARK;

// the body does not fit into an expression — a block and an explicit return
const sum = (numbers) => {
  let total = 0;
  for (const n of numbers) {
    total += n;
  }
  return total;
};

// one expression, but with a condition — a line break after the arrow for readability
const average = (numbers) =>
  numbers.length === 0 ? 0 : sum(numbers) / numbers.length;

// a program function with branches — an ordinary declaration
function verdict(avg) {
  if (avg >= 4.5) return "top student";
  if (avg >= 3.5) return "good student";
  if (avg >= 2.5) return "average student";
  return "needs work";
}

function makeReport(name, marks) {
  const valid = marks.filter(isValidMark);     // passed the function as a value
  const avg = average(valid);

  return `${name}: ${valid.length} of ${marks.length}, `
    + `average ${avg.toFixed(2)} — ${verdict(avg)}, `
    + `fives ${valid.filter(isFive).length}`;
}

console.log(makeReport("Aman", [5, 4, 9, 3, 5, 0, 4, 5]));
console.log(makeReport("Meret", [3, 3, 4]));
console.log(makeReport("Gülnar", [9, 0, "five"]));
console.log(makeReport("Sapar", [5, 5, 4, 5]));
Aman: 6 of 8, average 4.33 — good student, fives 3
Meret: 3 of 3, average 3.33 — average student, fives 0
Gülnar: 0 of 3, average 0.00 — needs work, fives 0
Sapar: 4 of 4, average 4.75 — top student, fives 3

The numbers are the same as yesterday — and that is right: the form of writing does not affect behavior. The report line got shorter: we removed the word “marks”. Something else changed too.

The selection loop is gone. Instead of eight lines of selectValid — marks.filter(isValidMark). Yesterday’s technique works here: a function is passed as a value. Notice that isValidMark is written without parentheses — we pass the function itself, not the result.

Counting fives became one line too — valid.filter(isFive).length. The function countFives is no longer needed.

And verdict stayed a declaration, because it has four branches and an arrow would gain nothing.

Three experiments.

The first. Add curly braces to isFive: (mark) => { mark === MAX_MARK }. Run it and explain why everyone’s fives became zero.

The second. Move verdict to the bottom of the file, under the console.log calls. Does it work? Now make it an arrow function and move it again.

The third. Write makeStudent that returns the object { name, marks } with a short body. First without parentheses, then with them.

  1. Why does (n) => { n * 2 } return undefined?
    Answer Curly braces turn the body into a block, and in a block the implicit return does not work — an explicit return is needed. Without it the function returns undefined, like any function without return.
  2. How do you return an object with a short body, and why exactly this way?
    Answer () => ({ a: 1 }) — in parentheses. Without them the language reads { as the start of a block and a: as a label, and the function returns undefined.
  3. Why can a declaration be called before its line, but an arrow function cannot?
    Answer A declaration with function is hoisted together with its body. An arrow function is a value in a variable, and before the line of its declaration the variable is in the dead zone from day 4.
  4. What three things does an ordinary function have that an arrow function does not?
    Answer Its own this, the arguments object and the ability to be called with new. The first is the reason an arrow is not made into an object method.
  5. What is the difference between filter(isFive) and filter(isFive())?
    Answer The first passes the function itself, so that filter calls it for each element. The second calls it immediately and passes the result — most likely undefined or an error.
