# Day 21. Tasks

<Subtitle>Lessons 2 and 3, 90 minutes. Warm-up — 20 minutes, main tasks — 50 minutes, starred tasks — 20 minutes. Tasks 1–3 are done in the console, the rest in the folder `day-21`.</Subtitle>

## Warm-up

<Task title="1. From two arrays to objects" level="easy" time="6">
<Goal>feel the difference between a link by order and a link inside.</Goal>

```js
const items = ["bread", "tea", "butter"];
const prices = [3.5, 12, 25];
```

Build from them an array of objects of the form `{ name, price }` — by hand,
not automatically. Then sort **only** the array
`prices` from the source data and explain what happened to the matching.

<Hint>
It is enough to write three objects by hand. The main thing is to compare the two approaches
afterwards on one and the same operation: sorting.
</Hint>

<Criteria>
- the array of objects is written and printed;
- it is shown that after sorting `prices` the matching
  with `items` broke;
- it is shown that sorting the array of objects breaks nothing;
- the rule for choosing “an array or an object” is written down in your own words.
</Criteria>
</Task>

<Task title="2. Predict first: access and checks" level="easy" time="7">
<Goal>catch the difference between a dot, brackets and the three checks.</Goal>

```js
const student = { name: "Aman", phone: undefined };
const key = "name";

student.key;
student[key];
student.phone !== undefined;
"phone" in student;
Object.hasOwn(student, "phone");
Object.hasOwn(student, "toString");
"toString" in student;
Boolean({});
```

<Hint>
The first two lines differ by one character and give completely different things.
The last two pairs show how `in` differs from
`hasOwn` and why an empty object is a trap.
</Hint>

<Criteria>
- eight predictions are written down before checking;
- it is explained why `student.key` gives `undefined`;
- it is explained why the first check about `phone` lies;
- it is explained where the object gets `toString` from;
- it is written down how to check correctly that an object is empty.
</Criteria>
</Task>

<Hint>
Count the total cost from `Object.values` with yesterday’s

## Main tasks

<Goal>master merging objects and not spoil the source data.</Goal>

```js
const defaults = { city: "Mary", group: "1-A", year: 2026 };
const given = { name: "Aman", city: "Ashgabat" };
```

Build the full settings so that what the user set overrides
the defaults. Then check that `defaults` did not change — and show
a variant in which it **gets spoiled**.

<Hint>
The order of the arguments decides what overrides what. And the first argument decides
which object suffers.

<Criteria>

- `defaults` is printed before and after — it did not change;
- a call that spoils `defaults` is shown, and it is explained why;
- a function `makeSettings(given)` with a default

</Task>

<Task title="5. A copy that is not a copy" level="medium" time="13">
<Goal>see a reference and a shallow copy with your own eyes.</Goal>

```js
const student = {
  name: "Aman",
  marks: [5, 4],
  address: { city: "Mary", street: "Mir" },
};
```

Carry out three experiments, printing the original each time:

1. `const b = student;` — change `b.name`;
2. `const copy = Object.assign({}, student);` — change
   `copy.name`;
3. in the same copy change `copy.address.city` and add a mark
   to `copy.marks`.

<Hint>
The third experiment is the main one. The top level of the copy is independent, while the nested object
and array stayed shared. The array here behaves the same way as the object.
</Hint>

<Criteria>
- the state of the original is written down for all three experiments;
- it is explained why experiment 1 changed the original and experiment 2 did not;
- it is explained why experiment 3 changed the original in both cases;
- a way to copy `address` separately is suggested —
  and it is checked that now the original is intact;
- the rule is written down in one line: when `assign` is enough,
  and when it is not.
</Criteria>
</Task>

## Starred tasks

<Task title="8. Your own groupBy" level="hard" time="10">
<Goal>build an object by accumulation and check it against the built-in method.</Goal>

Write `myGroupBy(list, getKey)` with `reduce`
and test it on two data sets.

<Example>
```js
myGroupBy([5, 4, 3, 5, 2], (m) => m % 2 === 0 ? "even" : "odd");
// { odd: [5, 3, 5], even: [4, 2] }

myGroupBy(cart, (item) => item.price < 10 ? "cheap" : "expensive");
// { cheap: [...], expensive: [...] }
```
</Example>

<Hint>
The accumulator is an empty object. At each step check whether there is already such a key
(`Object.hasOwn`), create an empty array if needed
and do not forget to return the accumulator.
</Hint>

<Criteria>
- both examples give what is written;
- the result is checked against `Object.groupBy`;
- it is explained why the check “is there already such a key” is needed;
- it is tested on an empty list — what came back is written down;
- it is written down why the accumulator is an object and not an array.
</Criteria>
</Task>
