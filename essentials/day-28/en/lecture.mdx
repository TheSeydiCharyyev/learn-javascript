## 1. The page asks {#why}

Until now the data of the “Report card” lived in the code: first in arrays, then in a JSON string.
A student could be added only from the console. A real program takes data
from a person, and the main way to do that is a **form**: input fields, checkboxes,
radio buttons and a submit button.

We already have everything a form needs: finding a field (day 24), showing
an error (day 25), adding a row (day 26), responding to a click (day 27). Today
we add three things: the values of fields, the events of fields and submitting a form.

There are many kinds of fields in HTML, and almost all of them are one tag `<input>` with a different
`type` attribute:

| `type` | What it is | The main property |
| --- | --- | --- |
| `text` (or no `type`) | a line of text | `value` |
| `number`, `email`, `password`, `date` | text with browser hints | `value` |
| `checkbox` | a “yes or no” checkbox | `checked` |
| `radio` | a radio button, one of a group | `checked` |

## 2. The student form {#page}

```html
<form id="student-form">
  <label>Name: <input name="name" placeholder="For example, Ilýas"></label>
  <label>Marks: <input name="marks" placeholder="5 4 5"></label>
  <label><input type="checkbox" name="present" checked> was in class</label>
  <p>
    Group:
    <label><input type="radio" name="group" value="JS-1" checked> JS-1</label>
    <label><input type="radio" name="group" value="JS-2"> JS-2</label>
  </p>
  <button>Add</button>
  <button type="reset">Clear</button>
</form>
<p id="message"></p>
```

A few details of the markup that matter for the code:

| In the markup | Why |
| --- | --- |
| `name="…"` | the name of the field: the code finds the field by it, and the browser sends the data by it too |
| `<label>` around a field | a click on the label puts the cursor into the field or toggles the checkbox |
| `type="checkbox"`, `type="radio"` | a checkbox and a radio button; without `type` — a text field |
| the same `name="group"` | radio buttons in one group: only one is selected |
| `<button>` without `type` | **submits the form** — section 7 is about this |
| `placeholder` | a hint in an empty field; it is not the value |

A label has a second way to connect to a field — the `for` attribute with the field’s
`id` as its value. It is written this way when the label and the field stand in different places of the markup:

```html
<label for="name-field">Name:</label>
<input id="name-field" name="name">
```

The markup of the form is in `index.html`, and `app.js` has four lines
that are needed in all the sections:

```js
// app.js
const form = document.querySelector("#student-form");
const nameInput = form.elements.name;   // how to find fields — section 6
const present = form.elements.present;
const message = document.querySelector("#message");
```

Write the examples of the sections in the console. The examples of one section continue each other,
and before each new section reload the page (<Kbd>F5</Kbd>): the form
will return to its initial state, and the four variables from `app.js` will appear again.

## 3. `value`: the value of a field {#value}

An input field in the DOM is an `HTMLInputElement` object, one more level of the lineage
from day 25, below `HTMLElement`. Its main property is `value`,
what is typed in the field right now:

```js
nameInput.value;          // "" — nothing is typed yet
nameInput.placeholder;    // "For example, Ilýas" — a hint, not the value
nameInput.value = "Aman"; // write into the field from code
```

Two rules that all work with forms rests on.

**`value` is always a string.** Even if “5” is typed in the field,
it is the string `"5"`, like everything we read from the page on day 25. A number is made
from it with `Number` — more in section 12.

**Writing from code causes no events.** `nameInput.value = "Aman"`
changes the field silently: neither `input` nor `change` will come. Events
come only from a person’s actions. If code changes a field and something has to be recalculated,
the recalculation is called by hand, with the same function the listener uses.

A field also has the `type` property — `"text"`, `"checkbox"`,
`"radio"` and dozens of others: for numbers, dates, colors, passwords. All of them are one
interface, `HTMLInputElement`, and for all of them the value lies in `value`,
as a string.

```js
form.elements.marks.type = "number";   // or type="number" right in the markup
form.elements.marks.value = 5;         // we wrote a number…
form.elements.marks.value;             // "5" — …and read a string
```

A number field will not let you type letters and will show arrows, but it does not change the rule:
its `value` is a string too.

<Mistake>
The text of a field is `value`, not `textContent`.
`<input>` has no children, so its `textContent` is always
an empty string, whatever is typed. The habit from day 25 lets you down here.
</Mistake>

```js
nameInput.value = "Ilýas";
nameInput.textContent;   // "" — a field has no text children
nameInput.value;         // "Ilýas"
```

## 4. `checked`: checkboxes and radio buttons {#checked}

For a checkbox what matters is not the value but **whether it is checked**. That is the
`checked` property, `true` or `false`:

```js
present.checked;               // true — the markup has the checked attribute
// the person unchecked it:
present.checked;               // false
present.hasAttribute("checked");   // true — the attribute stayed!
```

The last line is a subtlety from MDN. The `checked` attribute in the markup sets
only the **default** state. The current state lives in the property.
This is a case where the attribute and the property from day 25 differ: the attribute remembers how it was
in the markup, the property — how it is now.

And a checkbox, like a text field, does not report changes made by code:

```js
present.addEventListener("change", () => console.log("change"));
present.checked = false;   // the checkbox is unchecked, but "change" is not printed
```

Radio buttons with one `name` work as a group: only one can be selected.
When one becomes `checked`, the others become `false` by themselves.
The selected value of the group is easiest to find through the form:

```js
form.elements.group.value;   // "JS-1"
// JS-2 was selected:
form.elements.group.value;   // "JS-2" — the value of the checked radio button
```

## 5. `input` and `change` {#input-change}

Fields have two main events. They differ in **when** they come.

<Scheme src="scheme-input-change.svg">input — “the value is changing”, change — “the value has changed and is accepted”</Scheme>

`input` comes **on every change** — on every letter,
deletion, paste. For a text field `change` comes **once**,
when the change is “accepted”: the person has left the field. For a checkbox and a radio button
`change` comes at once on a click.

```js
nameInput.addEventListener("input", () => {
  message.textContent = `Letters: ${nameInput.value.length}`;
});
// we type “Ilýas” — below the form in turn: Letters: 1, 2, 3, 4, Letters: 5
```

When to use which: **`input` — when the page must respond
on the fly**: a letter counter, live search (section 13), a hint below the field.
**`change` — when the result matters**: save the choice of a checkbox,
recalculate when the field is filled in. For checkboxes and radio buttons MDN advises exactly
`change`: `input` on them used to not come in all browsers.

```js
present.addEventListener("change", () => {
  message.textContent = present.checked ? "Was in class" : "Missed class";
});
// a click on the checkbox: “Missed class”, one more click — “Was in class”
```

## 6. The form and its fields {#form}

The form itself is an `HTMLFormElement` object. It has `elements` —
a collection of all the fields and buttons of the form, and a field is found in it **by name**:

```js
form.elements.name;      // <input name="name" …>
form.elements.marks;     // <input name="marks" …>
form.elements.present;   // the checkbox
form.elements.length;    // 7 — two fields, a checkbox, two radio buttons and two buttons
form.length;             // 7 — the same
```

This is more convenient than `querySelector`: the field is searched only inside this form, and the name
reads right in the code.

```js
for (const field of form.elements) {
  console.log(field.nodeName.toLowerCase(), field.type, field.name);
}
// input text name        input text marks       input checkbox present
// input radio group      input radio group      button submit      button reset

nameInput.form === form;   // true — every field knows its form
```

Walking over the fields comes in handy when there are many of them and the same thing has to be done with each —
for example, removing the error highlight from all of them. Every field has the back reference `form`:
in a field’s listener it leads straight to the whole form.

So why exactly `form.elements.name`, and not shorter — `form.name`?
MDN warns about a trap:

```js
form.name === form.elements.name;   // true — form.name returned the FIELD, not the name of the form!
```

The browser also makes the fields of a form its properties. The field named `name`
covered the form’s own `name` property. The same will happen with fields
`id`, `action`, `method`. MDN’s rule: **always
through `elements`**, and never name a field `"elements"`.
In the “Report card”, just in case, we will name the name field `student`.

## 7. The `submit` event {#submit}

When a form is submitted, it is the **form** — not the button — that gets the event
`submit`. It is listened for on the form:

```js
form.addEventListener("submit", (event) => {
  event.preventDefault();   // the main line — section 8
  console.log("sending", form.elements.name.value);
});
```

A form can be submitted in three ways, and all three lead to one `submit`:

| What the person did | What happened |
| --- | --- |
| clicked a `<button>` without `type` | `click` on the button, then `submit` on the form |
| pressed <Kbd>Enter</Kbd> in a text field | the browser “clicks” the first submit button — the same `click` and `submit` |
| clicked a `<button type="submit">` | the same as without `type` |

That is why submitting is listened for through the form’s `submit`, not through the button’s `click`:
a click listener would miss <Kbd>Enter</Kbd>. The event object here is
`SubmitEvent`, a descendant of `Event`.

MDN spells out the rule for <Kbd>Enter</Kbd>. If the form has a submit
button, <Kbd>Enter</Kbd> in a text field always submits the form. If there is
no button, the form is submitted only when it has a single text field. A search form
of one field works without a button, while a form of two fields without a button will not be submitted by
<Kbd>Enter</Kbd>.

```js
form.querySelector("button").addEventListener("click", () => console.log("click"));
form.addEventListener("submit", (event) => {
  event.preventDefault();
  console.log("submit", event.target.nodeName);
});
// a click on “Add”:          click, “sending …” from the example above, then submit FORM
// Enter in the name field:   the same — the browser “clicked” the button itself
```

<Mistake>
A `<button>` inside a form **submits it by default**.
A “Show a hint” button in a form without `type="button"` will submit
the form on every click. Buttons that must not submit get
`type="button"`.
</Mistake>

## 8. Walkthrough: the page reloaded {#reload}

We wrote a `submit` listener without `preventDefault`:

```js
form.addEventListener("submit", () => {
  message.textContent = "Added!";       // flashes for a split second — and disappears
});
```

We filled in the form and pressed “Add”. The page blinked, the fields became empty, the console is empty.

<Scheme src="scheme-reload.svg">The browser’s default action for a form is to submit and reload. We cancel it</Scheme>

**Step 1. We look at the address.** At its end there is now
`?name=…&marks=5+4+5&present=on&group=JS-1`. This is the form data:
the browser collected it by the `name` attributes and sent it. Spaces became pluses,
the checked checkbox — the word `on`.

**Step 2. We understand what happened.** `submit` has a default
action (day 27): send the data where the form points and open the
response as a new page. Our form has no address, so the browser opened the same page
anew — with clean fields and untouched code. Everything our listener managed to do
was gone together with the old page.

**Step 3. We fix it.** The first line of any `submit` listener is
`event.preventDefault()`. We will learn to talk to a server without reloading the page
on day 31 — with `fetch`.

## 9. Your own input validation {#validate}

A person may press “Add” without filling anything in, or type only spaces.
Before working with data, it is checked — and an error is reported **on the page**,
next to the form, not in the console, which the person does not see.

```js
form.addEventListener("submit", (event) => {
  event.preventDefault();
  const name = form.elements.name.value.trim();   // spaces at the edges do not count

  if (name === "") {
    message.textContent = "Enter a name";
    form.elements.name.focus();                   // the cursor — to where the error is
    return;
  }

  message.textContent = `Added: ${name}`;
  form.reset();                                   // section 11
});
```

This code follows the order that all checks keep to.

<Step n="1" numberTag="span">
**Stop the browser**:
`preventDefault` as the first line, before all the checks.
</Step>

<Step n="2" numberTag="span">
**Read and clean**:
`trim` from day 16 — otherwise “&nbsp;&nbsp;&nbsp;” will pass as a name.
</Step>

<Step n="3" numberTag="span">
**Check one reason
at a time**: found an error — wrote a clear message, put the focus into the right field
(`focus` from day 27) and left through `return`.
</Step>

<Step n="4" numberTag="span">
**Only then work**
with the data — and clear the old error message.
</Step>

Which checks are usually needed — from the most common to rare:

| Check | An example in code |
| --- | --- |
| the field is not empty | `value.trim() === ""` |
| length | `value.trim().length < 2` |
| a number and its bounds | `Number.isInteger(n) && n >= 2 && n <= 5` |
| no repeat | `reports.some((r) => r.name === name)` |

This is the same order as for someone else’s JSON on day 23: check what came, and only
then trust it. Data from a form is the most foreign of all: a person types it.

### Highlighting a field and removing the highlight

A message below the form is good, but it is even better when the field with the error itself stands out. A class
from day 25 — and a rule in `<style>`:

```html
<style>
  .invalid { outline: 2px solid #b91c1c; }
</style>
```

```js
const nameField = form.elements.name;

form.addEventListener("submit", (event) => {
  event.preventDefault();
  if (nameField.value.trim() === "") {
    nameField.classList.add("invalid");
    message.textContent = "Enter a name";
    return;
  }
  message.textContent = "Done";
});

nameField.addEventListener("input", () => {
  nameField.classList.remove("invalid");   // the person started fixing it —
  message.textContent = "";                // we remove the error at once
});
```

The second listener is good manners: the highlight disappears with the first typed letter,
and does not hang there until the next submit. Here `input` does exactly what
it was made for — responding on the fly.

## 10. The browser’s validation: `required` {#required}

The browser can do some of the checks itself. The `required` attribute makes a field
mandatory:

```html
<input name="name" required>
```

```js
form.addEventListener("submit", () => console.log("submit"));
// the field with required is empty: a click on “Add” — silence in the console,
// and the browser’s hint at the field
```

If such a field is empty, the browser **will not submit the form**: it shows a hint
at the field in the browser’s language — “Please fill out this field.” — and `submit` does not happen at all,
our listener is not called. There are similar attributes for numbers, email addresses, text length.

Built-in validation is convenient, but it does not replace your own. It does not know the rules of the “Report card”: that
marks are digits from 2 to 5, that a name must not repeat. Usually they are combined: the simple things —
with attributes, the rest — with code in `submit`. Course 4 covers built-in validation
in detail.

## 11. `reset`: back to how it was {#reset}

The `form.reset()` method returns all the fields to their **default** values —
to the ones written in the markup. A `type="reset"` button does the same.

```js
form.elements.name.value = "Ilýas";
form.elements.present.checked = false;

form.reset();
form.elements.name.value;        // "" — the markup had no value
form.elements.present.checked;   // true — the checked attribute stayed in the markup
form.elements.group.value;       // "JS-1"
```

This is where the difference between the attribute and the property from section 4 comes in handy: `reset`
restores what the **attribute** remembers. The form also gets
a `reset` event. After a successful submit the form is usually cleared exactly this way —
in one line instead of emptying every field.

```js
form.addEventListener("reset", () => {
  message.textContent = "";   // remove the message together with the fields
});
```

## 12. Walkthrough: the mark became a string {#numbers}

```js
const marksInput = form.elements.marks;   // we typed “5”

marksInput.value + 1;           // "51" — but we expected 6
Number(marksInput.value) + 1;   // 6
```

**Step 1.** The answer is two digits side by side. This is string concatenation (day 8), not addition.

**Step 2.** `value` is always a string (section 3). `"5" + 1`
concatenates.

**Step 3.** A number is obtained with `Number` when reading — as with
`dataset` on day 25. But `Number` has its own surprises for input fields:

```js
Number("");      // 0 — an empty field became zero!
Number(" ");     // 0 — and so did a field of spaces
Number("5 ");    // 5 — spaces at the edges do not get in the way
Number("4,5");   // NaN — a comma does not work, a dot is needed
Number("4.5");   // 4.5
```

The first two lines are the most dangerous: an empty field does not give `NaN`, which is easy to
notice, but quietly turns into a mark of 0. That is why an empty field is checked **before**
converting to a number, with a separate condition. And many people write fractions with a comma out of habit —
in Turkmen and Russian, for example. If a field expects a fraction, it is worth saying so in the `placeholder` hint.

### Several marks in one field

In the “Marks” field several digits are typed separated by spaces: “5 4 9”. The `split` method
can break a string at the spaces, but that is course 2. Our marks are one digit each, so it is enough
to walk the string character by character — strings are walked this way since day 11 — and throw out the spaces:

```js
[..."5 4 9"].filter((ch) => ch !== " ");   // ["5", "4", "9"]
```

We got strings, not numbers — and that is what we need. `makeReport` from day 23
converts every mark to a number itself and discards the invalid ones: the nine will not pass
the check, but it will be counted in the percentage of valid marks.

And what if a person puts commas — “5,4,5”? The commas will become separate “marks”:

```js
[..."5,4,5"].filter((ch) => ch !== " ");
// ["5", ",", "4", ",", "5"] — makeReport: average 4.67, but only 60% valid

[..."5,4,5"].filter((ch) => ch !== " " && ch !== ",");
// ["5", "4", "5"] — 100% valid
```

Whether to fix such input silently or report an error is the programmer’s decision. The main thing is
to notice the case itself: input validation starts with the question “what else can a person type”.
In the “Report card” we will keep the simple option and hint at the format right in the field: “Marks: 5 4 5”.

### The whole form in one object

When there are many fields, it is convenient to collect them into an object at once — one for the whole form. The rest
of the program works with it, and it can also be saved or sent as JSON
from day 23:

```js
// filled in: Ilýas, “5 4 9”, the checkbox unchecked, JS-2
const data = {
  name: form.elements.name.value.trim(),
  marks: [...form.elements.marks.value].filter((ch) => ch !== " "),
  present: form.elements.present.checked,
  group: form.elements.group.value,
};

JSON.stringify(data);
// '{"name":"Ilýas","marks":["5","4","9"],"present":false,"group":"JS-2"}'
```

This is the same division that the “Report card” made on day 23: the form is responsible for input,
the object for data, and further on the code works only with the object.

## 13. Live search {#live}

The `input` event lets the page respond on the fly. Let us add a search field above the list
of students from day 24 — and hide those who do not match:

```html
<input id="search" placeholder="Search">
<p id="count"></p>
```

```js
const search = document.querySelector("#search");
const items = document.querySelectorAll("#list li");

search.addEventListener("input", () => {
  const query = search.value.trim().toLowerCase();
  items.forEach((li) => {
    li.hidden = !li.textContent.toLowerCase().includes(query);
  });
});
// “a” — Aman, Gülnar, Sapar, Oguljan; “man” — only Aman; “  MERET” — Meret
```

You can also show how many were found. The paragraph is found once, and the last two lines
go at the end of the same listener:

```js
const count = document.querySelector("#count");   // the paragraph below the search field
const shown = [...items].filter((li) => !li.hidden).length;
count.textContent = `Found: ${shown}`;
```

Three modules came together here. Strings from day 16: `trim`, `toLowerCase`
and `includes` — a search that ignores case and extra spaces. Finding elements
from day 24 and `hidden` from day 25. And `input` from today.
An empty query shows everyone: any string contains the empty string.

## 14. `alert`, `confirm`, `prompt` {#dialogs}

The browser has three ready-made dialog windows. All of them are **modal**: while the window
is open, the page stands still, and the code waits for an answer.

<Scheme src="scheme-dialogs.svg">The three dialogs of the browser: tell, ask “yes or no”, ask for a string</Scheme>

```js
alert("Saved");                   // undefined — a window with an OK button
confirm("Delete Meret?");         // true — OK was pressed, false — Cancel
prompt("Your name?", "Guest");    // "Ilýas" — typed; "" — OK with an empty field; null — Cancel
```

`prompt` has three different answers, and they have to be told apart: an empty string —
the person agreed but typed nothing; `null` — refused to answer.
The second argument is the text that is already in the field.

`confirm` almost always stands right in a condition:

```js
if (confirm("Clear the form?")) {
  form.reset();
}
```

And the answer of `prompt` must be checked for `null` before anything else,
otherwise Cancel will crash the program:

```js
const answer = prompt("What is your name?");
answer.trim();   // Cancel was pressed: TypeError: Cannot read properties of null (reading 'trim')

const name = answer === null ? "" : answer.trim();   // this way it is safe
```

MDN advises using dialogs with care. They stop the whole page,
look not like the site but like a window of the browser, and the browser may not show them at all —
for example, if the tab is not active. So:

| Dialog | When it fits | What to replace it with |
| --- | --- | --- |
| `alert` | a quick check while debugging | a message on the page through `textContent` |
| `confirm` | confirming something irreversible: delete, erase everything | fine as it is for study projects |
| `prompt` | almost never | a field in a form |

In the “Report card” `confirm` will stand before deleting a row. Deleting cannot be undone,
and a click on the “Delete” button is easy to make by accident — exactly the case
`confirm` exists for. Input error messages, though, the “Report card” will show on
the page, not in `alert`.

## 15. The “Report card” with a form {#tabel}

Now a student can be added without the console. Above the table — a form, below it — a place
for an error message:

```html
<form id="add-form">
  <input name="student" placeholder="Name">
  <input name="marks" placeholder="Marks: 5 4 5">
  <button>Add</button>
</form>
<p id="form-error" class="error"></p>
```

```js
// unchanged: everything from day 27 — the calculation, makeCells, the classes, makeRow,
// addDeleteButton, updateSummary, the tbody and Esc listeners

// new: marks from a string “5 4 9” — one digit each, without spaces
function parseMarks(text) {
  return [...text].filter((ch) => ch !== " ");
}

const form = document.querySelector("#add-form");
const error = document.querySelector("#form-error");

function fail(message, field) {
  error.textContent = message;
  field.focus();
}

form.addEventListener("submit", (event) => {
  event.preventDefault();                               // otherwise the page will reload
  const name = form.elements.student.value.trim();
  const marks = parseMarks(form.elements.marks.value);

  if (name === "") {
    fail("Enter a name", form.elements.student);
    return;
  }
  if (reports.some((r) => r.name === name)) {
    fail("This student already exists", form.elements.student);
    return;
  }
  if (marks.length === 0) {
    fail("Enter at least one mark", form.elements.marks);
    return;
  }

  const report = makeReport({ name, marks });
  reports.push(report);
  tbody.append(addDeleteButton(makeRow(report)));
  updateSummary();

  error.textContent = "";
  form.reset();
  form.elements.student.focus();
});
```

Three checks in a row do the same thing: write a message and put the cursor into a field.
This repetition is moved into a small function `fail` — the same way that on day 15
we split the “Report card” into functions by meaning. Each check became short,
and the message and the field are visible in one line.

And one new line in the `tbody` listener from day 27 — a confirmation
before deleting:

```js
tbody.addEventListener("click", (event) => {
  const row = event.target.closest("tr");
  if (event.target.closest(".delete")) {
    if (!confirm(`Delete ${row.dataset.name}?`)) return;     // new
    const i = reports.findIndex((r) => r.name === row.dataset.name);
    reports.splice(i, 1);
    row.remove();
    updateSummary();
    return;
  }
  row.classList.toggle("selected");
});
```

## 16. Common mistakes and the module summary {#mistakes}

| Mistake | What you will see | How to do it right |
| --- | --- | --- |
| no `preventDefault` in `submit` | the page reloaded, the data is in the address | as the first line of the listener |
| listening for the button’s `click` instead of `submit` | <Kbd>Enter</Kbd> does not work | `submit` on the form |
| `<button>` without `type` for another job | the button submits the form | `type="button"` |
| `value + 1` | `"51"` | `Number(value) + 1` |
| no `trim` | a name of spaces passes the check | `value.trim()` |
| `form.name`, `form.id` | a field instead of the property of the form | `form.elements.…` |
| waiting for `input` after writing from code | the event did not come | call the recalculation yourself |
| an error through `alert` | the window gets in the way, the page stands still | a message on the page |
| `prompt` without a check for `null` | an error when Cancel is pressed | check for `null` first |

<Selfcheck>
1. Why did `form.elements.marks.value + 1` give `"51"`?
   <Answer>`value` is always a string, and `+` with a string concatenates.
   You need `Number(form.elements.marks.value) + 1`.</Answer>
2. How does `input` differ from `change` for a text field?
   <Answer>`input` comes on every change, on every letter.
   `change` — once, when the person has left the field with a changed value.</Answer>
3. Why is submitting listened for on the form through `submit`, and not through
   the button’s `click`?
   <Answer>A form is also submitted with the Enter key in a field. `submit` comes
   with any way of submitting, while a click listener would miss Enter.</Answer>
4. What happens without `event.preventDefault()` in a `submit` listener?
   <Answer>The browser sends the data and loads the page anew: the fields are cleared,
   everything done by code is lost, the form data ends up in the address.</Answer>
5. Why is `form.elements.name` better than `form.name`?
   <Answer>The fields of a form also become its properties. The field named `name`
   covers the `name` property of the form — and the other way round, confusion
   is inevitable. `elements` contains only the fields.</Answer>
6. How do the answers of `prompt` differ: `""` and `null`?
   <Answer>`""` — OK was pressed with an empty field. `null` — Cancel was pressed.</Answer>
</Selfcheck>
