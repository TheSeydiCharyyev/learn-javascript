# Day 29. Mini project: a to-do list

<Subtitle>A summary of the lecture: how the program is built and how to check that the project is ready.</Subtitle>

## The five parts of the program

```js
// 1. The data — everything the look of the page depends on
let tasks = [
  { id: 1, text: "Review day 26", done: true },
  // … every task has id, text and done
];
let nextId = 4;
let filter = "all";

// 2. The elements of the page — we find them once
const list = document.querySelector("#tasks");

// 3. Showing: the page is built from the data
function render() {
  list.textContent = "";
  list.append(...tasks.filter(isVisible).map(makeItem));
  // the counter and the buttons — from the data too, over all the tasks
}

// 4. Actions: understand what happened → change the data → render()
// 5. The first showing
render();
```

<KeyPoint>
The page is a picture of the data. A listener does not fix the list itself: it changes
`tasks` or `filter` and calls `render()`. One action
changes the list, the counter and the buttons at once — when one function builds everything, the page will not
drift apart from the data.
</KeyPoint>

`makeItem(task)` makes one item out of one object and only returns it.
The data goes in through `textContent`, the class through `classList.toggle("done", task.done)`,
and in `data-id` the item remembers the number of its task.

## From an element to the data

```js
function taskOf(element) {
  const id = Number(element.closest("li").dataset.id);   // "2" → 2
  return tasks.find((t) => t.id === id);
}

// in the click listener on the list — delete the clicked task:
const task = taskOf(event.target);
tasks = tasks.filter((t) => t !== task);   // all but it; that is why let
```

<Remember>
Everything in `dataset` is strings: without `Number` the comparison
`"2" === 2` is false and `find` returns `undefined`.
The link “item — task” is built only through `id`: a position in the list changes
because of filtering and deleting, an `id` — never.
</Remember>

## Mistakes by their symptoms

| Symptom | Cause |
| --- | --- |
| the neighboring task was deleted | the item has a position number instead of `id` |
| `Cannot set properties of undefined` | a string against a number in `find` |
| the data changed, the page did not | `render()` was forgotten |
| `Assignment to constant variable.` | `const tasks`, while deleting assigns a new array |

For any oddity the first question is **what is in the data?** Ask the console:
`tasks`. If the data is right and the page is not, look for `render`.

## A readiness checklist

The project is ready when every row has been checked by hand on a clean page.

| What to check | How |
| --- | --- |
| the first showing | three tasks, the first one crossed out, “Left: 2 of 3” |
| adding | the task is at the end of the list, without spaces at the edges, the field was cleared |
| input validation | empty and only spaces — a message; 60 characters are allowed, 61 are not |
| marking | the checkbox crosses out and removes the crossing out, the counter changes |
| deleting | “✕” deletes exactly the clicked task under any filter |
| filters | the current one is highlighted; the counter does not depend on the filter |
| “Clear done” | visible only when there is something to delete |
| <Kbd>Esc</Kbd> | clears the field and the message |
| a text with markup | `<b>` in a task is visible as text |
| the console | no errors; `tasks` matches the page after every action |

## How to extend it

Any improvement fits into the same scheme: a new field or variable in the data
(`important`, `query`), a line in `makeItem` or
`isVisible`, a new listener that changes the data and calls `render`.
There is no saving yet: reload the page — the initial tasks are back. We will add it on day 31.
