## 1. The four days of the final project {#why}

All the new topics of the course are behind us. Four days are left, and in them everyone will build their own
application — from the idea to the defense. We built the mini projects of days 29 and 32 together from a ready
assignment. Now you come up with the assignment yourselves, and this is the main skill the final
project checks.

| Day | What we do | What is ready at the end |
| --- | --- | --- |
| 33 | the idea, data, mockup, skeleton, plan | the page shows the first data from the server |
| 34 | implementation according to the plan | all the features from the table work |
| 35 | polishing, checking on a phone, reading someone else’s code | an application you are not ashamed to show |
| 36 | the defense: a demo and an explanation of the decisions | you explain any line of your code |

What to come to the defense with is known in advance — the goal is visible from the first day:

| At the defense they look at | How it shows |
| --- | --- |
| what was promised works | the author goes through the feature table row by row |
| the data lives in data | the page is built from an array, not written in the markup |
| the code is readable | functions are named by meaning, there is a `render`, listeners change the data |
| the author understands the decisions | explains any line and any choice of storage |
| honesty | names by themselves what they did not manage and why |

Today’s lecture goes by an example: together we will plan the application “Word cards”
and make the first working step in it. On days 34–35 this example will keep growing — as
a model — while you build your own. The whole path of the day:

Code appears only at the sixth step — and this is no accident. A mistake in the idea
costs one line of text to fix, a mistake in a finished program — hours. That is why the first
half hour of the final project goes into decisions, not typing.

## 2. An idea: how to choose {#idea}

A good idea for the final project meets four conditions. **There is a list of
data** — books, words, dishes, events: the application shows them. **A person
does something** — searches, marks, chooses. **Something is remembered**
between page loads. And **you yourself are interested**: two days of work on a boring idea
drag on twice as long.

| Idea | Data | What a person does | What it remembers |
| --- | --- | --- | --- |
| word cards | words with a translation | flips them, marks the learned ones | the learned ones |
| a cafe menu | dishes and prices | searches, builds an order | the order |
| an events listing | events and dates | filters by day, marks “I’ll go” | the marks |
| a quiz | questions and answers | answers against the clock | the best result |
| a reference guide | plants, animals, countries | searches, filters | favorites |
| a timetable | lessons by day | picks a day, marks homework | the marks |
| a habit tracker | one’s own habits | marks days | everything |
| a shopping list | one’s own items | adds, marks what was bought | the list |

For the first six the data comes from a server, as in the catalog of day 32. For the last two
the person creates the data, as in the to-do list of day 29. Both work. You can take
an idea from the table or come up with your own — as long as it meets the four conditions.

An idea can also be too small. “A button that shows a random quote” is
an exercise, not a project: it has no search, no choice and no memory. Add
favorite quotes and a filter by author to it — and you get a project.

## 3. The idea in one sentence {#sentence}

Before writing out the details, the idea is checked with one sentence:
**who** the application is for, **what** it does and **why**.
If it does not fit into one sentence, the idea is vague or too big.

<ResultBox>
“Word cards” — for a school student who is learning English: they show a word, and on a click —
the translation; the student marks “I know” or “Again”, and learned words are not
shown any more, even after the page is reloaded.
</ResultBox>

Almost the whole plan is already hidden in this sentence. “Show a word” — data and
a showing function are needed. “On a click — the translation” — a listener and a variable “is the card flipped”.
“Marks” — two more listeners. “Even after the page is reloaded” — storage. Every word of
the idea will become a row of the feature table.

For comparison — an idea from another row of the ideas table: “Cafe menu — for a visitor
who is choosing lunch: it shows dishes with prices, searches by name, builds an order and
counts the total; the order does not disappear if the tab is closed by accident”. Who — a visitor;
what — a menu, search, an order, a total; why — to choose lunch. All three parts are in place.

## 4. What the application must be able to do {#spec}

The features are written down as a table, as on days 29 and 32. The main rule: every row
has a way to check it that a person who has never seen your code can carry out.

| No. | Feature | How to check |
| --- | --- | --- |
| 1 | load the words from the server | “Loading…”, then the first word |
| 2 | report a loading error | the file is renamed — a clear text |
| 3 | flip a card | a click on the card — the translation, one more click — the word |
| 4 | “I know” | the word disappears from the deck, the counter grows |
| 5 | “Again” | the next word is shown, this one will come back later |
| 6 | pick a topic | topic buttons from the data, the deck has only the words of the topic |
| 7 | a counter “Learned: N of M” | changes after every “I know” |
| 8 | remember the learned words | reloaded the page — there are no learned words in the deck |
| 9 | start over | a button brings back all the words |

Two extra lines are no less important. **Later, if time is left:**
shuffle the deck, a “translation → word” mode. **Does not do at all:** does not add
words (only the owner of the file changes them), does not pronounce them (that is course 4). The “later” list
is your reserve: if an hour is left on day 35, there will be something to add, and if not, the application
is ready anyway.

## 5. The data on the server {#data}

The folder `day-33/cards`, we open it through Live Server. The data is the file
`words.json`, eight words of three topics:

```js
[
  { "id": 1, "word": "book", "translation": "kitap", "topic": "school" },
  { "id": 2, "word": "teacher", "translation": "mugallym", "topic": "school" },
  { "id": 3, "word": "lesson", "translation": "sapak", "topic": "school" },
  { "id": 4, "word": "bread", "translation": "çörek", "topic": "food" },
  { "id": 5, "word": "water", "translation": "suw", "topic": "food" },
  { "id": 6, "word": "apple", "translation": "alma", "topic": "food" },
  { "id": 7, "word": "house", "translation": "jaý", "topic": "home" },
  { "id": 8, "word": "window", "translation": "penjire", "topic": "home" }
]
```

We choose the fields by the feature table: `word` and `translation` are needed by
the card, `topic` by the topic buttons, `id` by storage, to remember
the learned ones. There are no extra fields: each one is used by something. There is little data to start with — eight
words — but it makes everything easy to check by hand. A hundred more can be added at any moment,
the code will not change because of it.

How much data is needed to start? Enough to have something to check every feature with:
at least two topics (otherwise there is nothing to choose), a few words in each (otherwise the deck
runs out in two clicks), and at least one topic smaller than the others. Six to ten objects are usually
enough.

## 6. Check the data before the code {#check-data}

A data file is written by hand, and hands make mistakes. That is why the data is checked at once, while
`app.js` does not have a single line. First let us look at it with our eyes — with the table from day 2:

```js
const data = await (await fetch("words.json")).json();
console.table(data);   // a table: eight rows, the columns id, word, translation, topic
data.length;           // 8
```

Eight rows can be checked by eye, a hundred cannot. For that there is
`console.assert` from day 2: it is silent if the condition is true, and prints a red
line marked *Assertion failed* with our text if it is not. The first check —
every word has all four fields:

```js
console.assert(
  data.every((w) => w.id && w.word && w.translation && w.topic),
  "a word is missing a field"
);
// silence — all the fields are in place
```

The second — the numbers do not repeat. A word with a number stands in its own place if
`findIndex` finds this number for the first time exactly there:

```js
console.assert(
  data.every((w, i) => data.findIndex((x) => x.id === w.id) === i),
  "numbers repeat"
);
// silence — the numbers are different
```

The third — which topics there are and how many words each has. The “without repeats” technique of day 32:

```js
const names = [];
data.forEach((w) => {
  if (!names.includes(w.topic)) names.push(w.topic);
});
names;   // ["school", "food", "home"]
```

```js
names.map((t) => `${t}: ${data.filter((w) => w.topic === t).length}`);
// ["school: 3", "food: 3", "home: 2"]
```

Five minutes of such checks save an hour of searching later. A mistake in the data found
now is an edit of one line in the file. Found on day 35, it looks like a mistake
in the code, and it will be looked for in the code.

## 7. Walkthrough: data “by eye” {#bad-data}

Here is the same file typed in a hurry — `words-bad.json`. At first glance everything
is fine. Let us run the same checks:

```js
const bad = await (await fetch("words-bad.json")).json();
// the same two console.assert checks — on bad instead of data:
// Assertion failed: a word is missing a field
// Assertion failed: numbers repeat
// and the list of topics:
// ["school", "food", "Food", "home"]
```

**Step 1. What is wrong?** Two red lines and an extra topic. Which
word lacks a field, `find` will tell:

```js
bad.find((w) => !w.translation);
// {id: 8, word: 'window', translation: '', topic: 'home'}
```

**Step 2. Three mistakes — three future symptoms.** An empty translation — the card
“window” will flip into emptiness. The number 5 repeated at “water” and “apple” — “I know” at one word
will mark both as learned: favorites and learned words keep numbers. “Food” with a capital letter — an extra
topic button, and “food” will have two words instead of three. When the function `deck` from
section 12 is ready, both symptoms are visible right in the console:

```js
words = bad;
learned = [5];                // “I know” at water
deck().map((w) => w.word);   // ["book", "teacher", "lesson", "bread", "house", "window"] — two words are gone

learned = [];
topic = "food";
deck().map((w) => w.word);   // ["bread", "apple"] — water is hiding in the topic “Food”
```

**Step 3. We fix it — and leave a guard.** Fixing the file is not enough: tomorrow it
will be edited again. We move the checks into `app.js` itself, into a function that
runs after every loading. While the data is fine, it is silent:

```js
function checkData() {
  console.assert(words.length > 0, "there are no words");
  console.assert(words.every((w) => w.id && w.word && w.translation && w.topic), "a word is missing a field");
  console.assert(words.every((w, i) => words.findIndex((x) => x.id === w.id) === i), "numbers repeat");
}
```

## 8. Where what lives {#state}

The next decision is what data the program keeps and where. The method is the same as in the catalog:
every kind of data gets its own place.

| Data | Where | Why |
| --- | --- | --- |
| words | the server: `words.json` | shared by everyone, changed by the owner of the file |
| learned | `localStorage` | personal progress, needed tomorrow too |
| the topic, the card number, whether it is flipped | variables | needed only now |

```js
const KEY = "cards:learned";
let words = [];                                              // will come from the server
let learned = JSON.parse(localStorage.getItem(KEY)) ?? [];   // the numbers of learned words
let topic = "all";                                           // the selected topic
let position = 0;                                            // which card of the deck is current
let flipped = false;                                         // whether the translation is visible
```

Six lines — and all the decisions of the table are already written in them. The variables
`position` and `flipped` will not be needed today, but they are worth declaring
now: this shows that the whole idea fits into the data. If some feature did not get
a variable, the plan is not thought through. Checking the step:

```js
[words.length, learned, topic];   // [0, [], "all"]
```

## 10. The skeleton: stub functions {#skeleton}

Now — the list of functions. They are not written in full but declared as **stubs**:
a name, one line about what the function does, and the simplest body. Such a skeleton shows
how the whole program is built even before it works:

```js
// the deck: the words of the selected topic that are not learned yet
function deck() {
  return [];   // a stub — of the same type as the real answer
}

// topic buttons from the data — like the genres on day 32
function makeTopicButtons() {
  // day 34
}

// the page from the data
function render() {
  // day 33, section 12
}

async function load() {
  // day 33, section 12
}

load();
```

The skeleton can already be opened in the browser: there are no errors, simply nothing happens. And the list
of functions becomes a list of tasks: every stub will have to be replaced with a real body.

The listeners are declared the same way — one for every row of the feature table where
a person does something. Inside — a plan comment in the scheme of day 29: what to change in the data,
and call `render`:

```js
card.addEventListener("click", () => {
  // day 34: flipped = !flipped; render();
});
knowButton.addEventListener("click", () => {
  // day 34: the card’s number — into learned, save, render();
});
againButton.addEventListener("click", () => {
  // day 34: position — to the next card, render();
});
```

Click the card — nothing happens, and there are no errors: the listener is there, the body is not yet.
But the comments have already written down the decisions, and on day 34 all that is left is to turn them into code.

### A stub must return the same as the real function

The stub `deck` returns an empty array, not “nothing”. The difference shows as soon as
other code starts using it. Here is a stub without `return` and
a `render` that already needs the length of the deck:

```js
function deck() {
  // day 34
}
// on the page after loading:
// Could not load the words: Cannot read properties of undefined (reading 'length')
```

A function without `return` returns `undefined` (day 12), and that has
no length. A stub that returns an empty array honestly says “the deck is empty for now”,
and everything after it works. The rule: **a stub returns a value of the same
type** — an empty array, zero, an empty string.

## 11. Checks before the code {#tests}

Since we know what `deck` must do, we can write it down as checks before
the function itself. In the console of the page with the skeleton let us load the words by hand and ask
the stub:

```js
words = await (await fetch("words.json")).json();
console.assert(deck().length === 8, "at first — all 8 words");
learned = [1, 2];
console.assert(deck().length === 6, "learned words do not get into the deck");
topic = "food";
console.assert(deck().every((w) => w.topic === "food"), "only the words of the topic");
console.assert(deck().length === 3, "the topic “food” has three words");
// Assertion failed: at first — all 8 words
// Assertion failed: learned words do not get into the deck
// Assertion failed: the topic “food” has three words
```

Three red lines out of four — and that is good: the checks see that the function does not exist yet.
But why is the third one silent? The stub returned an empty array, and `every` on an empty
array always answers `true` — we saw this on day 20:

```js
[].every((w) => w.topic === "food");  // true — in an empty array nothing can fail to fit
```

The check “all fit” proves nothing if there is nobody to fit. That is why next to
it there is a length check: together they say “the deck has three words, and all of them are about food”.
Good checks are chosen so that **the stub fails them**: otherwise they
will not tell a finished function from an empty one.

### Checks that can be repeated

Typing four checks after every edit is tiring. They are put into a function —
in `app.js`, next to the function being checked. The function changes the data for the time of the check and
puts it back as it was:

```js
function testDeck() {
  const oldLearned = learned;
  const oldTopic = topic;
  learned = [];
  topic = "all";
  console.assert(deck().length === 8, "at first — all 8 words");
  learned = [1, 2];
  console.assert(deck().length === 6, "learned words do not get into the deck");
  topic = "food";
  console.assert(deck().every((w) => w.topic === "food"), "only the words of the topic");
  console.assert(deck().length === 3, "the topic “food” has three words");
  learned = oldLearned;   // put it back as it was
  topic = oldTopic;
}
```

Now after any edit of `deck` it is enough to type
`testDeck()` in the console. The checks with the numbers “8”, “6”, “3” know our data, so
they are run on the study `words.json`: add words — fix the numbers too.

## 12. The first working step {#first}

Now we replace the stub with a real function. The deck is the words that are not among the
learned ones and that fit the topic:

```js
function deck() {
  return words.filter((w) => !learned.includes(w.id) && (topic === "all" || w.topic === topic));
}
```

Let us save `app.js` — Live Server will reload the page. `load` is still
a stub, so we load the words by hand again and run the checks:

```js
words = await (await fetch("words.json")).json();
testDeck();
[learned, topic, deck().length];   // [[], "all", 8] — the checks are silent, the data is the same
```

Not a single red line, and `testDeck` put everything back as it was. And the deck of the topic
“food” with 1 and 2 learned:

```js
learned = [1, 2];
topic = "food";
deck().map((w) => w.word);   // ["bread", "water", "apple"]
```

What is left is to show the first word on the page. `render` is minimal for now: the word
of the first card of the deck and the counter. Flipping, buttons and topics are tasks of day 34:

```js
function render() {
  const cards = deck();
  card.textContent = cards.length > 0 ? cards[0].word : "No words";
  counter.textContent = `Learned: ${learned.length} of ${words.length}`;
}
```

```js
async function load() {
  try {
    const response = await fetch("words.json");
    if (!response.ok) throw new Error(`server replied ${response.status}`);
    words = await response.json();
    checkData();
    makeTopicButtons();
    render();
  } catch (err) {
    error.textContent = `Could not load the words: ${err.message}`;
  } finally {
    loading.hidden = true;
  }
}
```

`load` is almost word for word from the catalog of day 32, with the guard
`checkData` right after loading. Checking the step after reloading the page:

```js
[card.textContent, counter.textContent, loading.hidden];
// ["book", "Learned: 0 of 8", true]
```

And let us check storage right away, although there is no “I know” button yet. We write the learned ones by hand:

```js
localStorage.setItem("cards:learned", "[1, 2]");
// reloaded the page:
[card.textContent, counter.textContent];   // ["lesson", "Learned: 2 of 8"]
```

“book” and “teacher” are learned, and the deck starts with the third word. So reading
storage, the deck and the showing already work together — and on day 34 the “I know” button will
only have to write the number.

### Walkthrough: the markup and the code do not match

A common mistake of the first step is a typo between `index.html` and `app.js`:
the markup has `id="card"`, and the code has `querySelector("#cards")`.

```js
card;   // null
// in the console: Uncaught TypeError: Cannot read properties of null (reading 'addEventListener')
// on the page: “Loading…” hangs, there is no error text
```

The error came up not where it was made, but at the first use of the element — in the skeleton
of listeners from section 10. It stands outside functions, so the `catch` in
`load` does not see it: the script simply stops, and the call
`load()` is never reached. Hence the hanging “Loading…”. The check from section 9 —
“not a single `null`” — stands right after finding the elements exactly for this reason: it
catches the typo in the line where it was made.

## 13. The task plan for days 34–35 {#plan}

The skeleton is ready, and every stub is a task. What is left is to put them in order and estimate
the time. Every day has 90 minutes of practice. The plan of the “Cards”:

| Day | Task | Minutes | How to check |
| --- | --- | --- | --- |
| 34 | flipping a card | 15 | a click — the translation, one more click — the word |
| 34 | “I know” and “Again” | 25 | rows 4 and 5 of the feature table |
| 34 | topic buttons | 20 | row 6 |
| 34 | saving the learned words | 15 | row 8 |
| 34 | “All learned” and “Start over” | 15 | row 9 and an empty deck |
| 35 | checking on a phone | 25 | everything is visible and can be tapped on a narrow screen |
| 35 | edge cases | 25 | a table of edge cases, as on day 32 |
| 35 | shuffle the deck | 20 | from the “later” list |
| 35 | reading someone else’s code | 20 | the neighbor’s feedback is taken into account |

A plan is data too, and the sum of the minutes is better trusted to code than to your head:

```js
const plan = [
  { day: 34, task: "flipping a card", minutes: 15 },
  { day: 34, task: "“I know” and “Again”", minutes: 25 },
  { day: 34, task: "topic buttons", minutes: 20 },
  { day: 34, task: "saving the learned words", minutes: 15 },
  { day: 34, task: "“All learned” and “Start over”", minutes: 15 },
  { day: 35, task: "checking on a phone", minutes: 25 },
  { day: 35, task: "edge cases", minutes: 25 },
  { day: 35, task: "shuffle the deck", minutes: 20, later: true },
  { day: 35, task: "reading someone else’s code", minutes: 20 },
];
```

```js
[34, 35].map((d) => plan.filter((t) => t.day === d).reduce((sum, t) => sum + t.minutes, 0));
// [90, 90] — both days fit
```

The field `later` marks a task from the “later” list. If time starts
running out, it is thrown out first — and you can see how much is left without it:

```js
plan.filter((t) => t.later).map((t) => t.task);   // ["shuffle the deck"]
plan.filter((t) => !t.later).reduce((sum, t) => sum + t.minutes, 0);   // 160 — 20 minutes to spare
```

<Scheme src="scheme-plan.svg">The plan for four days: today — decisions and the first step, then — one feature at a time</Scheme>

The order of the tasks is not chosen by chance. First comes what the rest cannot be checked without: without
flipping you cannot tell whether “I know” works. What can be thrown out goes at the end: if time
runs out, “shuffle” will suffer, not “saving”.

The minutes in the plan are an estimate, not a promise. At the end of day 34 write down next to them how much
it really took, and adjust the plan of day 35. The difference between “I thought” and “it turned out” is the most useful
thing you can learn about yourself in these four days: next time the estimate will be more accurate.

## 14. Walkthrough: a plan that cannot be checked {#bad-plan}

Almost everyone’s first plan looks like this: “make the cards”, “make it pretty”,
“finish everything”. The trouble is not in the words, but in the fact that not a single task can be **closed**:
it is unclear when it is done.

| Not like this | Like this |
| --- | --- |
| make the cards | flipping: a click — the translation, one more click — the word |
| make it pretty | on a phone 360 pixels wide there is no sideways scrolling |
| saving | “I know” at “book”, reloaded — “book” is not in the deck |
| finish everything | every row of the feature table is checked by hand |

The second common trouble is **an idea that is too big**. The wish list of the first
draft of the “Cards” looked like this:

```js
const wishes = [
  { task: "sign-up and log-in", minutes: 120 },
  { task: "a chat between students", minutes: 150 },
  { task: "a leaderboard", minutes: 60 },
  { task: "a dark theme", minutes: 30 },
  { task: "cards and flipping", minutes: 40 },
  { task: "saving the learned words", minutes: 20 },
];
wishes.reduce((sum, t) => sum + t.minutes, 0);   // 420 — 2.3 times the 180 minutes of two days
```

Check your idea with the same sum: if the plan does not fit into the 180 minutes of two days,
cut. Sign-up and a chat need a real server — that is no longer Essentials. Cut not the quality but the amount: first what the application does not
work without, the rest goes to “later”. An application of five features where everything works
is stronger than an application of fifteen where half is not finished.

<Selfcheck>
1. What four conditions does a good idea for the final project meet?
   <Answer>There is a list of data; a person does something with it; something is remembered between
   page loads; you yourself are interested.</Answer>
2. Why is the idea written down in one sentence?
   <Answer>To check that the idea is clear and not too big. Every word of the sentence
   later becomes a row of the feature table.</Answer>
3. Why is the data checked before the first line of code?
   <Answer>A mistake in the data found at once is an edit of one line of the file. Found
   later, it looks like a mistake in the code, and it will be looked for in the wrong place.</Answer>
4. Why does the stub `deck` return `[]` and not nothing?
   <Answer>The code that uses it expects an array. `undefined` instead of an array
   gives the error `Cannot read properties of undefined`.</Answer>
5. Why did the check `deck().every((w) => w.topic === "food")` pass on the stub?
   <Answer>`every` on an empty array is always `true`. That is why a length check is needed
   next to it — together they fail on the stub.</Answer>
6. What is wrong with the task “make it pretty”?
   <Answer>It cannot be closed: it is unclear when it is done. A task is written down so that
   it is visible how to check it: “at a width of 360 pixels there is no sideways scrolling”.</Answer>
