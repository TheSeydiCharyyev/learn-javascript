# Day 33. Final project: idea and plan

<Subtitle>A summary of the lecture: seven steps from an idea to a plan, and what must be ready by the end of the day.</Subtitle>

## Seven steps

| Step | What you get |
| --- | --- |
| idea | there is data, a person’s actions, memory; you yourself are interested |
| one sentence | who for, what it does, why |
| features | a table “what — how to check”, the lists “later” and “does not do” |
| data | a JSON file and checks with `console.assert` |
| mockup | a narrow drawing, every part has a label: what data it comes from |
| skeleton | the frame, stubs, listeners with a plan inside, the first step |
| plan | tasks by day with minutes; the sum of a day is no more than 90 |

<KeyPoint>
Decisions first, code later. A mistake in the idea costs one line of text to fix, a mistake
in a finished program — hours. Code appears only at the sixth step.
</KeyPoint>

## Data is checked before the code

```js
console.table(data);                                          // by eye
console.assert(data.every((w) => w.id && w.word), "a field is missing");   // silent if all is well
console.assert(data.every((w, i) => data.findIndex((x) => x.id === w.id) === i), "numbers repeat");
```

Such checks are moved into a guard function `checkData` and called after every
loading: the data file is edited by hand, and a mistake can appear tomorrow. A repeated number,
an empty field, a topic with a capital letter — each gives its own strange symptom in the application.

## The skeleton and checks before the code

```js
function deck() {
  return [];   // a stub — of the same type as the real answer
}
```

<Remember>
A stub without `return` gives `undefined`, and the code below will fail with
`Cannot read properties of undefined`. Checks for a function are written before it and
chosen so that the stub fails them: `every` on an empty array is
`true`, that is why there is always a length check next to it. Checks are put into a function
that puts the data back as it was — it can be run after every edit.
</Remember>

The check “not a single `null`” right after finding the elements catches a typo in
a selector where it was made. Without it the script will fail at the first listener, and “Loading…”
will hang without explanation.

## The readiness checklist of day 33

| What | Ready when |
| --- | --- |
| the idea | one sentence; a neighbor retold it correctly |
| features | 6–10 rows, each with a check; there are “later” and “does not do” |
| data | a file or a sample object; the checks are silent |
| where what lives | a table with reasons; the variables in `app.js` |
| mockup | narrow, labeled, lies in the project folder |
| frame | the elements are found, not a single `null` |
| skeleton | stubs of the right type, listeners with a plan, no red lines |
| first step | the page shows the first data; a loading error is clear |
| plan | tasks with checks and minutes; the sum of a day is no more than 90 |

If the idea does not fit into the 180 minutes of two days, cut the amount, not the quality.
An application of five working features is stronger than one of fifteen unfinished ones.
