# Day 33. Tasks

<Subtitle>Lessons 2 and 3, 90 minutes. Warm-up — 20 minutes, main tasks — 50 minutes, starred tasks — 20 minutes. Today everyone plans **their own** final project by the steps of the lecture. Task 3 is done on the example of the “Cards” (the folder `day-33/cards`), the rest in the folder of your project (`day-33/project`), through Live Server. Keep the notes — tables and sentences — in a file `plan.md` next to the code: it will be needed at the defense on day 36.</Subtitle>

## Warm-up

<Task title="1. The idea in one sentence" level="easy" time="6">
<Goal>choose an idea that fits into two days, and put it into words.</Goal>

Take an idea from the table of section 2 or come up with your own. Check it against the four conditions
and write the idea down in one sentence: who for, what it does, why.

<Hint>
If the sentence does not fit into two lines, the idea is vague or too big. If it
has neither choice nor memory, it is too small: add a filter or favorites.
</Hint>

<Criteria>
- against each of the four conditions it is written down how the idea meets it;
- the sentence shows three parts: who for, what, why;
- a neighbor retold your idea in their own words — and did not get it wrong;
- it is decided where the data comes from: from a server, as in the catalog, or from the person, as in the to-do list.
</Criteria>
</Task>

<Task title="2. The feature table" level="easy" time="7">
<Goal>write down the promises so that they can be checked.</Goal>

Make a table “No. — feature — how to check”, as in section 4 of the lecture, and two
lines below it: “later, if time is left” and “does not do at all”.

<Hint>
A good check is an action and a visible result: “typed ‘ma’ — one card”.
Do not forget the states that are easy to miss: loading, an error, empty.
</Hint>

<Criteria>
- from 6 to 10 rows, each with a check that a person who has not seen the code can carry out;
- there is a row about a loading error or an empty result;
- “later” has at least two points, “does not do” at least one;
- every word of the idea from task 1 has found its row.
</Criteria>
</Task>

<Task title="3. Data checks on the example" level="easy" time="7">
<Goal>learn to catch mistakes in the data before the code.</Goal>

In the folder `day-33/cards` create `words.json` and `index.html`
from the lecture and repeat the checks of section 6. Then make a copy `words-bad.json` with
three mistakes: “window” has an empty translation, “apple” has the number 5, “water” has the topic “Food”.

<Hint>
The checks are the same two `console.assert` calls and the list of topics with `includes`;
only the name of the array changes.
</Hint>

<Criteria>
- on `words.json` the checks are silent, there are three topics, with 3, 3 and 2 words;
- on `words-bad.json` — two red lines, and there are four topics, with “Food”;
- the word without a translation is found with `find`;
- for each of the three mistakes it is written down what symptom it would give in the finished application.
</Criteria>
</Task>

## Main tasks

<Task title="4. Your own data" level="medium" time="12">
<Goal>prepare the data of the project and check it.</Goal>

If the data of your project comes from a server, create a JSON file: 6–10 objects,
each with an `id`. If the person creates it, write down in `plan.md` what
one object looks like, and make 3–4 sample objects. Check the data from the console.

<Example>
```js
const data = await (await fetch("items.json")).json();
console.table(data);
console.assert(data.every((x) => x.id && x.name), "a field is missing");
console.assert(data.every((x, i) => data.findIndex((y) => y.id === x.id) === i), "numbers repeat");
```
</Example>

<Hint>
Take the fields from the feature table: each one is used by something. There should be at least two categories,
otherwise there is nothing to check the filter with.
</Hint>

<Criteria>
- for every field it is written down which feature uses it;
- the checks of the fields and the numbers are silent;
- a list of categories without repeats and how many objects are in each is printed;
- one object is broken on purpose — the check caught it, the object is fixed.
</Criteria>
</Task>

<Task title="5. Where what lives" level="medium" time="12">
<Goal>turn the decisions into the variables of the program.</Goal>

Make a table “data — where — why”, as in section 8, and write the start of
`app.js`: all the variables of the program with a comment for each, and a storage key with
the project prefix.

<Hint>
Storage is read right at the declaration, with `?? []` or another “empty” value.
If a row of the feature table did not get a variable, the plan is not thought through.
</Hint>

<Criteria>
- every row of the table “where what lives” has a reason for the choice;
- every feature from task 2 has at least one variable;
- all the variables are printed in the console on the first opening of the page — the values are “empty”;
- it is explained why exactly this data is in storage, and the rest is not.
</Criteria>
</Task>

<Task title="6. The mockup and the frame" level="medium" time="13">
<Goal>see the page before the code and build its frame.</Goal>

Draw the mockup narrow, like a phone screen, and label every part: what data it is
built from and what changes it. From the mockup write `index.html` without data and the finding
of elements in `app.js`.

<Hint>
The places where data will come are empty in the markup: `<ul></ul>`,
`<p></p>`. “Loading…” is visible at once if the data comes from a server.
</Hint>

<Criteria>
- every part of the mockup has a label; there are no parts without data;
- the check “not a single `null`” from section 9 gives `false`;
- a typo is made in one selector on purpose — the check showed it, the typo is fixed;
- a photo or a drawing of the mockup lies in the project folder.
</Criteria>
</Task>

<Task title="7. The skeleton and the first step" level="medium" time="13">
<Goal>get a working page with the first data.</Goal>

Declare all the functions as stubs and all the listeners — with a plan comment inside. For one
main function (like `deck` in the “Cards”) first write a check function, then
the function itself. At the end — `load` and `render`, which show the first
data on the page.

<Hint>
A stub returns a value of the same type: `[]`, `0`, `""`.
Choose the checks so that the stub fails them — not only `every`,
but also the length.
</Hint>

<Criteria>
- the page with the skeleton opens without red lines in the console;
- the check function gives at least two red lines on the stub, and is silent on the real function;
- after a reload the page shows the first data;
- with the data file renamed — a clear error message.
</Criteria>
</Task>

## Starred tasks

<Task title="8. The plan for days 34–35" level="hard" time="10">
<Goal>spread the work over the days and fit it into the time.</Goal>

Write the plan down as an array, as in section 13: the day, the task, the minutes, the “later” mark. Compute
the sum for each day with code.

<Example>
```js
const plan = [
  { day: 34, task: "search by title", minutes: 20 },
  { day: 35, task: "sorting", minutes: 20, later: true },
];
[34, 35].map((d) => plan.filter((t) => t.day === d).reduce((sum, t) => sum + t.minutes, 0));
```
</Example>

<Criteria>
- every stub of the skeleton became a task of the plan;
- the sum for each day is no more than 90 minutes;
- every task has a check — a row of the feature table or its own;
- it is explained why the first task of day 34 is exactly this one.
</Criteria>
</Task>

<Task title="9. Someone else’s plan" level="hard" time="10">
<Goal>read someone else’s idea the way it will be read at the defense.</Goal>

Swap `plan.md` files with a neighbor and check their plan against the checklist
of the notes. Write down three remarks: what is unclear, what cannot be checked, what will not fit
into the time. Then fix your own plan according to the neighbor’s remarks.

<Hint>
A remark is useful when it has a “what” and a “why”: “the task ‘make the design’ cannot be
closed — it is unclear when it is done”. No “good / bad” grades are needed.
</Hint>

<Criteria>
- the neighbor got three remarks, each with a “why”;
- the plan is fixed according to the remarks you got, and it is visible what exactly changed;
- it is written down which remark was the most unexpected;
- it is explained why checking someone else’s plan is easier than your own.
</Criteria>
</Task>
