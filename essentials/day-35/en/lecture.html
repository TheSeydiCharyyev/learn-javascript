2. Open it on a phone

On day 2 we covered the address 127.0.0.1: it always means “my own computer”. If you type it on a phone, the phone will look for the page on itself — and will not find it. You need the address of the computer in the network. Live Server answers not only at 127.0.0.1, but also at this address, so three steps are enough.

1

The phone and the computer are in the same Wi-Fi network.

2

Find out the address of the computer: in the Windows command prompt type ipconfig and in the section of the Wi-Fi adapter find the line that starts with IPv4:

Wireless LAN adapter Wi-Fi:
   …
   IPv4 Address. . . . . . . . . . . : 192.168.1.23
3

On the phone open the same address as in the browser of the computer, but instead of 127.0.0.1 — the number from ipconfig:

http://192.168.1.23:5500/index.html

If the page does not open, the cause is usually the network: the phone is on mobile internet, not on Wi-Fi, or the network does not let one device reach another. The fallback is from day 2: the phone mode of DevTools, Ctrl + Shift + M, width 360. It shows the layout honestly, but it will not replace a finger: at the first chance, check on a real phone too.

3. Everything is tiny: the viewport line

We open the “Cards” in the phone mode with width 360 — and see a shrunk copy of the computer page: the heading, the buttons and the card are about three times smaller than expected. Let us ask the page what width it thinks it has. The window property innerWidth is the width of the page in CSS pixels:

innerWidth;   // 980 — although the screen is 360 wide

That is the answer. A mobile browser does not know whether the page is ready for a narrow screen, and just in case it builds the page as for a screen 980 wide and then shrinks it to 360 — almost three times. To stop it from doing that, one line is put into <head>:

<meta charset="UTF-8">
<meta name="viewport" content="width=device-width, initial-scale=1.0">

width=device-width — the width of the page equals the width of the device screen; initial-scale=1.0 — do not shrink anything on opening. Reloaded:

innerWidth;   // 360

Where does the mistake come from? We wrote the markup of the “Cards” on day 33 and forgot this line, and on a computer the difference is not visible. All the lessons of the course have it — check with Ctrl + U.

The first check of any project on a phone is whether <head> has the line <meta name="viewport" …>. Without it, checking everything else is useless: the sizes will be untrue.

4. For a finger and for a long word

The text became normal, but the buttons stayed small. The property offsetHeight returns the height of an element in pixels:

document.querySelector("#know").offsetHeight;   // 21

The button is 21 pixels high, and there are 4 pixels between “I know” and “Again”. With a mouse they are easy to hit, with a finger they are not: a finger covers both at once. And a miss is costly here: “I know” removes the word from the deck. This is cured not with code but with style — a bigger font, more padding inside, a bigger gap between the buttons:

<style>
  button { font-size: 18px; padding: 10px 16px; margin: 0 8px 8px 0; }
</style>
document.querySelector("#know").offsetHeight;   // 45 — more than twice as high

The rule button works on all buttons, including the topic buttons created by code. The gap became 12 pixels: 8 from margin and the space between the tags.

The longest word

You check not only your own eight words, but also the worst that can come. Let us put into words.json for a while a very long word instead of “window”: { "id": 8, "word": "internationalization", "translation": "internasionallaşdyrylma", "topic": "home" }.

The English word fits into the card. But the translation, opened with a click, runs into the right border and sticks out past it: the browser does not break a single word until it is asked to. You can ask with one CSS property in the rule .card:

<style>
  .card { … font-size: 32px; cursor: pointer; overflow-wrap: anywhere; }
</style>

overflow-wrap: anywhere allows breaking a word at any place if it does not fit as a whole. Short words are not affected. After the check, put “window” back.

Checking on a phone is checking the worst: the narrowest screen, the thickest finger, the longest word. If the worst looks decent, the usual will look decent all the more.

5. Edge cases

Task 2 is a table of edge cases, as on day 32. An edge case is data that the author did not expect: empty, broken, out of date. The “Cards” have two sources of data — storage and the file words.json, and each one can come wrong. We break storage from the console, one line at a time, and after each one we reload the page:

localStorage.setItem("cards:learned", "[object Object]");
localStorage.setItem("cards:learned", "5");
localStorage.setItem("cards:learned", "[1, 2, 3, 4, 5, 6, 7, 8, 99]");

Where does this come from in real life? "[object Object]" — it was saved without JSON.stringify, walkthrough 11 of day 31. A number — an old version of the program wrote something else under this key, or someone fixed the value by hand on the Application tab. Number 99 — the word was removed from words.json, but the storage of someone who studied earlier still has the number. We break the file one way at a time too: rename it, leave [] in it, put an extra comma after the last word.

6. Walkthrough: broken storage

Step 1. Read the red line. Storage has "[object Object]", we reloaded the page:

// Uncaught SyntaxError: "[object Object]" is not valid JSON

Step 2. Find the place. Under the message the console prints where it happened: at JSON.parse, and below it an address that ends with app.js:4:20. This is the fourth line: let learned = JSON.parse(localStorage.getItem(KEY)) ?? [];. This line is not inside try, so the error stops the whole script. The last line, load();, is never run — so nobody will hide “Loading…”.

Step 3. Check the guess in the console.

JSON.parse("[object Object]");    // SyntaxError: "[object Object]" is not valid JSON
JSON.parse("5");                  // 5 — this is valid JSON, but not an array
Array.isArray(JSON.parse("5"));   // false

With the string "5" there is no error while reading. It comes later, in deck(): a number has no method includes. But deck() is called from render(), and render() is inside try in load. That is why catch writes “Could not load the words”, although the words did load. The lesson: catch catches any error inside try, not only the one the author was thinking about.

Step 4. Fix it. We move reading storage into a function that always returns an array:

function readLearned() {
  try {
    const saved = JSON.parse(localStorage.getItem(KEY));
    return Array.isArray(saved) ? saved : [];
  } catch {
    return [];
  }
}
let learned = readLearned();   // instead of JSON.parse(…) ?? []

Three paths — one result. A broken string: JSON.parse throws an error, catch returns an empty array. Not an array, for example 5: Array.isArray answers false. No key yet: getItem returns null, JSON.parse(null) is also null, which is not an array. That is why ?? [] is no longer needed.

Step 5. Check the fix — the same way the error was found:

// storage had "[object Object]", reloaded the page:
[learned, localStorage.getItem("cards:learned")];   // [[], "[]"]

The program started from zero, and storage repaired itself: render wrote a proper empty array there. For "5" the result is the same.

7. Data is checked at the entrance

The fix of section 6 is a special case of a general rule. A program has places where data comes in from outside: reading storage and loading the file. Data is checked there, at the entrance — then all the rest of the code can trust the data and not check it in every function. Storage is already checked by readLearned. What is left is the place where storage and the file meet, and the file itself.

Numbers that are not in the file

After the words are loaded, we keep in learned only the numbers that have a word:

learned = learned.filter((id) => words.some((w) => w.id === id));   // only the numbers from the file
// storage has [1, 2, 3, 4, 5, 6, 7, 8, 99], reloaded:
counter.textContent;                        // "Learned: 8 of 8"
localStorage.getItem("cards:learned");      // "[1,2,3,4,5,6,7,8]" — 99 is gone from there too

We could fix the counter itself and count only the known numbers. But then the foreign number would stay in the data, and the next function would trip over it again. Cleaning once at the entrance is more reliable than remembering the garbage everywhere.

An empty file and a trainer without words

An empty file is the same loading error as a 404: there is nothing to learn. So its path must be the same — into catch, to a clear text:

// in load, right after words = await response.json():
if (words.length === 0) throw new Error("the file has no words");

Before, an empty file was caught by the check console.assert(words.length > 0, "there are no words") in checkData. But assert writes only to the console — for the developer. A person with a phone does not see the console; they saw “All the words of this topic are learned!”. Now the check has become handling, and we remove the line “there are no words” from checkData: it will never fire again.

What is left is to keep the frame and the buttons out of sight on any loading error. Let us wrap everything that is needed only with words into one block and hide it:

<div id="trainer" hidden>
  <p class="topics"></p>
  <div id="card" class="card"></div>
  <p>
    <button id="know">I know</button>
    <button id="again">Again</button>
  </p>
  <p id="counter"></p>
  <button id="reset">Start over</button>
</div>

We show it with the last line inside try, when everything has already worked:

render();
trainer.hidden = false;

Any error above this line goes into catch, and the trainer stays hidden. Let us run the table of section 5 once more:

CaseWhat you see now

How to write a remark

A remark is not a grade but an instruction for seeing the same thing you saw: where, what I did, what I saw, what I expected. A guess about the cause goes at the end, as an assumption:

f(), the line with return. The topic “home”, “I know” twice: the card says “All the words
of this topic are learned!”, but the counter says “Learned: 1 of 8”. I expected 2 of 8.
It looks like return fires before the line with the counter.
Bad remarks: “the code is unclear”, “I would have done it differently”, “rewrite everything”. They cannot be checked, and there is nothing to fix by them. A remark is about the code, not about the person, and one remark is one problem. The author fixes it: there is no need to rewrite someone else’s project for them.

9. Feedback on our code

Meanwhile the neighbor read our project and sent three remarks. The rule for receiving them is simple: every remark gets an answer. There are three kinds of answers: do it, explain, postpone. Staying silent is not an answer.

10. A task from “later”: shuffle the deck

We will shuffle like this: we go from the end of the array; for every place we choose a random place among the ones not touched yet — from the start up to the current one inclusive — and swap their contents. This method is called the Fisher–Yates shuffle.

function shuffle(list) {
  const result = [...list];
  for (let i = result.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    const temp = result[i];
    result[i] = result[j];
    result[j] = temp;
  }
  return result;
}

Math.floor(Math.random() * (i + 1)) is a random whole number from 0 to i, the formula of day 18. The swap goes through temp: without it the first assignment would wipe out a value. The copy [...list] (day 22) is there so as not to spoil the array that was passed in: the function returns a new one, like filter and map.

shuffle(words).map((w) => w.id);   // for example, [3, 7, 1, 8, 5, 2, 6, 4] — different every time
words.map((w) => w.id);            // [1, 2, 3, 4, 5, 6, 7, 8] — the original array is untouched

Why not sort with a random answer

On the internet a shorter way is often advised: list.sort(() => Math.random() - 0.5). Does it shuffle? Let us count how often each order of three numbers comes out in 60,000 tries:

function count(mix) {
  const result = {};
  for (let k = 0; k < 60000; k++) {
    const key = mix([1, 2, 3]).join("");
    result[key] = (result[key] ?? 0) + 1;
  }
  return result;
}
count(shuffle);   // all six orders — about 10,000
count((list) => [...list].sort(() => Math.random() - 0.5));
// "123" and "213" — about 15,000, the other four — about 7,500

Your numbers will be a little different, but the picture is the same. sort is built for a compare function that gives the same answer to the same question. Random answers confuse it, and in Chrome two orders out of six come out twice as often as the rest. Shorter does not mean right.

Where to put it and what broke

We shuffle once on loading — after the topic buttons: makeTopicButtons takes the topics in the order of the words, and shuffled words would shuffle the buttons too.

// in load, right after makeTopicButtons():
words = shuffle(words);

The order became random — and after a reload of the page the check from day 34 almost always complains:

testCurrent();
// two check messages in the console: “the first card is book” and “after the last one — the first again”

The program did not break, the check did: it knew an order that we no longer promise. “book” is now first only once in eight times on average. A check must guard a rule, not a random result. The rule is this: the first card is the first in the deck, and after the last one it comes again.

function testCurrent() {
  const oldLearned = learned;
  const oldTopic = topic;
  const oldPosition = position;
  learned = [];
  topic = "all";
  position = 0;
  const first = deck()[0];
  console.assert(current() === first, "the first card is the first in the deck");
  position = deck().length;
  console.assert(current() === first, "after the last one — the first again");
  learned = words.map((w) => w.id);
  console.assert(current() === null, "everything is learned — there is no card");
  learned = oldLearned;
  topic = oldTopic;
  position = oldPosition;
}
testDeck();
testCurrent();
// silence — with any order of the words

testDeck did not suffer: it counts the words and does not look at their order.

// AN ANSWER TO A REMARK: do it, explain or postpone
  1. On a phone everything in the “Cards” is very small, and innerWidth is 980. What is wrong?
    Answer <head> does not have the line <meta name="viewport" content="width=device-width, initial-scale=1.0">. Without it a mobile browser builds the page 980 wide and shrinks it to the width of the screen.
  2. Storage has "5". Why does the page say “Could not load the words” if the words did load?
    Answer JSON.parse("5") gives a number without an error. The error comes later, in deck() inside render() — inside try in load. catch catches any error from try.
  3. Why are foreign numbers removed from learned in load instead of fixing the counter?
    Answer Data is checked at the entrance: cleaned once — and after that it can be trusted. A fixed counter would remove the symptom, but the garbage would stay in the data.
  4. What is wrong with sort(() => Math.random() - 0.5) for shuffling?
    Answer The orders come out unevenly: in Chrome, for three numbers, two orders out of six come out twice as often. sort expects a function that gives the same answer to the same question.
  5. After shuffling, testCurrent complains. Did the program break?
    Answer No, the check broke: it knew that the first card is “book”. A check must guard a rule (the first card is the first in the deck), not a random order.
  6. What does a good remark on someone else’s code consist of?
    Answer Where, what I did, what I saw, what I expected; a guess about the cause at the end. Such a remark can be repeated and checked. “The code is unclear” cannot.
