## 1. How the defense goes {#format}

Today the lecture is about how to defend, and lessons 2 and 3 are the defenses themselves. Everyone has seven minutes,
and they have an order. Let us write it down the same way we wrote the plan — as data:

```js
const defense = [
  { part: "one sentence", minutes: 0.5 },
  { part: "demo by the scenario", minutes: 3 },
  { part: "one decision", minutes: 1 },
  { part: "one mistake", minutes: 1 },
  { part: "questions", minutes: 1.5 },
];
defense.reduce((sum, p) => sum + p.minutes, 0);   // 7
```

```js
Math.floor(90 / 7);   // 12 — this many defenses fit into lessons 2 and 3
```

If the group has more than twelve people, the teacher will say in advance how the
time is shared. A defense has three roles: **the presenter**; **the reviewer** — the
neighbor who read the project on day 35, they ask the first question; **the timekeeper**
watches the minutes and shows when a part is over.

<Scheme src="scheme-format.svg">Seven minutes of the defense; the width of the parts is proportional to the time</Scheme>

Why exactly this order? The listener first learns what it is needed for, then sees that
it works, and only then — how it is built. And the questions stand at the end with their own time,
so that a demo that is too long does not eat them.

### A timer in the console

The timekeeper does not need a clock: they have the array `defense` and the timers of day 30.
First let us count at what minute each part starts:

```js
function schedule(parts) {
  let start = 0;
  return parts.map((p) => {
    const at = start;
    start += p.minutes;
    return { part: p.part, at };
  });
}
schedule(defense).map((s) => s.at);   // [0, 0.5, 3.5, 4.5, 5.5]
```

Now for every minute of the schedule — its own `setTimeout`, and one more for the end:

```js
schedule(defense).forEach((s) => {
  setTimeout(() => console.log(`${s.at} min: ${s.part}`), s.at * 60 * 1000);
});
setTimeout(() => console.log("7 min: time is up"), 7 * 60 * 1000);
```

```js
// in the console as the defense goes:
// 0 min: one sentence
// 0.5 min: demo by the scenario
// 3.5 min: one decision
// 4.5 min: one mistake
// 5.5 min: questions
// 7 min: time is up
```

A small program, but half the course is in it: an array of objects, `map` with accumulation,
a template string, timers. Run it before every defense — and nobody will go over their
seven minutes unnoticed.

## 2. One sentence {#phrase}

The first half minute is one sentence: what it is and who it is for. Without the words “function” and “array” —
the listener does not expect them yet.

| Sentence | What is wrong |
| --- | --- |
| “I made an application in JavaScript with fetch and localStorage” | about the technology, not about the benefit |
| “These are cards” | unclear who it is for and why |
| “The Cards are a trainer of English words by topic: they show a word, on a click — the translation, and they remember what you have already learned” | good: what it is, what it does, how it helps |

The check of the sentence is simple: after it a stranger can say whether it will be useful
for them. The technology will appear in the demo and in the answers to questions — that is where it belongs.

A handy form of the sentence has three parts: **what it is**, **what it does**,
**how it helps**. For projects similar to the mini projects of the course it sounds like this:

| Project | Sentence |
| --- | --- |
| a to-do list, as on day 29 | “A to-do list for the week: you add a task, mark what is done, and nothing is lost after the page is closed” |
| a catalog, as on day 32 | “A book catalog: search by title, a filter by genre and favorites that are remembered” |

## 3. The demo by a scenario {#demo}

The demo is on a phone, by the scenario you went through on day 35. Before the defense the project is
open at the address of the computer in the network and is in its initial state. The simplest way is to press your own
“Start over” button. If you want to do it from the console — remove the key and reload the page right away:

```js
localStorage.removeItem("cards:learned");   // and reload the page right away
```

Why right away? While the page is open, `learned` lives in memory, and
`render` writes it to storage after every action — walkthrough 13 of day 34:

```js
// removed the key and pressed “Again” without reloading the page:
localStorage.getItem("cards:learned") !== null;   // true — render wrote learned back
```

### What to prepare in advance

| What | Why |
| --- | --- |
| the phone is charged, in the same Wi-Fi network, the address is already open | not to spend the demo on typing the address |
| the project is in its initial state | the counter says “0 of 8”, not the traces of a rehearsal |
| the code and the console are open on the computer | questions are answered there: the console of the phone is not visible |
| one rehearsal with a clock | find out whether you fit into seven minutes |

There is a trap connected with the third row. On the phone the project is open at the network address, and on
the computer — at `127.0.0.1`. For the browser these are two different sites, and each one has
its own storage:

```js
// on the phone, at the network address, “I know” twice — “Learned: 2 of 8”
// on the computer, at 127.0.0.1:
localStorage.getItem("cards:learned");   // "[]" or null — what was learned on the phone is not here
```

So if a question needs the data from the phone, open on the computer the same
network address as on the phone. Or better, answer “what happens if” on a clean page of the
computer — the experiments will not spoil the demo.

During the demo you **show, not tell**: an action — and what
changed. “I press ‘I know’ — the word is gone, the counter says ‘1 of 8’.” Start with the main
scenario, edge cases — one or two, if there is time left.

And if something breaks during the demo? Do not hide it. Open the console, read the red line
out loud and ask the data — steps 1 and 2 of the table “If you are stuck” of day 34:

```js
[words.length, learned, topic, position, flipped];   // [8, [], "all", 0, false] — on a page that was just opened
```

A mistake calmly worked out at the defense is a demo of skill too. Confusion is not.

## 4. One decision {#decision}

A minute for one place in the code you are happy with. The story is built of four parts:
what was being decided, how it was done, what would be different, how it was checked. An example for the “Cards” —
the current card is computed, not kept:

```js
function current() {
  const cards = deck();
  return cards.length === 0 ? null : cards[position % cards.length];
}
```

“What would be different” is strongest when it is shown. Let us say the deck was saved once —
on loading and on a change of topic:

```js
let cards = [];   // the deck saved in advance

function current() {
  return cards.length === 0 ? null : cards[position % cards.length];
}
// in load and in the topics listener: cards = deck();
```

We open it, “teacher” came first, we press “I know” twice:

```js
card.textContent;      // "teacher" — the word is learned, but it stayed on the screen
learned;               // [2, 2] — one number twice
counter.textContent;   // "Learned: 2 of 8" — the counter counts one word as two
[deck().length, cards.length];   // [7, 8] — the saved deck is out of date
```

The copy of the deck was out of date after the very first “I know”. The function `current` builds
the deck anew every time and that is why it does not go out of date. The check that guards this is
`testCurrent` of day 35. Here is how it sounds in a minute:

<KeyPoint>
“I do not keep the current card, I compute it from the deck and the position. If the deck is kept, after
‘I know’ the learned word stays on the screen, and the counter counts it twice — I checked.
The rule is guarded by `testCurrent`.”
</KeyPoint>

### The second example: topic buttons from the data

The topic buttons could have been written right in the markup — it is shorter and clearer at first
sight:

```html
<p class="topics">
  <button data-topic="all">all</button>
  <button data-topic="school">school</button>
  <button data-topic="food">food</button>
  <button data-topic="home">home</button>
</p>
```

What would be different is shown like this: a word of a new topic is added to `words.json` —
`{ "id": 9, "word": "street", "translation": "köçe", "topic": "city" }` — and
we look at the buttons in both variants:

```js
// buttons in the markup:
[...topics.children].some((b) => b.textContent === "city");    // false — there is no button
// buttons from the data, makeTopicButtons of day 34:
[...topics.children].some((b) => b.textContent === "city");    // true — it appeared by itself
```

In the first variant the word “street” gets only into the topic “all”, and “city” cannot be
chosen: someone forgot to add its button. In the second the button appeared by itself — the topics are taken from the same
data as the words. The decision sounds like this: “I build the topic buttons from the words, so a new topic in
the file does not need an edit of the markup.”

Other decisions of the course worth talking about, if your project has them:

| Decision | What would be different | Where we covered it |
| --- | --- | --- |
| one `render` draws everything | a part of the screen was not updated | day 29 |
| writing to storage is in one place | a new listener forgot to save | day 35, the neighbor’s feedback |
| topic buttons come from the data | a new topic in the file has no button | day 33 |
| data is checked at the entrance | checks in every function | day 35 |

## 5. One mistake {#bug}

One more minute — the story of one mistake. Not just any, but one that taught you something: where you searched for a long time or
where the cause turned out to be not where you thought. The order of the story is five steps:

| Step | The “Cards”, day 35 |
| --- | --- |
| 1. the symptom | “Loading…” hangs, there are no words |
| 2. how we found it | a red line in the console and the stack under it |
| 3. the cause | `JSON.parse` outside `try` on a broken string in storage |
| 4. the fix | `readLearned`, which always returns an array |
| 5. how we checked that it will not come back | a check function |

Steps 2 and 4 are code, and that is what is shown:

```js
// Uncaught SyntaxError: "[object Object]" is not valid JSON
//     at JSON.parse (<anonymous>)
//     at …/app.js:4:20
```

```js
let learned = readLearned();   // instead of JSON.parse(…) ?? [] — always an array
```

Step 5 is skipped most often, but it is the main one: it tells “fixed” from “fixed
for good”. The mistake is turned into a check — like `testDeck` and
`testCurrent`, only for the data entrance:

```js
function testInput() {
  const saved = localStorage.getItem(KEY);
  localStorage.setItem(KEY, "[object Object]");
  console.assert(readLearned().length === 0, "a broken string — an empty array");
  localStorage.setItem(KEY, "5");
  console.assert(readLearned().length === 0, "not an array — an empty array");
  localStorage.setItem(KEY, saved);   // put it back as it was
}
```

```js
testInput();
localStorage.getItem("cards:learned");   // the same as before the check — and silence in the console
```

If someone one day puts `JSON.parse` back in its old place, the check
will shout before “Loading…” hangs for a person with a phone.

## 7. The reviewer’s questions {#questions}

There are three kinds of questions at a defense, and each one has its own move:

<Scheme src="scheme-questions.svg">Every kind of question has its own move; a made-up answer is worse than an honest “I do not know”</Scheme>

The main rule: **not knowing the answer is not a mistake, making it up is**. For
“what happens if” you have the console in your hands — a check takes less than a minute. Let us go through the questions
that are asked most often at the defense of the “Cards”.

### “Where are the learned words saved?”

A “where” question is the simplest one if you do not retell but show. Two lines, and both
are visible in the file:

```js
let learned = readLearned();                          // reading — once, at the start
localStorage.setItem(KEY, JSON.stringify(learned));   // writing — at the end of render, after every action
```

The answer: “I read once at the start and write at the end of `render` — that is why any
action is saved by itself.” If an answer to “where” takes longer than five seconds, then
saving is smeared over the program — and that is already a reason for a “why” question.

### “What if two words have one number?”

We do not guess — we check. Let us add to `words.json` a ninth word with someone else’s number:
`{ "id": 7, "word": "door", "translation": "gapy", "topic": "home" }`. On
loading the console says “numbers repeat”: `checkData` of day 33 fired.

```js
counter.textContent;   // "Learned: 0 of 9"
// the topic “home”, “Again” until “door” comes up, and “I know” once:
deck().map((w) => w.word);   // ["window"] — two words left at once: door and house
counter.textContent;         // "Learned: 1 of 9"
```

The answer: “A number is the name of a word for the program. One name for two words — and the program
mixes them up. There is a warning in the console, and it is the file that gets fixed.”

### “And if it is opened in two tabs?”

Tab B was opened earlier, in A “I know” was pressed twice, then in B — once:

```js
// after two “I know” in tab A:
JSON.parse(localStorage.getItem("cards:learned")).length;   // 2
// after one “I know” in tab B:
JSON.parse(localStorage.getItem("cards:learned")).length;   // 1 — the write of B wiped out A
```

We reloaded A — “Learned: 1 of 8”, two words are gone. Each tab keeps its own
`learned` in memory and writes it as a whole; the last write wins. The honest
answer: “Not provided for. I wrote it into ‘later’.” This is a good answer: checked, short, with
a plan.

### “And if ‘I know’ is pressed ten times quickly?”

A finger cannot press that fast, but the console can: `click()` calls the listener
like a real click. There are eight words, ten clicks:

```js
for (let i = 0; i < 10; i++) knowButton.click();
[learned.length, counter.textContent];   // [8, "Learned: 8 of 8"] — the two extra clicks broke nothing
```

Each click learned the next word, and the last two ran into the guard
`if (current() === null) return;` of day 34 — there are no red lines. The answer: “The button
is hidden on an empty deck, and the listener is guarded anyway — here is the line.”

### “And if there are ten thousand words?”

Let us make ten thousand words right in the console and time `render` with
`console.time` of day 2:

```js
const big = [];
for (let i = 1; i <= 10000; i++) {
  big.push({ id: i, word: `word${i}`, translation: `söz${i}`, topic: "test" });
}
words = big;
learned = [];
for (let i = 1; i <= 5000; i++) learned.push(i);
```

```js
console.time("render");
render();
console.timeEnd("render");   // render: … ms — every computer and every run has its own number
```

In different runs we got from 5 to 114 ms: the time depends on the computer and on
what the browser was doing before. But where it comes from is clear: `deck()` asks `learned.includes` for each of the ten
thousand words, and that one goes through up to five thousand numbers.
For eight words this is not visible, for ten thousand it is already noticeable. It can be sped up with the collection
`Set` — it is covered in course 2:

```js
const learnedSet = new Set(learned);                             // course 2, module I5
big.filter((w) => !learnedSet.has(w.id)).length;                 // 5000 — the same answer, course 2
```

In our runs the filter with `includes` took from 5 to 22 ms, and with
`Set` — about a millisecond or less.
And an important thing after the experiment: `render` wrote five thousand numbers into storage. Reload
the page — and you will see “Learned: 8 of 8”, because numbers 1–8 are among them too. Experiments on
real data leave traces: after them — “Start over”.

### “Why does storage keep numbers and not the words themselves?”

```js
JSON.stringify(learned).length;   // 17 — when all eight are learned
JSON.stringify(words).length;     // 498 — all the words in full
```

The answer has two reasons. Numbers are shorter. And the main one: if a translation is fixed in the file, the progress
will not break — the number is the same, and the word is taken fresh from the file every time. The words live in one
place, in `words.json`, and storage remembers only which of them are learned.

### “Why does the shuffle come after the buttons and not right after loading?”

The reviewer sees in `load` the line `words = shuffle(words)` below
`makeTopicButtons()` and asks: would it not be clearer to shuffle right when
the words arrive? It is better to show the answer. Let us move the line above the buttons, reload the page three
times and look at the topics:

```js
[...topics.children].map((b) => b.textContent);
// ["all", "food", "school", "home"], then ["all", "school", "home", "food"], then ["all", "home", "school", "food"]
```

The buttons jump. `makeTopicButtons` collects the topics in the order in which
it meets them in the words — shuffled words shuffle the buttons too. Whoever found the “food” button in one place yesterday will find it in another place today. That is why the order of the lines is this:

```js
makeTopicButtons();       // topics — in the order of the file
words = shuffle(words);   // the words are shuffled only after that
```

```js
// six reloads in a row:
[...topics.children].map((b) => b.textContent);   // always ["all", "school", "food", "home"]
```

The words are still in random order. The answer at the defense: “The buttons are built from
the order of the words. If you shuffle earlier, the buttons jump every time it is opened — I checked.
That is why first the buttons, then the shuffle.” Behind two lines of code there is a decision that
can be shown. Questions about the order of lines are asked often: every order must have a
reason.

## 8. If you are the reviewer {#reviewer}

At every defense you are also a listener, and at one of them — the reviewer. A good question helps
the presenter show what they know, and a bad one only tests their nerves:

| A bad question | A good question |
| --- | --- |
| “Why like this?” | “Why is the current card computed and not kept?” |
| “And if everything breaks?” | “What happens if `words.json` is empty?” |
| “Are you sure it works?” | “Show where the learned words are saved.” |
| “Why did you not do it like I did?” | “What other options were there, and why was this one chosen?” |

A good question is specific, it can be answered with code or a check, and it is about the project,
not about the person. The reviewer’s first question is better taken from your own remarks of day 35: you already
know where the project has a weak spot, and you can ask what became of it.

After the defense the reviewer gives feedback of two parts: **one strong side — with
a place in the code** and **one suggestion — what to check in “later”**.
For example: “It is good that the data is checked in `readLearned` — a broken storage
is not a problem. Check two tabs: my progress got wiped out.” Praise without a place and advice without
a check is not feedback.

## 9. How it is graded {#marks}

What is graded is not the number of features but how well what was promised works and how clear it is to the author.
Five criteria, from 0 to 2 points each:

| Criterion | 2 points | 1 point |
| --- | --- | --- |
| works | all the rows of the feature table | all but one or two minor ones |
| phone | everything is visible and can be tapped | small inconveniences |
| edge cases | there is a table, the causes are fixed at the entrance | there is a table, not everything is fixed |
| code | clear names, one `render`, the checks are silent | one of the three is weak |
| answers | a place in the code or a check in the console | some answers are guesses |

```js
const marks = { works: 2, phone: 2, edges: 1, code: 2, answers: 1 };
Object.values(marks).reduce((sum, m) => sum + m, 0);   // 8 — out of 10
```

Zero for a criterion is when the main thing does not work or was not checked at all. Notice what is not in
the table: “complexity”, “how many lines”, “beauty”. A small project that works
on a phone and is clear to its author is worth more than a big one that the author cannot explain.

<Mistake>
Common mistakes at a defense: showing on a computer instead of a phone; reading the code from the screen
line by line; starting with “I did not manage”; arguing with the reviewer instead of checking in
the console; filling a pause with words like “well, something like that”. Each of them eats minutes,
and there are only seven.
</Mistake>

## 10. The whole course in one program {#course}

Thirty-five days ago we opened the console. Look at the “Cards” — every module of the course
works in them:

<Scheme src="scheme-course.svg">Eight modules of the course — eight parts of one program</Scheme>

One line of the program for each module — read them and recall the day where it
appeared for the first time.

```js
// E1: the console is not only for output, but also for checks
console.assert(deck().length === 3, "the topic “food” has three words");
```

```js
// E2: variables, comparison, the ternary operator
card.textContent = word === null ? "All the words of this topic are learned!" : (flipped ? word.translation : word.word);
```

```js
// E3: a condition and an exception — the error goes into catch
if (!response.ok) throw new Error(`server replied ${response.status}`);
```

```js
// E4: a function without side effects — it only answers
function deck() {
  return words.filter((w) => !learned.includes(w.id) && (topic === "all" || w.topic === topic));
}
```

```js
// E5: a template string and a random whole number
counter.textContent = `Learned: ${learned.length} of ${words.length}`;
const j = Math.floor(Math.random() * (i + 1));
```

```js
// E6: array methods and JSON
learned = learned.filter((id) => words.some((w) => w.id === id));
localStorage.setItem(KEY, JSON.stringify(learned));
```

```js
// E7: delegation — one listener for all the topic buttons
topics.addEventListener("click", (event) => {
  const button = event.target.closest("button");
  if (!button) return;
  topic = button.dataset.topic;
});
```

```js
// E8: loading from a server — in load, inside try
async function load() {
  const response = await fetch("words.json");
  words = await response.json();
}
```

The last three lines are a shortened `load`: without checks and without
`catch`, only to show where module E8 works. The full version is in
section 11 of day 35. Not one of these lines would have been clear on day 1. Today each one
is read in a second — that is what changed during the course.

## 12. After the defense {#retro}

When the defenses are over, one last thing is left — a retrospective: what was in the plan and
what came out in reality over all the days of the project.

```js
// plan — the array of tasks from day 33; actual — from the sections “Plan and actual” of days 34 and 35
const actual = { 34: 100, 35: 90 };
[34, 35].map((d) => plan.filter((t) => t.day === d).reduce((sum, t) => sum + t.minutes, 0));   // [90, 90]
Object.values(actual).reduce((sum, m) => sum + m, 0);   // 190 — 10 minutes more than the 180 of the plan
```

Ten minutes out of a hundred and eighty — the estimate was off by about six percent. For a first
project this is good accuracy, and it did not come by chance: the plan was broken into tasks of
15–25 minutes, and an overrun was moved to “later” at once.

A retrospective is written briefly, for yourself, while everything is fresh:

| Question | Why |
| --- | --- |
| what worked out best? | repeat it in the next project |
| which task took more than planned, and why? | next time plan more time for it |
| what would I do differently from the very start? | the most valuable answer of the day |
| what from “later” comes first? | the project goes on after the defense too |

| Question | Answer |

<Selfcheck>
1. What is wrong with the sentence “I made an application in JavaScript with fetch and localStorage”?
   <Answer>It is about the technology, not the benefit: the listener does not learn what the application does and who
   it is for. The technology belongs in the demo and in the answers to questions.</Answer>
2. Before the demo the storage key was removed, but the learned words came back. Why?
   <Answer>`learned` stayed in memory, and the very first `render` wrote
   it back. Remove the key and reload the page right away, or press “Start over”.</Answer>
3. Why is the part “what would be different” the strongest in a story about a decision?
   <Answer>It shows that the decision was chosen and did not just happen. If it is also
   checked — as with the saved deck — it is no longer an opinion but a fact.</Answer>
4. Which step of a mistake story is skipped most often, and why is it important?
   <Answer>The fifth: how you checked that the mistake will not come back. A check function like
   `testInput` tells “fixed” from “fixed for good”.</Answer>
5. The reviewer asks: “And if it is opened in two tabs?” You do not know. What do you do?
   <Answer>Do not guess, check: open two tabs and look at storage. If the
   behavior is bad, say honestly that it is not provided for, and write it into “later”.</Answer>
6. Why do you need “Start over” after the experiment with ten thousand words?
   <Answer>`render` wrote thousands of numbers into storage. After a reload of the
   page, the numbers of the real words will be among them, and all of them will be “learned”.</Answer>
